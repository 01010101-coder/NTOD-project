## Context

См. proposal.md — Why. Состояние на момент планирования (проверено в этой сессии): `common/` содержит `timeutil.py` и `logging_setup.py` из `m1-common`; `config.yaml` в корне репо отсутствует; модуля конфигурации в `common/` нет. `pydantic>=2` и `PyYAML` уже в `dependencies` (`pyproject.toml:14-15`), пакет `common` перечислен явно в `[tool.setuptools] packages` (`pyproject.toml:28`) — новые модули внутри него правки упаковки не требуют. Тулинг вехи готов: `make lint && make test` зелёные на текущем скелете.

## Goals / Non-Goals

**Goals:**
- Зафиксировать ключи всех секций скелета §5 плана M1 в pydantic-моделях с дефолтами (правило «старые конфиги грузятся») и `extra="forbid"` (решение §7.3).
- Дать единый вход загрузки `config.yaml` и эталонный `config.yaml` в корне репо (дерево §3).
- Закрыть пункты DoD §8: «конфиг грузится целиком из дефолтов; эталонный `config.yaml` валиден» — тестами `tests/test_config.py`.

**Non-Goals:**
- Смысловые значения калибровки (профили спроса, граф города, коэффициенты событий) — наполняются и уточняются в M2 (приложение А плана M2); в M1 фиксируются только ключи и стартовые значения.
- SQLite-схема и путь к БД «в деле» (создание каталога `data/`, подключение) — это `m1-storage`; конфиг лишь даёт `storage.db_path`.
- Чтение переменных окружения/CLI-переопределений поверх YAML — в вехе не запланировано; добавляется без изменения контракта при необходимости.
- Валидация «смысла» значений (положительность, доли 0–1) сверх типов — минимальные проверки только там, где это зафиксировано в specs.

## Decisions

1. **Модуль `common/config.py`, а не отдельный пакет.** Соглашение проекта отводит `common/` под «загрузку config.yaml (pydantic-модели)»; пакет `config/` на верхнем уровне потребовал бы правки `packages` в `pyproject.toml` и не даёт выгоды. Файл кладётся в уже явный список пакетов — правок упаковки нет (тот же приём, что в `m1-common`).
2. **`extra="forbid"` на каждой модели (`ConfigDict`) — решение §7.3.** pydantic v2 в `ValidationError` уже называет путь до лишнего ключа (`loc` вида `drivers.coun`) и причину («Extra inputs are not permitted»); свой враппер поверх не пишем — сообщение pydantic удовлетворяет требованию «понятная ошибка с путём», а тест проверяет подстроку с путём (`drivers`, `coun`), не точный текст (устойчивость к смене формулировок pydantic). Альтернатива — `extra="ignore"` — отклонена прямо решением §7.3: опечатка в конфиге должна падать, а не молчать.
3. **Дефолты у каждой секции: скаляры — из скелета §5, коллекции — пустые контейнеры.** Значения §5: `seed=42`, `storage.db_path="data/taxi.db"`, `population.scale=1.0`, `demand.dest_decay_min=15`, `drivers.count=200`, `drivers.wait_limit_min=6`, `pricing.elasticity_alpha=1.0`, `engine.agg_step_min=5`. `city.zones/roads`, `demand.profiles`, `weather.*`-наборы и вложенные `{...}` §5 не дают значений — их дефолты в M1 пустые/нейтральные (`zones=[]`, `roads=[]`, `profiles={}`, `events.friday_evening.enabled=false` и т.п.); это соответствует «смысловые значения наполняются в M2», а инвариант «конфиг целиком из дефолтов валиден» сохраняется. `default_factory` для мутабельных дефолтов — без shared-состояния между инстансами.
4. **Ключи нефиксированных в §5 секций берутся из их же комментариев §5.** `city`: зона = `id`, `archetype`, `attractiveness`, координаты карты `x`, `y`; дорога = `from_zone`, `to_zone`, `minutes` (дорожный граф). `weather`: «шанс дождя в день, параметры эпизода, множители» → `rain_chance_per_day`, `episode_duration_min`, `request_multiplier`, `driver_multiplier`. `events.friday_evening`: «дни, часы, архетипы, множитель» → `weekdays`, `hours`, `archetypes`, `demand_multiplier` (+`enabled`). `pricing.surge_injection`: обучающие инъекции → `enabled`, `days`, `hours`, `multiplier`. Это фиксирование ключей — прямая обязанность M1 («секции и ключи фиксируются в M1»); значения — стартовые, уточняются в M2 без изменения моделей.
5. **Загрузка: `yaml.safe_load` + явная проверка «это словарь».** `safe_load` (не `load`) — конфигу не нужен произвольный YAML. Пустой файл/пустой словарь → `AppConfig()` из дефолтов. Если `safe_load` вернул не `dict` (список, скаляр) — `ValueError` с текстом «конфиг должен быть словарём секций, получен …» до передачи в pydantic: иначе `AppConfig(**data)` падает внутренним `TypeError`, что нарушает сценарий «YAML не словарём отклоняется». API: `load_config(path) -> AppConfig` для файла; конструктор `AppConfig(...)` и `AppConfig.model_validate(dict)` — вход для кода и тестов без файла.
6. **Режим pydantic — стандартный (lax).** YAML-значения чистые (`42` — int, `1.0` — float), поэтому `strict=True` не нужен и ломал бы удобные записи (`1` для float-поля); собственные валидаторы сверх типов не добавляем — контракт M1 это «типы и запрет лишних ключей», не семантика значений (см. Non-Goals).
7. **Эталонный `config.yaml` в корне репо (дерево §3) — полный, со всеми секциями и значениями дефолтов §5.** Он одновременно документ и фикстура теста: тест находит его относительно себя (`Path(__file__).resolve().parents[1] / "config.yaml"`), без зависимости от cwd — `pytest` запускается из корня через `make test`, но путь не должен на это опираться. Дрейф эталона от моделей ловится тестом «эталонный файл валиден» + `extra=forbid`: лишний ключ в эталоне уронит тест, а не промолчит.
8. **Совместимость с планом (учтено по ask'у).** Скелет §5 воспроизведён секция в секцию (порядок и имена); решение §7.3 (`extra=forbid` + дефолты) — решения 2 и 3; правило соглашений «каждая новая секция имеет дефолты» — решением 3 и требованием specs; DoD §8 «конфиг грузится целиком из дефолтов; эталонный `config.yaml` валиден» — группой финальных задач tasks.md. Способ проверки из ask'а (четыре теста `test_config.py`) покрыт сценариями specs один к одному. Схема SQLite §6 конфиг не затрагивает (это `m1-storage`); для неё конфиг даёт только `storage.db_path`.
9. **Ruff-совместимость сразу.** Модуль пишется под правила `E,F,I,W,UP` и line-length 100 из `pyproject.toml`, docstring на русском, идентификаторы на английском (соглашение проекта) — чтобы финальный `make lint` не потребовал отдельного прогона `make fmt`.

## Risks / Trade-offs

- [Пустые дефолты `city.zones/roads` валидны, но город без зон симуляцию не запустит] → принято осознанно: в M1 симулятора нет; M2 обязан дать калиброванные значения (приложение А плана M2), и место для них уже зарезервировано моделями. Тест фиксирует именно «валидность из дефолтов», а не «пригодность к симуляции».
- [Тест на «понятную ошибку» завязан на текст pydantic] → проверяется подстрока пути (`drivers.coun` / ключ корня), не точная формулировка; при мажорном обновлении pydantic меняется одна строка теста.
- [Ключи `weather`/`events`/`pricing.surge_injection` зафиксированы по комментариям §5 и могут не совпасть с финальной калибровкой M2] → это предусмотрено планом: значения и уточнение ключей — зона M2; благодаря дефолтам расширение секций не ломает старые конфиги, а `extra=forbid` отловит рассинхрон на этапе загрузки, а не в движке.
- [Эталонный `config.yaml` в корне не входит в устанавливаемый пакет] → принято: эталон — репозиторный артефакт (дерево §3); в пакет он не нужен, загрузка в рантайме идёт по явному пути.

## Migration Plan

Не применим: только добавляются файлы (`common/config.py`, `config.yaml` в корне, `tests/test_config.py`); существующие код и конфиги не меняются. Откат — удаление добавленных файлов; потребителей в репо ещё нет.
