# Design: m6-compare-tab

## Context

Опора — `m6-worlds` (реестр `simulator.branches.list_worlds` → `WorldInfo`{name, db,
label, exists}; тень-прогнозы `mlp`/`lstm` в `forecasts` каждой ветки с дня 31),
`m6-worlds-ui` (`GET /api/worlds`, `world_db`), `m3-ml-tab` (вкладка
«Лаборатория»: `body[data-tab]`, ленивая загрузка, `LabCharts.drawTimeSeries` с
guard'ом нулевого layout'а, `redrawLabCharts` на показе), `ml.metrics`
(`join_facts`, `regression_metrics`, `deficit_metrics`), `ml.dataset`
(`SqliteRowSource`, `world_start`, `deficit_label`), `simulator.city.build_city`
(`path_min`). Выручка в БД не хранится (§10.15 M2) — формула восстанавливается
post-hoc.

Замер на реальной сетке (2026-11-15, тест-неделя с 2026-12-02): невыполненных
заказов 0 во всех ветках, `zone_metrics_5min.avg_wait_min` = 0 (это ожидание
**назначения**, водитель почти всегда есть); различаются поездки
(63 474 / 60 259 / 62 211 / 61 344), ожидание подачи `pickup_at − created_at`
(0.66 / 0.40 / 0.57 / 0.50 мин), доля дефицитных зона-бакетов
(18.2 / 14.7 / 17.3 / 15.4 %) и выручка (14.31 / 14.25 / 14.27 / 14.28 млн).
Отсюда решения 2–3.

## Goals / Non-Goals

**Goals:** одна функция расчёта исходов ветки по её БД, проверяемая ручным SQL;
REST без пересчёта на каждый запрос; вкладка по прецедентам `m3-ml-tab`.

**Non-Goals:** поминутные ряды кроме кумулятивной выручки; доверительные
интервалы; селектор окна/горизонта в UI; переиспользование графика «Города»;
показ точности в B/C/D даже «для справки».

## Decisions

1. **Расчёт — чистый модуль `app/compare.py`, не `server.py`.** Функции
   `branch_outcomes(db, cfg, path_min, window)` → dict исходов + часовой ряд;
   `accuracy_vs_base(db_a, cfg, window)` → точность; `build_compare(cfg,
   worlds_dir)` собирает ответ (дельты, порядок реестра). Сервер только кэширует
   и отдаёт. Тестируется без TestClient, `server.py` (уже >1000 строк) не растёт.
   Альтернатива `ml/compare.py` отклонена: это не ML-слой, а аналитика миров
   поверх `simulator` + `ml.metrics`; `app` уже импортирует оба.
2. **Ожидание = `pickup_at − created_at` завершённых заказов по `trips`.**
   `avg_wait_min` агрегатов — время до назначения, на сетке тождественно 0, не
   отличает ветки и не соответствует «ожиданию» пассажира. Из `trips` число
   сверяется с SQL напрямую (DoD §9). Считается в SQL через `julianday`, разность
   в минутах (время с точностью до минуты, дробей нет).
3. **Доля дефицита — пятый исход сверх плана.** Правило контракта по
   `zone_metrics_5min` окна (то же, что `deficit_label`). Это главная величина,
   которую двигают политики при невыполненных ≈ 0; столбец «невыполненные»
   остаётся (план, честный ноль). Отклонено: убрать «невыполненные» — тогда
   таблица скрыла бы, что город на сетке не доходит до брошенных заказов.
4. **Выручка — Python-проход по завершённым заказам окна с `path_min` из
   `build_city(cfg)`**, не SQL: матрицы путей в БД нет. ~60 тыс. строк на ветку
   — доли секунды. Часовой ряд копится в том же проходе: индекс часа =
   `(created_at − start) // 60 мин`, затем cumsum; последняя точка = итог по
   построению (одна сумма, без расхождения округлений).
5. **Окно — по `created_at` заказа, `[world_start + train_days, + test_days)`.**
   Заказ, созданный в последние минуты недели и завершённый после, считается —
   цена заказа фиксируется при создании (§M2), политика активна с дня 31 по
   тому же правилу (`PolicyContour._activation`). Метрики — по `ts` бакета в том
   же полуинтервале.
6. **Точность против A — `SqliteRowSource(a-base.db)` + `join_facts` +
   `regression_metrics`/`deficit_metrics`** по строкам `forecasts` A окна
   (семейства `mlp`/`lstm`, горизонты 15/30). Переиспользование гарантирует ту
   же математику, что в сводке M3. Отдаются MAE спроса и F1 дефицита;
   precision/recall тоже кладутся в ответ (дёшево), UI показывает MAE и F1.
7. **Кэш — по ключу (путь, `st_mtime_ns`, `st_size`) всех БД веток.** Ответ
   считается при первом запросе (~2–4 с: загрузка `SqliteRowSource` A — самая
   дорогая часть) и хранится в замыкании `create_app`; изменение ключа —
   пересчёт. Альтернатива «считать при старте сервера» отклонена: замедляет
   старт ради вкладки, которую могут не открыть; файл-кэш на диске — лишняя
   инвалидация.
8. **Дельты — сервером, в процентах, `null` при нулевой/отсутствующей базе.**
   Клиент не дублирует арифметику и не рисует `Infinity`. Округление — только в
   UI (сервер отдаёт полные float — сверка с SQL точная).
9. **Фронт — секция `#compare` под `body[data-tab="compare"]`, состояние
   `compare = {loaded, loading, data}` и `ensureCompareLoaded`/`redrawCompare` по
   образцу лаборатории; график — `LabCharts.drawTimeSeries` (ось времени,
   серия на ветку, фиксированные цвета веток A серый / B оранжевый / C голубой /
   D фиолетовый)**. Лучшее значение столбца — класс `best`; направление
   «лучше» — константа на столбец в `app.js`. Ось Y кумулятивной выручки — от
   нуля не включается (`includeZero: false`): линии к концу недели различаются
   на ~0.5 %, с нулём их не отличить; вместо этого под графиком — подпись
   итоговой разницы к A.

## Risks / Trade-offs

- [Выручка различается на десятые процента — «вердикт» по выручке слабый] →
  честно: план §8 п. 3 это предвидел; таблица ставит доли дефицита и ожидание
  рядом, подпись графика называет разницу числом. Мир не подкручиваем.
- [B выигрывает по доле дефицита у C/D на реальной сетке] → это результат
  эксперимента, а не дефект вкладки; вкладка отображает числа как есть, вывод —
  в отчёте вехи.
- [Первый запрос медленный (загрузка источника A)] → кэш (решение 7);
  вкладка показывает «загрузка…» до ответа.
- [Тест-БД без части таблиц/строк] → пустые выборки дают `null`/0, не исключения
  (сценарии спеки); мини-БД тестов строятся `storage.schema.init_db`.
- [Изменение формы ответа ломает фронт] → тест статики проверяет наличие
  элементов вкладки, тест REST — ключи ответа; форма фиксирована спекой.
