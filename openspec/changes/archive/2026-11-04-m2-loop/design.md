## Decisions

### 1. Часы мира и каркас цикла Engine.run

`run(days, writer, *, progress=None)`: `sim_start_dt = from_iso(cfg.engine.sim_start + " 00:00:00")` — строгий `from_iso` (решение §10.16); минуты `t = add_minutes(sim_start_dt, k)`, `k = 0 … days×1440−1`. Один `rng = np.random.default_rng(seed)`, `seed=None → cfg.seed`, создаётся в `__init__` и передаётся `WorldEnv(cfg, rng)` и `spawn_requests(rng, …)` — один генератор на мир (§10.9). Шаги каждой минуты — в порядке §3.7: (1) среда: на `00:00` суток — `env.advance_day(day_index)` (розыгрыши дождя и инъекций на сутки); (2) спавн; (3) диспатч; (4) движение; (5) истечения; (6) на каждой 5-й минуте — агрегат. Итерации — только по упорядоченным последовательностям (зоны по возрастанию `zone_id` — `CitySpec.zones` сортирован контрактом; ожидающие заказы по `(created_at, внутренний_id)`; внутренние id — счётчик с 1, решение §10.11). Wall-clock: `time.perf_counter` замеряется только по периметру `run` для `progress.elapsed_sec` и `Summary.wall_sec` (§5 — замер входит в DoD; поля заданы приложением Б) и не влияет на состояние мира; `datetime.now()`/`time.*` в механике запрещены (§2.2 п. 3). Альтернатива «отдельный rng для среды и спроса» отвергнута: нарушает §10.9 и делает A/B-ветки несравнимыми.

### 2. Передача среды в спавн: `event_mult` — значение из конфига, условие уже в demand

Движок вызывает `spawn_requests(rng, city, t, is_rain=env.is_rain(t), event_mult=cfg.events.friday_evening.demand_mult, price_mult_by_zone=…, cfg)` — всегда одно и то же **значение** из конфига (эталон 1.3): условие «пятничный вечер для архетипа» проверяет `demand.py` (приватный `_friday_evening_active`, `demand.py:40`) — зафиксировано change `m2-demand` (его design, решение 3 и вопрос 2). Движок не дублирует календарную логику и не подставляет 1.0/1.3 сам. `price_mult_by_zone` собирается по зонам в порядке возрастания id из источника тарифа (решение 4 ниже). Время поездок и подачи — `ceil(path_min × travel_k)`, минимум 1 (§10.5), `travel_k = weather.travel_mult` при дожде в момент назначения (`env.is_rain(t)`), иначе 1.0.

### 3. Агрегация: AggregateBuffer — окно закрывается после последней минуты интервала

Движок держит `AggregateBuffer(zone_count)` и на каждую минуту после шага 1 вызывает `set_env(zone, is_rain, event, minute_price)` для каждой зоны: `is_rain = env.is_rain(t)`, `event = env.event_label(zone, t)`, `minute_price` — источник тарифа (решение 4). Счётчики: `add_request(origin)` — на каждый спавн; `add_assignment(origin, wait_min)` — на каждое назначение, `wait_min = номер минуты t − created_at` (назначение той же минутой даёт 0); `add_completion(dest)` — на каждую высадку (`dropoff_at` внутри интервала); `add_expiry(origin)` — на каждое истечение. `snapshot_drivers(fleet.free_by_zone(), fleet.busy_by_zone())` — ровно один раз на окно, в момент закрытия: **после** шага 5 последней минуты интервала = «снапшот на конец интервала» (§10.2). `flush(ts)` закрывается на минутах `k`, где `(k+1) % agg_step_min == 0` (после 5-й обработанной минуты), `ts = bucket5(t)` — переиспользование M1 (§2.2 п. 4); первый `ts` = `sim_start`; 30 дней → 8 640 уникальных `ts`, `51 840` строк (A5). Семантика полей flush — дословно §3.8: `avg_wait_min = None` при пустом списке назначений интервала; `supply_demand_ratio = free / max(requests, 1)`; `is_rain = 1`, если дождь в любой минуте интервала; `event` — первая непустая метка минут интервала (эквивалент приоритета `friday_evening` > `surge_injection` > `''`, т.к. `env.event_label` возвращает метку с этим приоритетом на минуту); `price_multiplier` — сумма поминутных значений, делённая на `agg_step_min` (5). Строки — дикты по зонам в порядке возрастания id, готовые под `storage.repo.insert_zone_metrics`. Правило дефицита — приватная функция в `aggregate.py` (`free/max(requests,1) < 0.5 or unfulfilled > 0`): единый источник для `Summary.deficit_share` и заготовки `calibrate.py`; колонкой не хранится (§3.8). Альтернатива «снапшот в середине интервала / среднее за интервал» отвергнута — противоречит §10.2.

### 4. Шов price_fn §10.13: подменяется только числовой множитель

Единая точка: `mult(zone_id, t) = price_fn(zone_id, t)`, если задан, иначе `env.price_multiplier(zone_id, t)` — используется в трёх местах: `price_mult_by_zone` для `spawn_requests` (эластичность внутри λ), `price_multiplier` заказа (множитель зоны происхождения на момент создания, §3.4), `minute_price` агрегата. При этом `env.advance_day` вызывается безусловно — розыгрыши инъекций и дождя продолжаются, поток rng не сдвигается (`price_fn` — чистая функция без rng); метки `event` и `is_rain` агрегата продолжают отражать состояние среды. Следствие: A/B-ветки на одном seed сравнимы попарно (различаются только тариф и его следствия — эластичность и множители в данных). Альтернатива «price_fn выключает инъекции» отвергнута — прямо запрещена §10.13.

### 5. Движок и writer: терминальные записи trips, дренаж хвоста, батчи раз в сим-час

Движок не знает про SQLite (§10.12): `TripWriter` — Protocol с `write_trips(rows)` / `write_metrics(rows)` (дикты под `storage.repo`). Активные заказы — во внутренней структуре движка (по внутреннему id: `TripRequest` + состояние + `assigned_at`/`pickup_at`/`driver_id`). Строка trips формируется один раз, в терминальном состоянии, и немедленно попадает в батч: высадка (шаг 4) → `completed` с полным набором времён; истечение (шаг 5, приватный предикат `demand._is_expired`, `assigned=False`) → `unfulfilled` с `assigned_at = pickup_at = dropoff_at = None`. Поля дикта — по контракту данных: `created_at, origin_zone, dest_zone, assigned_at, pickup_at, dropoff_at, status, price_multiplier`; времена — ISO-строки через `to_iso` (контракт M1: «YYYY-MM-DD HH:MM:SS»); порядок строк — порядок создания заказов (решение §10.11: `trip_id` назначает SQLite при батч-вставке в порядке создания — генерация требует пустой `trips`, guard §4). **Дренаж хвоста** (proposal, вопрос 1): после последней минуты основной фазы движок продолжает шаги 4–5 (движение, истечения) без спавна, диспатча и агрегации, пока все заказы «в полёте» и «ожидающие» не достигнут терминального состояния; в writer уходят только терминальные строки, `created_at` всех строк остаётся в окне [2026-11-02, 2026-12-02) (A6), окна метрик не выходят за основную фазу (A5: ровно `дней × 288 × 6` строк). Хвост ограничен: `wait_limit_min` (6) + максимум подачи/поездки (`path_min ≤ 21` × `travel_mult` 1.4 ≈ 30 мин) — меньше сим-часа. Батчи: накопленные строки обеих таблиц сбрасываются writer'у раз в сим-час (§5) — на границе часа после шага 6: `write_trips(…)` и `write_metrics(…)` одним списком каждый; затем `progress(t, trips_so_far, elapsed_sec)` — `trips_so_far` = строк trips, переданных writer'у (proposal, вопрос 3). Sqlite-writer — в `__main__.py`: `storage.db.connect` + `storage.db.transaction` + `storage.repo.insert_trips`/`insert_zone_metrics`, без логики мира.

### 6. CLI §4: guard, прогресс, сводка, CSV

argparse: `--days` (int, обязателен), `--config` (default `config.yaml`), `--seed`/`--db` (default None → `cfg.seed` / `cfg.storage.db_path`), `--csv` (default None). **Guard до прогона**: `connect(db)`, `select count(*) from trips` > 0 → сообщение «генерация требует пустой таблицы trips — укажите новый --db» в stderr и exit 2 (A8: grep по «trips»); новой БД guard не мешает — `connect` создаёт схему M1. Прогресс: callback движка печатает в stderr `f"[{to_iso(t)[:16]}] trips={n} elapsed={sec:.1f}s"` — машинный формат §4 (30 дней → 720 строк ≥ 24, A4). Сводка — ровно 4 строки `print` в stdout, формат дословно §4: `sim: days={days} seed={seed} db={db}` (`db` — как передано: флаг или конфиг); `trips: total=… completed=… completed_share={:.1f}% unfulfilled=… unfulfilled_share={:.1f}%`; `wait: avg_wait_min={:.2f} deficit_share={:.1f}%` (`avg_wait_min` — глобально по назначенным заказам прогона, proposal, вопрос 2; `deficit_share` — доля дефицитных 5-минуток по правилу §3.8 в процентах); `wall: {:.1f}s` (числовые форматы — как в примере §4; regex скрипта допускает любые `[0-9.]+`). CSV: `os.makedirs(dir, exist_ok=True)` + `storage.csv_export.export_table(conn, "trips", dir/"trips.csv")` и `…"zone_metrics_5min"…` (A9: строки = таблица + заголовок). `Summary.wall_sec` и exit code 0.

### 7. Заготовка calibrate: прогон + строка deficit_share

`python -m simulator.calibrate --days 30 [--seed S]` (дефолты: 30 дней, seed из конфига): создаёт `Engine`, прогоняет мир с внутренним in-memory writer'ом (копит только строки метрик), считает `deficit_share` той же приватной функцией `aggregate.py` и печатает одну машинную строку `deficit_share=<X>%` (§9; её проверяет A13 — после `m2-calibration`). matplotlib/pandas не подключаются (заготовке не нужны; разрешены только в этом файле, §2.2 п. 2 — придут с `m2-calibration`). Никакого подгона чисел: заготовка честно печатает долю дефицитных 5-минуток текущего мира.

### 8. Скрипт приёмки и Makefile: дословность приложения В

`scripts/accept_m2.sh` — побайтовый текст приложения В (shebang, комментарии, порядок A1–A13, `exit "$fails"`); правка допустима только вместе с правкой плана (§11.1). Скрипт сам чистит свои артефакты, требует только `.venv`, `sqlite3`, `shasum`; полный прогон ~2–4 минуты. Makefile: две новые цели и расширение `.PHONY`: `sim:` → `.venv/bin/python -m simulator --days 30 --seed 42` (§4 дословно: БД по умолчанию из конфига); `accept-m2:` → `bash scripts/accept_m2.sh` (приложение В). Существующие цели (`install/test/lint/fmt`) и шапка не меняются. Гейт после change'а: `make accept-m2` → PASS A1–A12, единственный FAIL — A13, exit 1 (§7: провалены могут быть только критерии будущих changes).

### 9. Тесты: три файла §8, границы допусков

Конфиги тестов — эталонный `load_config("config.yaml")`, дефолты `AppConfig()` и синтетические `AppConfig.model_validate({...})` (управляемый мир: профили, парк, множители; магические числа тестов — параметры конфигов, не кода).

- `tests/test_sim_loop.py` — **`test_aggregation_math`**: микросценарий на синтетическом мире (нулевой/управляемый парк, форсированная среда), движок прогоняет несколько минут, все 11 колонок строк `zone_metrics_5min` по каждой зоне сверены с рукописными ожиданиями (спека: «Микросценарий сверяет все 11 колонок»); плюс точные равенства порядка шагов §3.7: заказ, созданный в минуту t, назначается в ту же минуту при свободном водителе (wait 0); истечение ровно в `created_at + wait_limit_min`; назначение спасает (§10.3); `avg_wait_min = NULL` в окне без назначений; поминутное среднее `price_multiplier` при форс-инъекции; `is_rain` при дожде в одной минуте окна.
- `tests/test_sim_repro.py` — **`test_reproducibility`**: два независимых полных прогона движка по 7 дней, seed 42 (полная неделя от понедельника `sim_start`: будни/выходные, «пятничный вечер» пт+сб, дожди и инъекции; «полный» = весь цикл с дренажем хвоста, обе таблицы — proposal, вопрос 4), файловые БД в `tmp_path`, попарное сравнение всех строк `trips` (по вставке) и `zone_metrics_5min` (по `(ts, zone_id)`); соседний тест: seed 43 даёт отличный префикс `trips`.
- `tests/test_sim_cli.py` — **CLI smoke 1 день**: subprocess `.venv/bin/python -m simulator --days 1 --seed 42 --db tmp/a.db --csv tmp/csv` → exit 0; в обеих таблицах N > 0 строк (для 1 дня точно `288 × 6 = 1728` строк метрик и 288 уникальных `ts`); лимит времени — производная граница бюджета §5 с запасом (≤ 10 с на 1 день; жёсткое число план не фиксирует); guard: повторный запуск в ту же БД → exit 2, вывод содержит «trips»; CSV: строка в каждом файле = строк таблицы + 1; сводка: ровно 4 строки по regex §4; прогресс: ≥ 1 строка машинного формата в stderr.

Бюджет `make test` после change'а: два 7-дневных прогона (~2×14 с) + CLI smoke (~2–3 с) — в пределах обычного набора.

## Risks / Trade-offs

- [Производительность цикла: ~43 200 минут × 6 зон λ-вызовов и диспатч на питон-уровне] → бюджет 60 с (§5) замеряется на 30 днях (гейт A4); резерв §5 — векторизация пуассонов всех зон одним вызовом numpy «не меняя порядок разыгрываний»; векторизация меняет поток rng относительно последовательной версии, поэтому допустима только внутри этого change'а до фиксации `test_reproducibility`/A7 (после — только через правку артефактов).
- [Сцепка с решениями `m2-demand`: движок обязан передавать `event_mult` значением из конфига, а условие пятницы проверять в demand] → зафиксировано решением 2; нарушение даст двойное применение множителя — ловится `test_aggregation_math` и тестом горба `m2-env`.
- [Дренаж хвоста (решение 5) — поведение, не выведенное напрямую из плана] → proposal, вопрос 1; без него A5 («других статусов нет») и A6 (`completed` требует все времена) невыполнимы, т.к. вставка без UPDATE (§10.11). Если заказчик ответит иначе — правка через `openspec-update-change`.
- [Юнит-тест `test_reproducibility` на 7 днях не заменяет 30-дневный A7] → 30-дневный детерминизм закреплён скриптом приёмки (два прогона seed 42 в A7); юнит-тест — быстрый регресс на механику, гейт сдачи — `make accept-m2`.
- [Скрипт приёмки требует `sqlite3` и `shasum` в PATH] → заявлено приложением В («самодостаточен»); на машине разработки macOS оба присутствуют; отсутствие — среда заказчика, не правка скрипта.
- [Время полной приёмки ~2–4 минуты] → заявлено приложением В; в `make test` скрипт не входит, вызывается гейтом сдачи.

## Migration Plan

Только новые файлы (`simulator/aggregate.py`, `engine.py`, `__main__.py`, `calibrate.py`, `scripts/accept_m2.sh`, три теста) и добавление двух целей в `Makefile` — существующие импорты, тесты и цели не ломаются; `simulator/__init__.py` остаётся пустым (реэкспорт `Engine` — необязательная альтернатива приложения Б, не требуемая A12). Откат — удаление новых файлов и целей. Схема SQLite не меняется (§2.2 п. 5); `forecasts` остаётся пустой (M3).
