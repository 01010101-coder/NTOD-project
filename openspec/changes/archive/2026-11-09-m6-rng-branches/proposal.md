# Proposal: m6-rng-branches

## Why

Вехе M5+M6 «Лаборатория политик» (план `docs/plan-m5-m6-policy.md`, change 1 из §7)
нужны ветки будущего A/B/C/D на одном seed, где политики меняют цену. Сейчас весь
мир пьёт из одного `numpy.random.Generator` (§10.9 M2): политика меняет цену →
λ → значения пуассоновских розыгрышей → число вызовов выбора назначения → общий
поток сдвигается → **погода и инъекции разъезжаются между ветками после первой
смены цены**, и парное A/B замутняется (мина зафиксирована в §3 плана M5+M6 и
§11 плана M3). Без разделения потоков сравнение веток нечестно, без веточного
генератора их нечем записывать.

## What Changes

- **Разделение rng-потоков в `Engine`**: вместо одного `default_rng(seed)` — два
  дочерних генератора, высаженных из `np.random.SeedSequence(seed).spawn(2)` в
  фиксированном порядке: эндогенный (пуассоновский спавн, выбор назначения —
  потребляется `simulator.demand`) и экзогенный (`WorldEnv`: дождь, surge-инъекции).
  Сигнатура `Engine` не меняется.
- **Принимаемое следствие (явно)**: последовательности розыгрышей иные, мир после
  разделения ≠ `taxi.db`/`m3_epoch.db` побитово. Эталонные БД M2/M3 не
  перегенерируются и не трогаются; контроль — прогон `simulator.calibrate`,
  коридор дефицита [10, 20] % (§3 плана M5+M6).
- **Скелет веточного генератора**: новый модуль `simulator/branches.py` — реестр
  веток (дизайн под N веток) + `generate_branch(...)` + CLI
  `python -m simulator.branches --branch a-base`; ветка `a-base` — мир без
  политики (price_fn нет), 37 дней, seed 42 → `data/worlds/a-base.db`.
- **Вынос sqlite-инфраструктуры прогона** в общий модуль `simulator/writers.py`
  (`SqliteTripWriter`, печать прогресса/сводки) — переиспользуют оба CLI
  (`simulator` и `simulator.branches`) без копирования формата §4 M2.
- **Тесты**: независимость экзогенного потока (агрессивный `price_fn` давит спрос,
  но эпизоды дождя/инъекций побайтово те же — до изменения этот тест красный),
  побитовая повторяемость ветки, guard непустой БД, дефолты CLI.

Не входит (последующие changes вехи): ступенчатая и реактивная политики и
`policy:`-секция конфига (`m6-policy`); ветки B/C/D, δ-калибровка, тень-прогнозы,
реестр миров в приложении (`m6-worlds`); UI (`m6-worlds-ui`, `m6-compare-tab`).

## Capabilities

### New Capabilities

- `simulator-branches`: генерация веток будущего — реестр веток, функция
  `generate_branch`, CLI `python -m simulator.branches`, конвенция
  `data/worlds/<ветка>.db`, детерминизм и guard.

### Modified Capabilities

- `simulator-loop`: требование «Минутный цикл в фиксированном порядке» — вся
  случайность теперь через ДВА дочерних генератора из `SeedSequence(seed).spawn(2)`
  (было: один `Generator`, создаваемый `Engine`); требование «Шов price_fn для
  A/B-экспериментов (§10.13)» — формулировка гарантии меняется с «общий поток не
  сдвинут» на «экзогенные розыгрыши в отдельном потоке и совпадают между ветками
  побайтово; эндогенная история заказов закономерно расходится при изменившемся
  тарифе».

## Impact

- Затронутые модули: `simulator/engine.py` (инициализация rng, ~10 строк),
  `simulator/__main__.py` (импорт из `writers.py`), новые `simulator/writers.py`,
  `simulator/branches.py`, новые тесты `tests/test_sim_branches.py`.
- Спецификации: дельты `specs/simulator-loop/spec.md` (MODIFIED ×2) и
  `specs/simulator-branches/spec.md` (ADDED); `simulator-env` не меняется
  (контракт `WorldEnv(cfg, rng)` прежний — двигается только то, какой генератор
  передаёт `Engine`).
- Совместимость: CLI `python -m simulator` и `simulator.calibrate` без изменений
  поведения; существующие тесты детерминизма (`test_sim_repro`) остаются зелёными
  (сравнивают прогоны одного кода). **Побитовая связь новых прогонов со старыми
  эталонными БД разрывается** — это осознанное решение вехи, задокументировано в
  плане и приёмке.
- Приёмка: `make lint && make test`; генерация `a-base` 37 дней ≈ 25–50 с;
  `deficit_share` прогона и `python -m simulator.calibrate --days 30` в коридоре
  [10, 20] %.
