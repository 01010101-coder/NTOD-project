## Context

Change `m3-dataset` закрыт и даёт готовый фундамент: протокол `RowSource`
(`metrics_at(zone_id, ts) -> MetricPoint(requests, free_drivers, unfulfilled)`,
`time_range()`), правило дефицита `deficit_label(requests, free_drivers,
unfulfilled)`, бакет-арифметику `bucket_index`/`from_bucket_index` и роли дней
`day_role` (`ml/dataset.py`). Запись прогнозов существует с M1:
`storage.repo.insert_forecasts` / `list_forecasts`. Этот change добавляет
поверх них два наива и все метрики сравнения (план M3 §6, §8 change 2).
Хронология вехи: наивы и метрики появляются ДО сетей (`m3-model`), чтобы
сравнение с первого дня шло через один и тот же расчёт метрик.

## Goals / Non-Goals

**Goals:**

- Наивы как чистые функции поверх `RowSource` — без обучения, без CLI, без
  своего walk-forward по эпохе (прогон и сводная 4 строк — `m3-inference`).
- Один расчёт метрик для любых `model_version` — наивов сейчас, MLP/LSTM в
  `m3-inference`/`m3-train-cli`.
- Полная детерминированность и отсутствие NaN на вырожденных данных.

**Non-Goals:**

- CLI и прогон по реальной эпохе `data/m3_epoch.db` (веха оставляет БД эпохи
  нетронутой до `m3-inference`).
- Калибровочные процедуры (Platt, isotonic) — только таблица наблюдаемой
  калибровки (§10.7 плана M3: отдельная процедура не входит).
- Веса/вероятности вместо жёстких 0/1 у наивов: бинаризация — сознательная
  простота бейзлайна.

## Decisions

1. **Наивы поверх `RowSource`, не поверх SQLite-запросов.** Оба наива —
   функции `(source, ts, zone_id) -> список строк forecasts`, читающие
   `metrics_at`. Альтернатива — прямые SQL-запросы к `zone_metrics_5min` —
   отклонена: дублирует доступ к данным мимо единого шва, а тестам пришлось бы
   собирать настоящие БД вместо фейкового источника в памяти.
   - «как сейчас»: `metrics_at(ts)`; обе строки горизонтов — одни и те же
     значения; `deficit_prob = float(deficit_label(бакет ts))`.
   - «сутки назад»: `metrics_at(ts − 24 ч)`; та же схема. Отсутствие
     исходного бакета → пустой список (молчаливый пропуск пары, спека
     «Вчерашнего слота нет»).
2. **Строки forecasts — словари полей контракта.** Наив возвращает
   `list[dict]` с ключами вставки `insert_forecasts` (ts — момент прогноза,
   не целевой бакет; цель = ts + horizon_min). Это фиксирует общий формат
   «источник строк для walk-forward», который `m3-inference` переиспользует
   для сетей.
3. **Вход метрик — пары, не SQL.** `ml/metrics.py` принимает результаты
   `list_forecasts` (или те же dict-строки наивов) плюс `RowSource` для
   факта; соединение — по (ts, zone_id, horizon_min): факт целевого бакета
   `metrics_at(ts + H)`, метка дефицита — `deficit_label`. Так метрики
   работают и на мини-БД в тестах, и на реальной эпохе без изменений.
   Строка без пары к факту исключается из всех метрик (спека).
4. **Вырожденные случаи дают 0.0.** precision/recall/F1 при отсутствии
   истинных или предсказанных позитивов — 0.0 (не None/NaN/ZeroDivision);
   обоснование: сводная таблица должна печататься всегда, а «0.0 у
   модели, не поймавшей ни одного дефицита» — честная нижняя граница.
5. **Сводная структура — вложенный dict, рендер отдельной функцией.**
   `build_summary(...) -> dict` (структура: model_version → таргет × горизонт
   → метрика; + калибровка по горизонтам) и `render_table(list[dict]) -> str`
   (7 колонок §6 плана). JSON-совместимость структуры — требование будущего
   `artifacts/summary-<дата>.json` (m3-inference), поэтому никаких
   numpy-скаляров внутри (приведение к float/int на выходе).
6. **Калибровка: 10 бинов [0.0,0.1)…[0.9,1.0], верхний бин включает 1.0.**
   Наивы попадают только в бины 0/1 — таблица остаётся осмысленной для сетей.
   Пустые бины опускаются.
7. **Никаких новых зависимостей и файлов кроме `ml/baselines.py`,
   `ml/metrics.py`, `tests/test_ml_baselines.py`.** numpy для средних;
   pandas для расчётов не нужен (объёмы тестов малы, а единообразие с
   `ml/dataset.py` — чистый numpy).

## Risks / Trade-offs

- [Сезонный наив силён на суточной периодике — сети обязаны его побеждать
  честно] → это ожидание вехи, а не риск реализации: DoD плана M3 прямо
  требует «MLP и LSTM не хуже сезонного наива, иначе дообсуждение».
- [Дыры в истории (пропущенные бакеты) тихо сужают выборку метрик] →
  поведение зафиксировано спекой (пропуск пары); `m3-inference` добавит
  контроль ожидаемого числа строк (24 120/модель), дыр в реальной эпохе нет.
- [Расхождение факта между `metrics_at` и SQL-агрегатами] → исключено
  конструктивно: факт читается тем же `RowSource`, что и обучение.

## Migration Plan

Добавляющие изменения: новых таблиц/конфиг-секций нет, БД эпохи не трогается.
Откат — удаление двух модулей и теста.
