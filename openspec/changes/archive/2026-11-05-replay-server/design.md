## Context

Шов `simulator-live` (`live-engine`) отдаёт записи `MinuteRecord` колбэком `on_minute`; движок детерминирован (один seed → побайтово те же таблицы, `simulator-loop`), поэтому повторный прогон — воспроизведение. Архитектура «живого города» зафиксирована на exploring-фазе: log-first — сервер один раз тихо прогоняет мир и дальше работает только с логом; движок в воспроизведении не участвует. Стек решён plan-m1: FastAPI + WebSocket + статика без сборки; строка про Streamlit в `openspec/config.yaml` обещана к актуализации «в вехе сервера» — это этот change. Потребитель протокола — `city-canvas` (следующий change): карта по `/api/city`, анимация «чистой функцией сим-времени» по `records`/`snapshot`, слайдер и графики с кликом-переходом.

## Goals / Non-Goals

**Goals:**

- Seek в обе стороны за константное время (чтение лога по индексу) — драг слайдера не гоняет движок.
- Прогрессивная готовность: страница работает через секунды после старта сервера, лог дозаполняется в фоне.
- Самодостаточность: серверу не нужна сгенерированная БД — всё строит собственный прогон по seed конфига.
- Протокол достаточен для клиента без знания механики: снимок активных поездок при connect/seek, дальше — поток записей.

**Non-Goals:**

- Отрисовка: карта, слайдер, графики — `city-canvas`; здесь только страница-заглушка для приёмки сервера.
- Персистентность лога: лог живёт в памяти процесса; сохранение/загрузка записей — не нужно (детерминизм делает прогон дешёвым воспроизведением).
- Ветки `price_fn` и A/B-режим M6 — тот же интерфейс позже, отдельным change'ом.
- Авторизация, многопользовательский режим — учебный локальный инструмент.

## Decisions

1. **Log-first: один тихий прогон → append-only лог, а не step-live движка.** Seek назад при живом движке — рестарт с догоном (десятки секунд на 30 днях) — неприемлем для драга слайдера. Лог даёт случайный доступ по индексу в обе стороны; стоимость — память (см. решение 8) и фоновый прогон при старте. Записи иммутабельны (frozen `MinuteRecord` из `live-engine`), лог — только аппендится: это делает одновременное чтение безопасным почти без блокировок.

2. **Прогон в фоновом потоке при старте, обслуживание начинается немедленно.** Первые записи появляются практически сразу (движок производит минуты быстрее реального времени), 30 дней закрываются за десятки секунд (бюджет A4). Граница заполненности — монотонно растущий счётчик `filled`; читатели (REST/WS) видят только `[0, filled)`. Playhead на краю ждёт пополнения — «live-край», как прямой эфир, догоняющий запись. Альтернатива — дождаться полного прогона до старта HTTP (простая, но пустые десятки секунд) отклонена: прогресс виден и полезен.

3. **Метрики — из того же прогона in-memory, а не из SQLite.** Движок пишет `zone_metrics_5min` через writer'а; в фоновом прогоне writer — словарь-сборщик в памяти. Один источник истины на сеанс, нулевая сцепка с БД (нет требований к `data/taxi.db`, seed-совпадению, guard'ам). По контракту детерминизма строки байт-в-байт равны таблицам CLI-прогона — это тест. Цена: графики прогрессивно заполняются вместе с логом — совпадает с UX слайдера, ценой не считается.

4. **Снимок при connect/seek — восстановление активных поездок из лога.** Активные на конец минуты t = назначения в записях ≤ t, для которых нет высадки с тем же `internal_id` в записях ≤ t (истечение назначенных невозможно — механика M2). Снимок несёт поля назначения (`driver_zone`, `origin`, `dest`, `pickup_at`, `dropoff_at`) плюс среду записи t (`is_rain`, `price_mult`, `free_by_zone`) — клиент после снимка анимируется потоком без перестроения мира. Индексация для восстановления: словарь `internal_id → (индекс назначения, индекс высадки)` строится на лету при чтении; полного прогона на снимок не требуется.

5. **Маршруты — next-hop Флойд на сервере, отдельным модулем.** `path_min` движка даёт только длины; для анимации по рёбрам нужен путь как последовательность зон. Z = 6 — next-hop матрица строится из конфига дорог тривиально и независимо от движка (проверка: свёртка маршрута в сумму рёбер == `build_city().path_min`). Клиент получает готовую матрицу `routes` в `/api/city` и сам раскладывает фазы `driver_zone → origin` и `origin → dest` по точкам зон.

6. **Транспорт: один FastAPI-процесс, WS-сессии делят один лог и один playhead.** Лог и playhead — глобальное состояние процесса: все вкладки смотрят один мир и одну позицию (демо-режим проекта); независимые playhead на вкладку — бессмысленны при общем детерминированном мире и лишь усложнили бы протокол. Продвижение playhead — серверный тик ~10 Гц: `playhead += speed × dt`, пересечённые записи уходят пачкой; клиент ведёт непрерывную интерполяцию сам (позиция — функция сим-времени). Скорость в сим-минутах/сек, зажим [0.25, 600]: низ — разглядывать диспатч, верх — быстрый проход дня (~2.4 мин/сутки).

7. **Протокол — JSON-текст, время ISO-минутами.** Команды `play`/`pause`/`speed`/`seek`, сообщения `state`/`snapshot`/`records`/`log-extended`. Время — строки «YYYY-MM-DD HH:MM:SS» (контракт времени проекта), никаких эпох-миллисекунд. Сериализация `MinuteRecord` — прямая (dataclass → dict, кортежи → массивы); отдельная версионная схема протокола не вводится — потребитель один, эволюция — следующим change'ом вместе с `city-canvas`.

8. **Структура пакета и память.** `app/replay.py` — лог, фоновый прогон, восстановление снимка; `app/paths.py` — next-hop; `app/server.py` — FastAPI (REST, WS, статика); `app/__main__.py` — CLI и запуск uvicorn; `app/static/` — заглушка. Память лога 30 дней: ~820 тыс. событий минуты + 51 840 строк метрик — порядок десятков МБ, приемлемо для лабораторного инструмента; компактная колоночная схема не вводится, пока не понадобится (YAGNI, фиксируется риском).

9. **Зависимости и конфиг.** `fastapi` + `uvicorn[standard]` (тянет websockets) — в `[project.dependencies]`, пакет `app` — в setuptools-список; тесты через `fastapi.testclient` (starlette) без реального сокета. Секция `app` конфига (`host`, `port`, `days`) — с дефолтами в `common/config.py` (соглашение «старые конфиги грузятся»), в `config.yaml` — явно. Актуализация `openspec/config.yaml` (Streamlit → FastAPI/WebSocket/canvas) выполняется здесь — обещание plan-m1.

## Risks / Trade-offs

- [Потокобезопасность лога при фоновом прогоне] → записи иммутабельны, лог append-only (list.append атомарен при GIL), `filled` — int с монотонным обновлением после аппенда; читатели берут срез `[start:filled]` и не видят недописанное; при необходимости — одна блокировка на метаданные, без копирования записей.
- [WS-пачки при 600× обходят медленный клиент] → пачки ограничиваются по числу записей (например, 200/пачка) и отправляются по готовности сокета; при устойчивом отставании клиент сам делает `seek` к playhead — протокол это разрешает.
- [Память лога на 30 дней недооценена] → оценка десятков МБ консервативна (посчитана по 820 тыс. событий); при превышении — переход на numpy-колонки без смены интерфейса лога (точка инкапсуляции — `app/replay.py`).
- [Прогон и uvicorn конкурируют за CPU] → прогон однопоточный в фоне; на 8+ ядрах влияние на отклик минимально; при необходимости — `nice`-приоритет потока, интерфейс не меняется.
- [Расхождение лога и taxi.db при правке конфига между генерациями] → это свойство детерминизма, а не баг: мир определяется конфигом+seed; сервер не претендует на соответствие чужой БД, а воспроизводит мир своей конфигурации (графики и карта всегда согласованы с логом).
