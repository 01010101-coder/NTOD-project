Ключи среды уже есть в моделях конфига: `WeatherCfg`, `FridayEveningCfg`, `SurgeInjectionCfg`, `EngineCfg.sim_start` (`common/config.py:228-274`) — править `common/config.py` не нужно. Источник содержания — `docs/plan-m2-engine.md`; этот change — строка №4 таблицы §7 (параллельная ветка после `m2-city`, вместе с `m2-demand` и `m2-drivers` до `m2-loop`). ## Goals / Non-Goals

**Goals:**

- `simulator/env.py`: `WorldEnv` по приложению Б — дождь (Bernoulli/день, эпизод U(6:00–22:00) × U(1–3) ч), «пятничный вечер» по календарю (дни/часы/архетипы из конфига), случайные surge-инъекции (Bernoulli/день → зона, старт U(сутки), 30–60 мин, множитель 1.2–1.6), `price_multiplier(zone, t)` = 1.0 вне инъекций.
- Нескачущий rng-поток: все розыгрыши — безусловно в `advance_day`, запросы — чистые чтения (§10.13); один генератор, переданный снаружи (§3.7).
- `tests/test_sim_env.py` закрывает проверки строки №4 §7 на уровне API `WorldEnv`: форс-дождь (шанс 1.0), форс-инъекция (шанс 1.0), пятница в заданных архетипах, детерминизм по seed и чистота запросов.
- Гейт change'а: `make lint && make test` зелёные (правило `openspec/config.yaml`).

**Non-Goals:**

- Применение множителей среды к λ (формула §3.3 с множителями «(дождь? × rain.demand_mult) × (пятничный вечер для архетипа? × events.friday_evening.demand_mult)» и эластичностью) — change `m2-demand`; умножение времени поездок на `k_дождь` (`ceil(path_min × k_дождь)`, §3.2) — change `m2-drivers`; вызов `advance_day` в шаге 1 цикла, колонки агрегата `is_rain`/`event`/`price_multiplier` и шов `price_fn` в `Engine` — change `m2-loop` (§3.7, §3.8, §10.12, §10.13).
- Агрегатная проверка «`price_multiplier` в агрегате > 1 в заданном окне» (строка №4 §7) — завершается в тестах `m2-loop`, когда существует `AggregateBuffer`; здесь — проверка на API `WorldEnv` (Open Question 1 proposal.md).
- Правки `common/config.py`, `config.yaml`, `common/` и `storage/` (запрет §2.2 п. 5), новых модулей и подпакетов (запрет §2.2 п. 1), новых зависимостей (запрет §2.2 п. 2).

## Decisions

### 1. Публичный API `env.py` — приложение Б плана M2 дословно

```python
# env.py
class WorldEnv:
    def __init__(self, cfg: AppConfig, rng: np.random.Generator) -> None: ...
    def advance_day(self, day_index: int) -> None: ...          # розыгрыши дождя/инъекции на сутки (00:00)
    def is_rain(self, t: datetime) -> bool: ...
    def event_label(self, zone: ZoneInfo, t: datetime) -> str: ...   # 'friday_evening' | 'surge_injection' | ''
    def price_multiplier(self, zone_id: int, t: datetime) -> float: ...
```

Сигнатуры не меняются; `datetime` — из `common.timeutil` (наивный, секунды 00), `AppConfig` — из `common.config`, `ZoneInfo` — из `simulator.city`. Приватные функции и поля — на усмотрение исполнителя (приложение Б). Никаких базовых классов и фабрик (запрет §2.2 п. 1); импорт `from simulator.env import WorldEnv` — проверка A12 приложения В на конце вехи.

### 2. Модель среды — §3.6 плана M2 дословно

- **Дождь**: «раз в день Bernoulli `weather.rain_day_chance` (эталон 0.15). Эпизод: старт U(6:00–22:00), длительность U(1–3) ч. Во время эпизода: спрос × `rain.demand_mult` (1.4), время поездок × `rain.travel_mult` (1.4)».
- **«Пятничный вечер»**: «календарно, дни из конфига (пт, сб), часы 17–23 включительно, для архетипов business/mixed — спрос × 1.3».
- **Тариф**: «всюду 1.0, кроме **обучающих инъекций**: раз в день Bernoulli `surge_injection.day_chance` (0.10) → случайная зона, старт U(сутки), длительность U(30–60) мин, множитель U(1.2–1.6). Это единственный источник вариации `price_multiplier` в эпоху генерации — нужен, чтобы признак не был константой для ML (M3)».

Состояние среды — розыгранные на текущие сутки эпизоды дождя и инъекции (абсолютные интервалы сим-времени); календарная «пятница» не розыгрывается, а вычисляется из метки времени запроса. Дождь и «пятница» на `price_multiplier` не влияют (§3.6: тариф «всюду 1.0, кроме обучающих инъекций»).

### 3. Решение §10.13 — нескачущий rng-поток (дословно)

«Шов ценовой политики для M6: `Engine(cfg, price_fn=None)`. При `price_fn=None` тариф даёт `WorldEnv` (инъекции §3.6). Если `price_fn` задан — он подменяет тариф зон, но **розыгрыши инъекций всё равно происходят**: поток rng не сдвигается, ветки A/B на одном seed сравнимы попарно».

Следствия для `env.py` в этом change'е: (а) `WorldEnv` вообще не знает о `price_fn` — все розыгрыши происходят в `advance_day` безусловно, до и независимо от решений потребителя; (б) запросы `is_rain`/`event_label`/`price_multiplier` — чистые чтения состояния, rng не тратят; (в) подмену тарифа выполняет `Engine` в change `m2-loop`, вызывая либо `env.price_multiplier(...)`, либо `price_fn` — поток rng в обоих случаях одинаков. Альтернатива «ленивый розыгрыш в момент первого запроса» отвергнута: она сдвигала бы поток в зависимости от того, спрашивал ли потребитель тариф (ломает §10.13 и парные A/B M6).

### 4. Остальные применимые решения §10 плана M2 (дословно, в части этого change'а)

- **§10.1.** «Порядок шагов цикла и правила тай-брейков — часть контракта детерминизма; их изменение меняет мир (другая история при том же seed)» → порядок розыгрышей внутри `advance_day` фиксирован (решение 6).
- **§10.4.** «Дождь действует одинаково на спрос (×1.4) и на время поездок (×1.4); значения калибруемы» → среда сообщает состояние `is_rain(t)`, множители `weather.demand_mult`/`weather.travel_mult` читают потребители из конфига; `WorldEnv` их не дублирует.
- **§10.9.** «Один `numpy.random.Generator`; разыгрывания всегда для всех зон (λ=0 → Poisson(0)) — устойчивость к рефакторингу» → единственный генератор передаётся конструктору; никаких собственных источников случайности.
- **§10.10.** «Сим-часы стартуют в понедельник `engine.sim_start` (эталон 2026-11-02); нумерация дней недели Mon=0; wall-clock внутри движка запрещён» → день недели — по сим-дате, `datetime.now()`/`time.*` не используются (запрет §2.2 п. 3).

### 5. Значения мира — приложение А плана M2 (секции, читаемые средой)

```yaml
weather:
  rain_day_chance: 0.15
  episode_start_h: [6, 22]      # U(6:00–22:00)
  episode_duration_h: [1, 3]
  demand_mult: 1.4
  travel_mult: 1.4

events:
  friday_evening:
    days: [4, 5]                # пт, сб (нумерация с понедельника = 0)
    hours: [17, 23]             # диапазон включительно
    archetypes: [business, mixed]
    demand_mult: 1.3

pricing:
  surge_injection:
    day_chance: 0.10
    duration_min: [30, 60]
    multiplier: [1.2, 1.6]

engine:
  sim_start: "2026-11-02"       # понедельник, старт сим-часов 00:00
```

Магических чисел в коде нет: все границы, шансы и множители — из конфига (запрет §2.2 п. 6); количество зон для розыгрыша зоны инъекции — `len(cfg.city.zones)`.

### 6. Механика розыгрышей `advance_day` (предлагаемые ответы на Open Questions 2–3 proposal.md)

Порядок розыгрышей — в порядке изложения §3.6: дождь, затем инъекция; внутри каждого — Bernoulli, затем параметры эпизода. Бернулли — `rng.random() < шанс`; целые равновероятные значения — `rng.integers(low, high + 1)` по замкнутому диапазону ключа конфига (час старта дождя 6..22, длительность дождя 1..3 ч, длительность инъекции 30..60 мин, зона инъекции 0..Z−1); старт инъекции — целая минута `rng.integers(0, 1440)` («U(сутки)»); множитель инъекции — вещественный `rng.uniform(1.2, 1.6)`. При неуспехе Bernoulli параметры эпизода не разыгрываются: «безусловно» в §10.13 означает независимость от решений потребителя тарифа, а не от исхода Bernoulli. Эпизоды хранятся как абсолютные интервалы `[старт, старт + длительность)` сим-времени: эпизод дождя, начавшийся в 22:00 с длительностью 3 ч, делает `is_rain` истинным до 01:00 следующего дня — розыгрыш следующего дня этого не меняет (вопрос 3 proposal.md). Альтернатива «обрезать эпизод полуночью» отвергнута: план не задаёт усечения, а интервалы без усечения проще и однозначнее.

### 7. Календарь: `day_index` → сим-дата и день недели (Open Question 4 proposal.md)

Дата суток = `common.timeutil.from_iso(cfg.engine.sim_start) + day_index` суток; день недели — `weekday()` этой даты (Mon=0, §3); для эталонного старта «2026-11-02» (понедельник) совпадает с `day_index % 7`. Календарная часть `event_label` вычисляется из самой метки запроса `t` (день недели и час 17–23 включительно), поэтому событие автоматически верно и для минут эпизодов, перешедших через полночь.

### 8. Метка события — правило колонки `event` из §3.8 (дословно)

«первое сработавшее: `'friday_evening'` | `'surge_injection'` | `''`» → `event_label(zone, t)` возвращает `'friday_evening'`, если событие активно для архетипа зоны в этот день/час, иначе `'surge_injection'`, если surge-инъекция активна в этой зоне (`zone.id`), иначе `''`. Тот же порядок приоритета `m2-loop` воспроизводит в агрегате (§3.8) — здесь он фиксируется в самой среде.

### 9. Потребители состояния среды — границы change'а

Среда даёт только состояние (API решения 1). Формула λ с множителями дождя и «пятницы» — §3.3, `m2-demand`; «Время поездки = `ceil(path_min[A][B] × k_дождь)`, минимум 1 минута» — §3.2, `m2-drivers`; «Заказ рождается с `created_at` и `price_multiplier` = множитель зоны происхождения на момент создания» — §3.4, `m2-demand`/`m2-loop`; шаг 1 цикла «Среда: переходы погоды, календарь, состояние тарифа» и колонки агрегата — §3.7–§3.8, `m2-loop`. Поэтому композитные проверки строки №4 §7 («спрос выше», «поездки дольше», «в агрегате») завершаются в тестах changes 2, 3, 5 (Open Question 1 proposal.md), а `tests/test_sim_env.py` проверяет среду через её публичный API — перечень в решении 10.

### 10. Верификация — `tests/test_sim_env.py` по строке №4 §7

- **Форс-дождь** (`weather.rain_day_chance = 1.0`, фиксированный seed): эпизод разыгран, `is_rain` истинен внутри окна 1–3 ч со стартом 6:00–22:00 и ложен вне; конфиг даёт потребителям `demand_mult = 1.4` / `travel_mult = 1.4` (композит — в `m2-demand`/`m2-drivers`).
- **Форс-инъекция** (`pricing.surge_injection.day_chance = 1.0`, фиксированный seed): `price_multiplier(zone, t) > 1` внутри разыгранного окна (длительность 30–60 мин, множитель в [1.2, 1.6], ровно одна зона) и `= 1.0` вне; агрегатная проверка — в `m2-loop`.
- **Пятница**: `event_label` = `'friday_evening'` в днях `[4, 5]`, часы 17–23 включительно, архетипы business/mixed; `''` вне дней/часов/архетипов; приоритет над `'surge_injection'` (§3.8).
- **Поток rng (§10.13)**: два seed-одинаковых `WorldEnv` дают одинаковые эпизоды; запросы не сдвигают поток (сценарий спеки «Запросы не сдвигают поток rng»).
- Отрицательные случаи: `rain_day_chance = 0.0` и `day_chance = 0.0` — среда тождественно без дождя и с тарифом 1.0.

Форс-режимы — правкой значения конфига в тесте (`weather.rain_day_chance = 1.0` и т. п.) на модели `AppConfig`, без новых параметров API: API приложения Б не расширяется (запрет §2.2 п. 1).

### 11. Применимые запреты §2.2 плана M2 (контроль исполнителя)

1. Не изобретать структуру: только `simulator/env.py`; никаких абстрактных базовых классов, плагинов, шин событий, «стратегий», фабрик; никаких дополнительных модулей и подпакетов.
2. Не добавлять зависимости: в движке numpy и stdlib (pandas и matplotlib — только в `calibrate.py`, здесь не нужны).
3. Никакого параллелизма и wall-clock времени: без asyncio, потоков, `datetime.now()`/`time.*` внутри симуляции; единственное время — сим-часы, передаваемые явно.
4. Переиспользовать M1 по именам, не создавая дублей: `common.config.AppConfig`/`load_config` (в тестах), `common.timeutil.from_iso`/`add_minutes`; дублей `common/`/`storage/` не создавать.
5. Конфиг-модели не правятся (уже канон §6 после `m2-city`); схема SQLite не меняется; `common/` и `storage/` не трогаются.
6. Магических чисел в коде нет: все параметры среды — из конфига (значения — решение 5).
7. Идентификаторы на английском, комментарии и docstring на русском (правило `openspec/config.yaml`); машинные метки событий `'friday_evening'`/`'surge_injection'`/`''` — оговорённый §3.8 формат.
8. Непонятность в плане — вопрос в чейндже (Open Questions proposal.md), а не молчаливое решение своим способом.

## Risks / Trade-offs

- [Целочисленные розыгрыши по замкнутому диапазону (включая границы 22:00 и 3 ч) — интерпретация «U(6:00–22:00)», не зафиксированная планом] → зафиксировано как Open Question 3 с предлагаемым ответом; детерминизм и все проверки строки №4 §7 выполняются при любом из вариантов, смена интерпретации меняет только конкретную историю при seed и требует правки только `env.py`.
- [Эпизоды, переходящие через полночь] → абсолютные интервалы без усечения (решение 6); `m2-loop` агрегирует `is_rain` по минутам интервала (§3.8: «1, если дождь был в любой момент интервала») — коллизий с агрегацией нет.
- [`tests/test_sim_env.py` находит окно инъекции по наблюдаемому состоянию] → при фиксированном seed окно детерминировано; сканирование минут (решение 10) не зависит от приватных полей и переживёт рефакторинг (приложение Б: приватные детали — на усмотрение исполнителя).
- [Параллельные ветки `m2-demand`/`m2-drivers` компилируют λ и длительности по API среды] → контракт API заморожен приложением Б (решение 1); ветка `m2-env` ничего не экспортирует сверх него.
- [Линтер/форматтер на новый файл] → файл пишется сразу с русскими docstring в стиле ruff-конфига репо; контроль — `make lint` в последней группе задач.

## Migration Plan

Изменение аддитивное: новый `simulator/env.py` и новый `tests/test_sim_env.py`; конфиг и существующие модули не меняются, миграций данных нет. Откат — git revert change'а целиком; ломающих промежуточных состояний нет (`m2-demand`/`m2-drivers`/`m2-loop` начнут падать по импорту `WorldEnv` только если начаты после отката — порядок конвейера §7 это исключает).
