## Context

Веха M3 (план `docs/plan-m3-ml.md` §3–§4) требует обучающие примеры «окно →
таргеты» из записанной истории. Сейчас есть: `data/taxi.db` (30 дней, seed 42),
детерминированный CLI `python -m simulator --days N --db PATH` (guard непустой
trips, exit 2), контракт таблиц `zone_metrics_5min`/`trips`, правило дефицита.
Пакета `ml/` и секции `ml:` нет. Мотивация — proposal.md.

## Goals / Non-Goals

**Goals:**

- одна БД эпохи 37 дней с ролями дней train/val/test (test — продолжение);
- сборка окон/признаков/таргетов, отделённая от источника строк (слой для M6);
- нормализация с fit только на train и сериализацией;
- анти-лик гарантии, проверяемые автотестами на синтетике.

**Non-Goals:**

- torch-обвязка (Dataset/DataLoader) — в `m3-model`; здесь только numpy-массивы;
- walk-forward, метрики, бейзлайны — следующие changes;
- онлайновый (движковый) источник строк — M6; здесь только SQLite-реализация;
- загрузка реальной 37-дневной эпохи в автотестах — тесты работают на
  рукописных мини-БД, реальная генерация — ручная приёмка (быстро, но ~26 с).

## Decisions

1. **Одна эпоха одним прогоном, роли — чистая функция времени.** 37 дней
   пишутся в `data/m3_epoch.db` существующим CLI; роли дней вычисляются от
   `engine.sim_start` + `ml.train_days/val_days/test_days`, без дублирования
   дат в БД. Альтернатива «отдельные train-БД и test-БД» отвергнута: удвоение
   генерации и риск рассинхрона; детерминизм A7 делает префикс одного прогона
   идентичным 30-дневному (`taxi.db`) — это и есть контроль целостности.
2. **Слоистый `RowSource`.** Сборка признаков зависит только от узкого
   интерфейса источника: окно метрик (зона, ts, число шагов) и расписание
   высадок (зона, интервал, граница назначения). Единственная реализация здесь
   — `SqliteRowSource` поверх `m3_epoch.db`. Альтернатива «SQL внутри сборки»
   отвергнута: M6 должен строить окна из живого состояния движка без
   переписывания.
3. **Загрузка истории в память один раз.** `zone_metrics_5min` эпохи (~62 тыс.
   строк) читается в pandas целиком; окна — срезы по отсортированному индексу
   (ts, zone). Для ret-признаков предвычисляется индекс высадок: по каждой
   паре (dest_zone, бакет высадки) — отсортированный массив `assigned_at`;
   `ret_H(z, ts)` = число поездок с **бакетом высадки в (бакет ts, бакет ts+H]**
   и назначением ≤ ts (bisect по массиву). Семантика бакетная, не
   хронологическая: минуты внутри бакета не различаются. Выравнивание с
   таргетом сознательное: free_drivers бакета ts+H в БД — снапшот парка на
   конец этого бакета, поэтому «кто вернётся к моменту таргета» считается по
   бакетам высадки (хронологический подсчёт по минутам дал бы
   рассинхрон ±1 бакет с тем, что предсказывает таргет). Альтернатива
   «SQL-запрос на каждое окно» отвергнута: 48 тыс. примеров × 2 признака
   давали бы ~100 тыс. запросов.
4. **Фиксированный манифест признаков.** Порядок 17 признаков на шаг —
   константа-список в модуле (имена колонок + календарные производные); окно —
   numpy (steps, 17), метка зоны отдельно. Манифест — контракт для
   m3-model/m3-inference: изменение набора = правка одного списка.
5. **Scaler'ы по признаку, а не по позиции.** StandardScaler учит статистики
   на 17 признаков (все шаги окна — одно измерение в разные моменты), не на
   72×17 позиций flatten. Таргеты: по одному scaler'у на величину (requests,
   free_drivers; оба горизонта совместно), метка дефицита не нормализуется.
   Альтернатива per-position отвергнута: взорвала бы статистику и связь с
   LSTM-вариантом, где позиций в входе нет.
6. **Сериализация pickle в `artifacts/`.** sklearn-трансформеры сериализуются
   `pickle` в `artifacts/dataset/scalers.pkl` (каталог `artifacts/` уже
   gitignored). npz только mean/std — компактнее, но теряет API transform и
   плодит свою обёртку.
7. **`MlCfg` — 12-я корневая секция** `AppConfig` (`extra="forbid"`, дефолты =
   приложение А плана M3): `db, train_days, val_days, test_days,
   window_hours, seed` + гиперпараметры обучения, которые нужны следующим
   changes, но заводятся один раз (lr, batch_size, patience, …). Прецедент
   добавления секции — `AppCfg` в replay-server.
8. **Make-цели `epoch` и `epoch-check`.** `epoch` вызывает симулятор с
   `--days $$(… train_days+test_days из config.yaml)` (подстановка через
   python -c, чтобы цель не рассинхронилась с конфигом); `epoch-check` —
   разовая ручная цель: md5 CSV-выгрузок первых 30 дней эпохи против
   `data/taxi.db` (прецедент m2_analysis). Обе цели не входят в `make test`
   (БД в CI отсутствуют).

## Risks / Trade-offs

- [37-дневный прогон зависит от неизменности эталона M2] → `epoch-check`
  сверяет префикс с `taxi.db`; при будущем изменении мира (например, rng-потоки
  M6) контроль сознательно перегенерирует эталон — это documented в плане §11.
- [ret-признак тонкий: граница «назначено ≤ ts» легко ошибится на отменённых
  поездках; бакетная семантика интервала высадок — на минутах внутри бакета] →
  в индекс высадок попадают только поездки со статусом completed (отменённые
  не высаживаются); тест на рукописной мини-БД с краевыми случаями
  (назначение ровно в ts, высадки на границах бакетов ts/ts+15/ts+30 и внутри
  бакета — ts+2 не считается, ts+17 считается).
- [время в БД — ISO-текст] → все конвертации через `common.timeutil`
  (`from_iso`/`to_iso`), сравнения — по datetime, не по строкам.
- [scaler на pandas-колонках: NaN при константах] → константных признаков в
  эпохе нет (проверено анализом m2_analysis); при std=0 StandardScaler
  отдаёт 1.0 — поведения достаточно.
- [двойное чтение эпохи тестами замедлит suite] → мини-БД в фикстурах
  создаются in-memory (sqlite `:memory:` или tmp_path), реальная эпоха тестами
  не трогается.

## Migration Plan

Изменение аддитивное: новые файлы + новая секция конфига с дефолтами (старые
конфиги грузятся). Отката не требуется; удаление = снос `ml/` и цели Makefile.
