## Context

Движок M2 закрыт и принял гейт (`simulator-loop`): `Engine.run(days, writer, *, progress=None)` монолитен — весь минутный цикл в одном методе (`simulator/engine.py:285`), `Fleet` имеет публичные агрегаты `free_by_zone`/`busy_by_zone`, но по-водительное состояние приватно; `WorldEnv` хранит интервалы дождя и surge-окон приватно. Единственный потребитель шва — будущий `replay-server`: один тихий прогон полной истории с `on_minute` строит событийный лог, дальше seek в обе стороны — чтение лога, движок в воспроизведении не участвует. Интерфейсное решение «рисуются только активные машины» (остальное — счётчики зон) уже принято на exploring-фазе и связывает `replay-server`/`city-canvas`.

## Goals / Non-Goals

**Goals:**

- Минимальный дифф в цикле движка при полном событийном покрытии мира на уровне минуты.
- События самодостаточны для клиента: анимация — чистая функция сим-времени, без знания механики `Fleet.tick` и диспатча.
- Контракт детерминизма `simulator-loop` не задет: побайтовая идентичность таблиц с наблюдателем и без, проверяется тестом.

**Non-Goals:**

- Событийный лог, его хранение и свёртка среды в окна — `replay-server`.
- Реконструкция маршрутов (next-hop Флойда) для анимации по рёбрам — `replay-server`, считается из конфига дорог без движка.
- Интерактивный step()/pause/resume API движка — не нужен при log-first архитектуре; появится, если будущей вехе понадобится живое вмешательство (тогда отдельный change).
- По-водительный публичный API парка и аксессоры эпизодов `WorldEnv` — не нужны составу событий (см. решения 2 и 4).

## Decisions

1. **Колбэк `on_minute`, а не step()-API и не генератор.** Потребитель один и его сценарий — пакетный: тихий прогон → лог. Колбэк встраивается в существующий цикл (локальные списки событий минуты + один вызов после шага 6) без перестройки потока управления; контракт детерминизма рискует меньше всего. Альтернативы — рефакторинг тела итерации в публичный `step()` с внешней петлёй либо генератор `run_steps()` — дают ту же функциональность большим диффом; генератор к тому же меняет сигнатуру прогона. Отклонены.

2. **События, а не по-водительный снапшот парка.** Активные машины (к пассажиру + в поездке) клиент восстанавливает из событий: назначение создаёт машину в `driver_zone`, высадка убирает; поэтому зона водителя в момент назначения — обязательное поле `AssignEvent` (в `trips` её нет — главный пробел, который закрывает change). Простой парк рисуется счётчиками зон — `free_by_zone` уже публичен. Расширение `Fleet` по-водительным снапшотом раздуло бы полезную нагрузку ради машин, которые не рисуются, и вскрыло бы приватный канал `_plan_trip`. Отклонено.

3. **В назначение кладутся готовые `pickup_at`/`dropoff_at`.** Движок в момент назначения уже вычисляет `pickup_min`/`trip_min` (через `travel_minutes` с rain-коэффициентом); `pickup_at = t + pickup_min − 1`, `dropoff_at = pickup_at + trip_min` — это инвариант механики `Fleet.tick` (комментарий в `engine.py`: «`dropoff − pickup == trip_min`»). Отдавая готовые моменты, движок оставляет формулу тика себе — клиент не дублирует механику и может планировать обе фазы движения сразу. Возможный рассинхрон с фактической высадкой ловится сценарием спеки (t записи dropoff == `dropoff_at` назначения).

4. **Среда — поминутными значениями, а не окнами эпизодов.** `is_rain` и вектор тарифа зон — ровно те значения, которые движок уже вычисляет каждую минуту (шаг 1а, `_tariff_mult`); при `price_fn` вектор автоматически фактический. Движок остаётся тупым источником значений, а свёртку в кусочно-постоянные окна (дождь, surge) делает билдер лога `replay-server` сравнением соседних минут. Альтернатива — публичные аксессоры интервалов `WorldEnv`: новый API и утечка внутреннего формата эпизодов к потребителю. Отклонена. В записях дренажа среда вычисляется теми же чистыми чтениями на `t` записи (`is_rain`/тариф rng не тратят).

5. **Типы — отдельный модуль `simulator/live.py`, frozen dataclass, кортежи.** `engine.py` остаётся сфокусирован на цикле; `live.py` — чистые данные без логики. Frozen + tuple: запись минуты неизменяема, её безопасно хранить в логе и передавать колбэку; времена — наивные datetime (контракт сим-времени M1).

6. **Ноль накладных расходов при `on_minute=None`.** Сбор событий и построение записи — только при заданном колбэке; прогон CLI не меняется ни по строкам, ни по производительности (бюджет A4 не затронут). При заданном колбэке стоимость — аппенды в списки минуты, по порядку величины меньше существующей поминутной работы (λ-розыгрыши, диспатч), поэтому тихий pre-run `replay-server` на 30 днях останется в десятках секунд.

7. **Нить событий — внутренний id заказа.** `internal_id` уже существует (§10.11) и в порядке создания совпадает с `trip_id` вставки; отдельный идентификатор событий не нужен, клиент связывает цепочку spawn → assignment → dropoff/expiry без обращения к БД.

## Risks / Trade-offs

- [Предсказанный `dropoff_at` назначения разошёлся с фактической высадкой] → тест сверки t(dropoff) == dropoff_at(assignment) по полному прогону; при нарушении инварианта правится вычисление в точке назначения, не механика тика.
- [Наблюдатель оказался нечистым (событие мутировало состояние мира)] → события строятся из иммунных к мутации значений (datetime/числа/кортежи в frozen dataclass); тест побайтовой идентичности таблиц с наблюдателем и без плюс равенство последовательностей записей на повторном прогоне.
- [Клиент предполагает «запись = полноценная минута мира», а записи дренажа без спавна] → спека фиксирует состав записей дренажа (только dropoffs/expiries, пустые списки легальны); фазу клиент различает по `t` за границей `days × 1440`.
- [Стоимость колбэка в длинном прогоне недооценена] → события собираются только при заданном колбэке; формальный лимит не вводится (A4 — про CLI без наблюдателя), порядок величины проверяется вручную при приёмке `replay-server`.

## Migration Plan

Чистое расширение: новый модуль и опциональный параметр; существующие вызовы, CLI, таблицы и тесты не меняются. Откат — удалить `simulator/live.py`, параметр и сбор событий из `run()`.
