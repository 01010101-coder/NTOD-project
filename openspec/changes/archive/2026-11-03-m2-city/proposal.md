## Why

M1 реализовал скелет конфига, часть ключей которого расходится с миром M2 (`docs/plan-m2-engine.md` §6): веса зоны не разделены на источник/цель, у спроса нет `base_rate`, у погоды и событий другая структура ключей, нет точки отсчёта сим-часов и ключей формулы выручки. Движок M2 начинается с модели города — канонический конфиг и `build_city` → `path_min` нужны всем последующим changes вехи (`m2-demand`, `m2-drivers`, `m2-env`, `m2-loop`, `m2-calibration`). Это change №1 в порядке конвейера §7 плана M2.

## What Changes

- **BREAKING** `common/config.py`: конфиг-модели правятся один раз под канон §6 — таблица замен против скелета M1:
  - `ZoneCfg(id, name, archetype, attract_origin, attract_dest, map:{x,y})` вместо `ZoneCfg(id, archetype, attractiveness, x, y)`;
  - `DemandCfg` + `base_rate: float = 2.0`, `profiles` — жёсткая структура «архетип → `{weekday: [24 float], weekend: [24 float]}`» вместо свободного dict;
  - `WeatherCfg` → `rain_day_chance: 0.15, episode_start_h: [6,22], episode_duration_h: [1,3], demand_mult: 1.4, travel_mult: 1.4` (ключи `rain_chance_per_day`, `episode_duration_min`, `request_multiplier`, `driver_multiplier` удаляются);
  - `events.friday_evening` → `days: [4,5], hours: [17,23] (диапазон включительно), archetypes: [business, mixed], demand_mult: 1.3` (без флага `enabled`);
  - `pricing.surge_injection` → `day_chance: 0.10, duration_min: [30,60], multiplier: [1.2,1.6]` (инъекции случайные, не календарные);
  - `PricingCfg` + `base_boarding: 100.0, per_min_rub: 12.0` (формула выручки §10.15 плана M2, в БД не пишется);
  - `EngineCfg` + `sim_start: "2026-11-02"` (понедельник — точка отсчёта сим-часов);
  - `RoadCfg` — без изменений (форма M1 сохранена осознанно).
  - После правки дефолты моделей равны каноническим значениям: пустой конфиг грузится и валиден. Обратная совместимость со старыми конфигами не требуется, внешних конфигов, кроме эталонного в репо, не существует (§6).
- `config.yaml` переписывается целиком под приложение А плана M2 (эталонный мир: 6 зон-архетипов, 7 двунаправленных дорог в минутах, профили спроса 4 архетипов × будни/выходные, множители дождя, «пятничного вечера» и surge-инъекций, тариф).
- Новый `simulator/city.py`: типы `ZoneInfo`, `HourProfile`, `CitySpec` и функция `build_city(cfg: AppConfig) -> CitySpec` по приложению Б плана M2 — зоны сортированы по id без пропусков, профили → numpy-массивы длины 24, Флойд на графе дорог → `path_min` `(Z, Z)` int.
- Новый `tests/test_sim_city.py`: конфиг-канон, связность графа, свойства `path_min`, профили (§8 плана M2).

## Capabilities

### New Capabilities

- `simulator-city`: модель города симулятора — зоны-архетипы с весами источника/цели (§3.1), двунаправленный дорожный граф с весами-минутами и матрица кратчайших путей `path_min` (Флойд, §3.2), суточные профили спроса по архетипам; публичный контракт типов `ZoneInfo`/`HourProfile`/`CitySpec` и `build_city` — приложению Б плана M2.

### Modified Capabilities

- `config-loading`: состав полей и дефолты конфиг-моделей меняются под канон §6 плана M2 (таблица замен против скелета M1); эталонный `config.yaml` в репо переписывается под приложение А плана M2; правило «дефолты = канонические значения, пустой конфиг валиден» сохраняется; запрет неизвестных ключей и частичная загрузка с дозаполнением дефолтами сохраняются без изменений.

## Impact

- Файлы change'а — ровно список §7 стр. 1 плана M2: `common/config.py`, `config.yaml`, `simulator/city.py`, `tests/test_sim_city.py`. Остальной код `common/` и `storage/` не трогается (запрет §2.2 п. 5 плана M2), схема SQLite не меняется.
- M1-тест `tests/test_config.py` остаётся зелёным без правок: его инвариант «эталонный конфиг равен дефолтам» (`tests/test_config.py:54-56`) сохраняется, поскольку `config.yaml` = приложение А = дефолты моделей.
- Зависимые changes вехи M2: `m2-demand` (λ использует `base_rate`, профили, `path_min`), `m2-drivers` (`path_min`), `m2-env` (ключи погоды/событий/инъекций), `m2-loop` (движок на `CitySpec`), `m2-calibration` (итоговые числа вносятся в `config.yaml`).
- Гейты приёмки (§7 плана M2): после этого change'а зелёны A1 (`make lint`), A2 (`make test`), A11 (`config.yaml` = канон §6); полный `make accept-m2` (A1–A13) — только после `m2-loop`.

## Open Questions

Непонятности плана, зафиксированные вопросами (§2.2 п. 8 плана M2: «непонятность — вопрос в чейндже, а не молчаливое решение своим способом»). План самодостаточен по разделам §3.1–3.2, §6, приложениям А и Б; ниже — места, где он не задаёт представление явно, с предлагаемыми ответами. Ни один из вопросов не меняет внешнее поведение из §7 стр. 1:

1. **Представление `map:{x,y}` в `ZoneCfg`.** §6 задаёт состав (`map:{x,y}`), но не тип значения в модели. Предлагаемое решение: вложенная pydantic-модель `MapCfg(x: float, y: float)` с базовым `extra="forbid"` — единый стиль с остальными секциями M1, опечатка в `x`/`y` даёт понятную ошибку с путём; координаты движком не читаются и в `ZoneInfo` не попадают (§3.1). Альтернатива — `dict[str, float]` (проверка слабее). На поведение по §7 стр. 1 не влияет.
2. **Уровень проверки профилей.** §7 стр. 1 относит «профили длины 24, неотрицательные» к проверкам `tests/test_sim_city.py`; pydantic-модель проверяет жёсткую структуру (архетип → `{weekday, weekend}`, списки float) и не дублирует проверку длины/неотрицательности. Предлагаемое решение — так и оставить: одна проверка в тестах, а не две.
3. **Тип `path_min` int (приложение Б) при `RoadCfg.minutes: float` (форма M1 сохранена §6).** Для эталонного конфига минуты целые; `build_city` приводит матрицу после Флойда к int (длительности далее считаются как `ceil(path_min × k)`, §3.2 — целые по построению). Дробные минуты в конфигах вне эталона планом не рассматриваются (§6: «внешних конфигов, кроме эталонного в репо, не существует»). Предлагаемое решение: привести к int без дополнительной валидации дробности.
