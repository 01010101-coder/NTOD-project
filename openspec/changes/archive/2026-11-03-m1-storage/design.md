## Context

Пакет `storage/` существует как скелет (`storage/__init__.py` — только docstring «содержимое добавляется в change m1-storage»), пакет внесён в `[tool.setuptools] packages` (`pyproject.toml:32`). Зависимости уже готовы из архивированных changes: `common/timeutil.py` (`to_iso`/`from_iso` — единая точка работы с ISO-строками, решение §7.4 плана M1) и `common/config.py` (`StorageCfg.db_path`, по умолчанию `data/taxi.db`). Окружение `.venv` содержит pytest и ruff; `make lint` = `ruff check` + `ruff format --check`, `make test` = `pytest` (Makefile из m1-tooling). Схема, прагмы, индексы фиксированы планом M1 §6 — «точная, из контракта openspec/config.yaml», менять нельзя.

## Goals / Non-Goals

**Goals:**
- Точная схема §6 (три таблицы + три индекса) и идемпотентная инициализация.
- Соединение с прагмами `foreign_keys=ON`, `journal_mode=WAL` и явными границами транзакции.
- Слой доступа: батч-вставка и параметризованные выборки по таблице/зоне/времени.
- CSV-экспорт и демо-скрипт `python -m storage.demo`.
- Тесты `tests/test_storage.py`, закрывающие способы проверки строки №4 таблицы §4 плана M1.

**Non-Goals:**
- Миграции сложнее «создать при отсутствии» (§2 плана M1); изменение схемы в будущих вехах — отдельный change.
- Наполнение `forecasts` данными (до M3 таблица пустая, но существует).
- Индексы/оптимизация под объёмы M2+, параллельная запись из нескольких процессов.
- Правка `config.yaml`, `pyproject.toml`, Makefile.

## Decisions

1. **Идемпотентность — `IF NOT EXISTS` в DDL, один `executescript`.** DDL трёх таблиц и трёх индексов — константа в `storage/schema.py`; `init_db(conn)` исполняет её одним `executescript`, где каждый объект объявлен с `CREATE ... IF NOT EXISTS`. Альтернатива — предварительная проверка `sqlite_master` или миграционная библиотека — отвергнута: план M1 §2 прямо ограничивает миграции «создать при отсутствии», а проверка перед выполнением добавляет состояние без выигрыша. Повторный init потому не падает и не трогает данные.
2. **`db.connect(path)`: прагмы после открытия, `row_factory=sqlite3.Row`, `isolation_level=None`.** Прагмы `foreign_keys` и `journal_mode` не персистентны между соединениями (WAL персистентен, `foreign_keys` — нет), поэтому применяются в каждом `connect`. `isolation_level=None` (autocommit-режим драйвера) — чтобы границы транзакции задавал наш код, а не скрытое поведение драйвера по умолчанию. `Row` даёт доступ к колонкам по именам без ORM. Альтернатива — дефолтный `isolation_level=""` с неявными транзакциями — отвергнута: границы фиксации становятся неявными, что усложняет батчи и тесты rollback.
3. **Транзакция — контекст-менеджер `transaction(conn)` в `db.py`**: `BEGIN` на входе, `COMMIT` при нормальном выходе, `ROLLBACK` при исключении с пробросом исключения наружу. Без вложенности (вложенный вызов — ошибка значения): вложенные транзакции в M1 не нужны, SAVEPOINT — усложнение.
4. **`repo.py` — функции модуля, по паре на таблицу, строки — dict.** Вставка `executemany` (одна транзакция на батч), выборки с опциональными фильтрами. `trips`: вставка без `trip_id` (SQLite генерирует его как alias rowid), вставка возвращает список сгенерированных id через `cursor.lastrowid` + счётчик; выборка с фильтрами по `origin_zone`, диапазону `created_at`. `zone_metrics_5min` и `forecasts`: вставка готовых строк (PK задаёт вызывающий код), выборка по `zone_id`/`ts`-диапазону (`forecasts` — ещё и опционально по `model_version`). Альтернатива — классы-репозитории или SQLAlchemy — отвергнута: стек проекта фиксирует stdlib `sqlite3` (openspec/config.yaml), функции проще и покрываются тестами напрямую.
5. **Время: на входе repo — `datetime`, конвертация только через `common.timeutil`.** При записи `to_iso(dt)`, при фильтрах — тоже `to_iso` для границ диапазона (лексикографический порядок ISO-текста «YYYY-MM-DD HH:MM:SS» совпадает с хронологическим, поэтому сравнение текстов корректно). Решение §7.4 плана M1: единственная точка работы с ISO-строками — `timeutil`. В БД текст хранится как есть — проверяется тестом прямым SQL.
6. **Имена таблиц для выборки/экспорта — белый список трёх констант**, SQL строится подстановкой имени только из этого списка, все значения — через параметры `?`. Исключает SQL-инъекцию через имя таблицы, не тянет ORM.
7. **`csv_export.export_table(conn, table, out_path)` — stdlib `csv.writer` поверх `SELECT *`.** Заголовок — из `cursor.description`; NULL → пустая строка. Альтернатива — pandas (`DataFrame.to_csv`) — отвергнута: pandas приводит NULL/float к своим представлениям (NaN, переформатирование float), а тест «CSV содержит те же строки» требует побайтово предсказуемого вывода; зависимости на модуль не нужны.
8. **`storage/demo.py` — демо на временных путях.** `tempfile.TemporaryDirectory`: БД и CSV создаются там, `data/taxi.db` из эталонного конфига не затрагивается (демо обязано быть безопасным для повторного запуска и CI). Пишет по строке в каждую таблицу, читает выборками, экспортирует CSV, печатает сводку (путь БД, число строк, путь CSV), код возврата 0. `common.logging_setup` используется для сообщений. Альтернатива — писать в `data/demo.db` — отвергнута: оставляет мусор в репо.
9. **Тесты `tests/test_storage.py` (tmp_path, «сырое» соединение для проверки формата).** Способы проверки ask'а закрыты по одному сценарию specs: повторный init; roundtrip всех трёх таблиц (write→read, поля равны); ISO-текст — чтение вторым `sqlite3`-соединением напрямую (проверяется именно формат хранения, а не поведение repo); CSV — сравнение заголовка и строк с выборкой; демо — `subprocess.run([sys.executable, "-m", "storage.demo"])` c проверкой кода возврата (заодно проверяет упаковку пакета). CHECK-статус, прагмы, rollback — тесты через `pytest.raises` и PRAGMA-запросы.
10. **`storage/__init__.py` — docstring по факту и реэкспорт public API** (`init_db`, `connect`, `transaction`, функции repo, `export_table`) для удобного `from storage import ...`; без циклических импортов (каждый модуль импортирует только `db`/`schema`, `__init__` — последним).

## Risks / Trade-offs

- [WAL создаёт файлы `-wal`/`-shm` рядом с БД] → `data/` уже в .gitignore, тесты и демо живут во временных каталогах; соединение закрывается после записи, чекпоинт происходит при закрытии.
- [`journal_mode=WAL` может не примениться на экзотических ФС] → не критично для M1: тест прагм читает фактическое значение; на CI Linux/ext4 и локальном macOS/APFS WAL применяется.
- [Повторный init не обновляет схему при её изменении] → осознанный предел M1 («создать при отсутствии», §2 плана); любое изменение схемы — будущий change с миграцией.
- [Батч-вставка trips возвращает id, вычисленные из `lastrowid` — при пустом списке вернётся пустой список] → контракт функции зафиксирован в docstring и тесте.
- [Демо через subprocess зависит от того, что пакет импортируется из окружения] → пакет установлен editable (m1-tooling), тест запускает `sys.executable` того же `.venv`.

## Migration Plan

Новый код, миграция не требуется: файлы добавляются в существующий пакет `storage`, обратный откат — удаление `storage/schema.py`, `storage/db.py`, `storage/repo.py`, `storage/csv_export.py`, `storage/demo.py` и `tests/test_storage.py`. БД в `data/` не создаётся change'ом (только кодом потребителя); `data/` в .gitignore.
