## Context

`m3-dataset` закрепил контракт данных: `FEATURE_MANIFEST` — 17 признаков на шаг
окна (комментарий модуля прямо называет его контрактом для m3-model),
`Examples` — окна `(n, steps, 17)` и таргеты `(n, 2)` по горизонтам
`RET_HORIZONS_MIN = (15, 30)`, `DatasetScalers` — нормализация (fit на train).
Гиперпараметры `ml:` уже в `MlCfg` (приложение А плана M3). План M3 §5
фиксирует: две архитектуры за контрактом туловища «окно + зона → R = 128»,
общие головки, одна BCE-головка с двумя выходами, loss MSE+MSE+вес×BCE,
детерминизм по `ml.seed`. Этот change — только архитектура и loss: цикл
обучения с ранней остановкой и артефакты — `m3-train-cli`, walk-forward и
запись `forecasts` — `m3-inference`.

## Goals / Non-Goals

**Goals:**

- Один модуль `ml/model.py`, покрывающий контракт туловища, обе архитектуры,
  multi-task головки, loss и seed — всё, что нужно `m3-train-cli` для цикла
  обучения без доработок модели.
- Взаимозаменяемость MLP/LSTM до уровня подстановки в один и тот же вызов
  (честное сравнение плана §5: одинаковые головки, loss, условия).

**Non-Goals:**

- Цикл обучения, ранняя остановка, артефакты, DataLoader — `m3-train-cli`.
- Запись `forecasts`, обратное преобразование scaler'ов при инференсе —
  `m3-inference` (сеть предсказывает в нормализованном пространстве таргетов).
- Отдельные гиперпараметры под LSTM (кроме `lstm_hidden`/`lstm_layers`),
  тюнинг, ансамбли, GPU — план M3 §2 «чего не делать».

## Decisions

1. **Контракт туловища — сигнатура, а не абстрактный класс.** Оба туловища —
   `nn.Module` с `forward(windows (n, steps, 17) float32, zone_ids (n,) int64)
   → (n, 128)`; фабрика `build_model(arch, cfg, n_zones)` собирает
   `MultiTaskNet` вокруг выбранного туловища. Protocol/ABC не вводим:
   взаимозаменяемость проверяется параметризованным тестом, а не иерархией
   типов (прецедент — лёгкие интерфейсы `ml-dataset`).
2. **Размер R = 128 — константа модуля `TRUNK_OUTPUT_DIM`; последний элемент
   `ml.mlp_hidden` обязан равняться ему** (`ValueError` с сообщением иначе).
   При дефолте `[256, 128]` MLP — это `Linear(steps·17 + 8 → 256) → ReLU →
   Dropout(ml.dropout) → Linear(256 → 128)` без лишней финальной проекции,
   ровно как в плане §5. Альтернатива («скрытые слои + всегда добавляемая
   проекция в R») отвергнута: добавляет слой сверх плана при дефолте.
3. **LSTM-туловище**: эмбеддинг зоны конкатенируется к каждому шагу окна →
   `(n, steps, 17 + zone_embed_dim)` → `LSTM(hidden=ml.lstm_hidden,
   layers=ml.lstm_layers, batch_first=True)` → последнее скрытое состояние →
   `Linear(lstm_hidden, 128)`. Нелинейности после проекции нет — «сырое»
   представление R.
4. **Головки — три независимых `Linear(128, 2)`** (спрос, сток, логиты
   дефицита); порядок колонок — `RET_HORIZONS_MIN` (15, 30). Выход сети —
   `ModelOutput` (NamedTuple): `pred_requests`, `pred_free_drivers` (оба в
   нормализованном пространстве таргетов), `deficit_logits` (для BCE),
   `deficit_prob = sigmoid(logits)` (для инференса/метрик). Две репрезентации
   дефицита осознанно: BCE-with-logits численно стабилен, инференсу нужны
   вероятности.
5. **Loss — модуль `MultitaskLoss`**: `total = mse_requests + mse_free +
   cls_weight × BCEWithLogits(deficit_logits, метки, pos_weight)`. Возвращает
   `LossComponents(total, mse_requests, mse_free, bce)` — компоненты раздельно
   для кривых обучения и `metrics.json`. `pos_weight` считает функция
   `deficit_pos_weight(train_deficit (n, 2)) = (1 − p) / p` по фактической
   доле дефицита train-роли; вырожденные `p → 0/1` — `ValueError` (мир без
   дефицита не обучаем — сигнал ошибки конфигурации, а не тихий fallback).
   Расчёт доли живёт здесь, вызывается из `m3-train-cli`.
6. **Конвертация numpy → tensor на границе вызывающего** (train/infer),
   сеть принимает `torch.Tensor` (`float32` входы, `int64` зоны). Датасет
   отдаёт `float64` numpy — конвертация с понижением до `float32` происходит
   один раз в батче, а не в forward.
7. **Детерминизм — `set_global_seed(seed)`** (`torch.manual_seed` +
   `np.random.seed`) вызывается перед построением сети; отдельные
   `torch.use_deterministic_algorithms` не включаем — на CPU операции и так
   детерминированы, флаг может ломать доступные ядра. Детерминизм dropout в
   тестах шагов обеспечивается одинаковым порядком вызовов после одинакового
   seed (маски dropout расходуются одинаково), а сравнение чистых forward —
   в `eval()`.

## Risks / Trade-offs

- [MLP `mlp_hidden[-1] ≠ 128` ломает контракт общих головок] → явный
  `ValueError` в конструкторе туловища с сообщением о `TRUNK_OUTPUT_DIM`.
- [LSTM медленнее MLP на CPU, 48 тыс. примеров × 72 шага] → приемлемо по
  плану (минуты на эпоху, patience 8 в m3-train-cli); ускорение — не цель
  вехи, GPU запрещён планом.
- [Dropout вносит стохастичность в сравнение сетей] → одинаковый seed и
  одинаковый порядок батчей для обеих архитектур закреплены в m3-train-cli;
  здесь — только гарантия одинаковости масок при одинаковом seed.
- [`float64 → float32` на границе] → данные нормализованы (StandardScaler),
  потеря точности в 7-й значащей цифре несущественна.

## Migration Plan

Новый модуль, ничего не заменяет: `ml/model.py` + `tests/test_ml_model.py`.
Откат — удаление файлов; зависимости вниз по потоку (`m3-train-cli`,
`m3-inference`) ещё не существуют.
