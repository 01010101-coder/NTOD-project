## Context

См. proposal.md — Why. Состояние на момент планирования (проверено в этой сессии): `common/` содержит только `__init__.py`, `common/timeutil.py` и `common/logging_setup.py` не существуют; `tests/` содержит только `test_imports.py` из `m1-tooling`; тулинг вехи готов (`make lint && make test` зелёные на скелете). `pyproject.toml` (`m1-tooling`) перечисляет пакеты явно (`common`, `storage`, `simulator`), поэтому новые модули внутри `common/` не требуют правки упаковки.

## Goals / Non-Goals

**Goals:**
- Закрепить единственную точку работы с ISO-текстом времени (решение плана M1 §7.4) с инвариантом «секунды всегда 00».
- Дать `m1-config`, `m1-storage` и симулятору M2 готовые примитивы времени и логирования, покрытые тестами `tests/test_timeutil.py`.

**Non-Goals:**
- pydantic-модели и эталонный `config.yaml` (план §5) — это `m1-config`; timeutil от конфига не зависит.
- SQLite-схема (план §6), репозиторий, CSV-экспорт — это `m1-storage`.
- Векторизованная работа со временем над массивами меток (pandas) — если понадобится, это код движка M2 поверх примитивов timeutil.
- Таймзоны, DST, `dateutil`, `zoneinfo` — против решения §7.2 (наивный `datetime`, никаких таймзон).

## Decisions

1. **Только стандартная библиотека (`datetime`, `logging`).** Новых зависимостей нет; `arrow`/`pendulum`/`dateutil` отклонены — примитивы тривиальны, а лишняя зависимость усложняет `make install` без выгоды для M1.
2. **`to_iso` нормализует, а не валидирует.** Секунды и микросекунды входного `datetime` обнуляются (усечение, не округление) перед форматированием `"%Y-%m-%d %H:%M:%S"`. Инвариант «секунды всегда 00» выполняется даже для «грязного» входа; альтернатива — падать при ненулевых секундах — отклонена: она превращает удобную функцию в источник ошибок в горячем пути симулятора, а отбрасывание секунд детерминировано и покрывается тестом.
3. **`from_iso` — строгий `datetime.strptime(s, "%Y-%m-%d %H:%M:%S")`.** `strptime` сам бросает `ValueError` на чужих форматах (`T`-разделитель, дата без времени, мусор); сообщение об ошибке дополняется именем ожидаемого формата. Известная уступка: `strptime` допускает числа без ведущих нулей (`2026-3-1 9:05:00`); для M1 принимаем — разбор таких строк корректен, а регэксп-предвалидация усложнила бы код без поведенческой пользы.
4. **`add_minutes(dt, n)` = усечение результата после `dt + timedelta(minutes=n)`.** Отрицательные `n` разрешены (откат во времени нужен для горизонтов прогноза 15/30 мин: `ts − horizon`). Результат всегда минутной точности. Альтернатива с оком правки в `datetime` отклонена — изменять встроенный тип ради проекта не нужно.
5. **`bucket5(ts)` возвращает наивный `datetime`**, а не строку: по решению §7.4 остальной код живёт в `datetime`, а ISO-метка бакета — это `to_iso(bucket5(ts))`, и именно она попадает в колонку `zone_metrics_5min.ts` схемы §6. Формула — модуль минут: `replace(minute=minute - minute % 5, second=0, microsecond=0)`. Альтернатива через арифметику epoch (`timestamp() // 300`) отклонена: `timestamp()` вовлекает локальную таймзону, что опасно для наивного времени; модуль минут точен и тривиально проверяется на границах (`:00–:04 → :00`, `:05–:09 → :05`, `:55–:59 → :55`, переходы часа/полуночи — тестами).
6. **`logging_setup` — `logging.basicConfig(..., force=True)` (Python ≥ 3.8).** Единый формат «время | уровень | имя логгера | сообщение», поток `stderr`, уровень — параметр функции. `force=True` снимает прежние обработчики корневого логгера, что напрямую даёт поведение «повторная настройка не плодит дублей» из specs; альтернатива — ручное управление списком handler'ов — отклонена как избыточная при наличии стандартного механизма.
7. **Совместимость с планом (учтено по ask'у).** Скелет конфига §5: дефолт `engine.agg_step_min = 5` совпадает с шагом `bucket5`, `drivers.wait_limit_min` и горизонты 15/30 работают через `add_minutes`; сам timeutil конфиг не читает — зависимость односторонняя (`m1-config` → `m1-common`). Схема SQLite §6: вывод `to_iso` — это в точности TEXT-формат колонок `trips.created_at/assigned_at/pickup_at/dropoff_at`, `zone_metrics_5min.ts`, `forecasts.ts`, инвариант «секунды 00» отражён в комментарии схемы; `m1-storage` получает время уже в готовом формате и свой парсер не пишет. Решения §7.2 и §7.4 реализованы формулами выше. DoD §8 («последний прогон — `make lint && make test`») закрыт финальной группой tasks.md; правила `openspec/config.yaml` (способ проверки у каждой задачи) соблюдены в tasks.md.
8. **Ruff-совместимость сразу.** Модули пишутся под правила `E,F,I,W,UP` и line-length 100 из `pyproject.toml` (`m1-tooling`), чтобы не гонять `make fmt` отдельным шагом; docstring — на русском, идентификаторы — на английском (соглашение проекта).

## Risks / Trade-offs

- [`strptime` допускает числа без ведущих нулей] → документируется в docstring; roundtrip через `to_iso` всегда возвращает канонический вид с нулями, поэтому в БД неканонических строк не появится.
- [`force=True` в `basicConfig` сносит обработчики, поставленные сторонним кодом] → функция вызывается только на входных точках проекта (CLI/демо/симуляция), где сторонних обработчиков ещё нет; тест фиксирует отсутствие дублей.
- [`bucket5` скалярный — в M2 на больших массивах меток возможен перебор в цикле] → примем: движок агрегирует по шагам, объёмы малы (десятки зон × шаги суток); при необходимости pandas-векторизация добавляется в M2 поверх, не вместо timeutil.
- [Расхождение контекста `openspec/config.yaml` (упоминание streamlit/app) с планом M1 §2] → на этот change не влияет: timeutil и логирование интерфейсной части не касаются; актуализация текста конфига запланирована на M4.

## Migration Plan

Не применим: только добавляются новые файлы (`common/timeutil.py`, `common/logging_setup.py`, `tests/test_timeutil.py`), существующие не меняются. Откат — удаление добавленных файлов; зависимых потребителей в репо ещё нет.
