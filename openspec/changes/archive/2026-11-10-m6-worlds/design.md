# Design: m6-worlds

## Context

Опора — закрытые change'ы вехи: `m6-rng-branches` (реестр `BRANCHES`,
`generate_branch`, побитовая повторяемость; `data/worlds/a-base.db` существует) и
`m6-policy` (`PolicyContour` с диагностикой `fire_count/fire_slots/fire_rate`,
`LiveRowSource`, `NetworkPredictor`, окно активации от `ml.train_days`, секция
`policy:` конфига с `shift = {mlp: 0.0, lstm: 0.0}`). Машина M3: `collect_examples`
даёт роли train/val/test (val = дни 29–30 при эталоне), `predict_windows` — общий
батч-инференс, `insert_forecasts` пишет строки контракта, PK `forecasts` уже с
`model_version` (миграций нет — §3 плана). Каталоги артефактов обоих семейств есть
(`mlp-v1-2026-11-07`, `lstm-v1-2026-11-07`). Направление зависимостей — решение 1
design `m6-policy`: `simulator` импортирует `ml` публично, не наоборот.

## Goals / Non-Goals

**Goals:**

- δ-калибровка честности как воспроизводимая офлайн-процедура с артефактом и
  обновлением конфига (до генерации сетки — «правила до эксперимента»);
- тень-прогнозы обеих моделей в каждой ветке без влияния на rng/историю;
- генерация сетки A/B/C/D одной операцией с наблюдаемой диагностикой честности;
- реестр миров как API для `m6-worlds-ui`.

**Non-Goals:**

- Platt/изотонная калибровка вероятностей, ретрейн сетей, правка артефактов M3 и
  `m3_epoch.db` (только чтение) — §2 плана;
- подключение реестра к серверу/UI, вкладка «Сравнение» — change'ы 4–5;
- мир «Эпоха» в реестре миров (живёт в `ml.db`, добавит `m6-worlds-ui`);
- гистерезис ступеней (патч-запас §8.2 — только по факту мигания).

## Decisions

1. **δ-калибровка — чистая функция подбора + CLI-обвязка; модуль
   `simulator/policy_calibration.py`** (не в `ml/`): калибровка потребляет
   `policy.stairs`/`target_fire_rate` — это предметная область политики, `ml` не
   знает про политику (решение 1 design `m6-policy`). Данные — `ml.db` через
   `SqliteRowSource`, примеры val-роли — обобщение `_collect_test_examples` до
   параметра роли (публичная функция в `ml/infer.py`, walk-forward и калибровка
   делят один сборщик); инференс — `predict_windows` на всех окнах одним батчем.
   Чистая функция `fire_fraction(probs, delta, stairs) -> float` — доля пар с
   `p_eff ≥ min(p_min)`; подбор — бинарный поиск δ ∈ [−1, 1] (доля монотонна по δ)
   до входа в допуск ±1 п.п. или исчерпания итераций (запас на дискретный скачок —
   риск §8.4 фиксируется честно). Альтернатива «подбор прогонами контура»
   отклонена: дорога (прогон мира на каждый δ) и не нужна — частота выражается
   аналитически по вероятностям.
2. **Обновление `config.yaml` — точечная правка текста, не перезапись YAML.**
   PyYAML не сохраняет комментарии; перезапись уничтожила бы пояснения эталона.
   Обновляется только строка `shift:` в секции `policy:` (замена по шаблону строки
   со значениями, округлёнными до 3 знаков); после правки — контроль
   `load_config` round-trip: сдвиги из файла равны записанным в json. Если строка
   не найдена — ошибка до записи (конфиг heterodox, чинится руками).
3. **Тень-прогнозист — отдельный наблюдатель `ShadowForecaster` в
   `simulator/policy.py`, батч на закрытие бакета.** Две сети (`mlp`, `lstm`)
   поднимаются из свежайших каталогов (`latest_artifact_dir`) на старте
   генерации; на закрытии бакета, когда строки всех зон бакета собраны (счётчик
   зон, не порядок строк), — один батч-прогон `predict_windows` на окна всех зон
   (быстрее поштучного `NetworkPredictor.predict`, прецедент `INFER_BATCH_SIZE`).
   Каденс и граница записи — окно активации (день `ml.train_days + 1`):
   прецедент M3 (forecasts = тест-эпоха), иначе объём ×5 (37 дней вместо 7) и
   инференсы в прогреве ~128 тыс. на ветку взламывают ориентир 25–50 с (§3);
   тумблер «факт» покрывает прогрев, «прогноз» осмыслен там, где политика.
   `model_version` = имя семейства (`mlp`/`lstm`), не имя каталога — прямое
   указание §3 плана (PK и чтение UI по семейству); имена каталогов фиксируются в
   `policy-calibration.json` для прослеживаемости. Запись — буфер строк, flush в
   соединение БД ветки на каждом закрытом бакете (`insert_forecasts`).
   Альтернатива «переиспользовать прогноз политика в C/D» отклонена: решение 7 —
   тень независима от политики (в C/D политик и тень — разные инференсы; двойная
   работа ~12 тыс. инференсов ≈ +6 с на ветку — принята).
4. **Тень — часть формата ветки: `shadow=True` по умолчанию в `generate_branch`,
   guard артефактов обоих семейств для любой ветки.** Иначе формат миров
   раздваивается («мир с тенью/без»), а UI-тумблер «прогноз» работал бы через мир.
   `shadow=False` оставлен как параметр функции (не CLI) для прямых тестовых
   прогонов математики политик — существующие тесты `m6-policy` без артефактов
   не переписываются. CLI `--branch` всегда генерирует полный формат (с тенью).
5. **Сетка — `generate_worlds(cfg, *, seed=None, days=37, worlds_dir=None)` +
   флаг CLI `--all`** (не отдельный модуль): переиспользует guard, сводки и
   порядок реестра; `--db` с `--all` взаимоисключителен (пути задаёт реестр).
   Guard сетки — пре-чек всех целевых БД до первой ветки (fail fast: полусетка
   после 3 минут прогона хуже отказа до старта). Диагностика честности — после
   каждой контурной ветки печать `fire_rate` контура (свойство уже существует,
   пишется в stdout рядом со сводкой): сверка «C и D ±1 п.п.» наблюдаема без
   чтения внутренностей. `worlds_dir` берётся из `policy.worlds_dir` (в CLI
   `--all` добавляется `--worlds-dir` для тестов).
6. **Реестр миров — `WorldInfo` (dataclass) + `list_worlds(cfg, *, worlds_dir=None)`
   в `simulator/branches.py`.** Производная `BRANCHES` (порядок реестра), метка
   политики — константа описания в `BranchSpec` (новое поле `label`), наличие —
   `Path.exists()`. Список фиксированного состава, не скан каталога (§2.7):
   реестр описывает миры генератора, мусор в каталоге мирами не становится.
7. **Тесты — фабрика мини-артефактов тестов `ml/`** (прецедент `m6-policy` 4.2):
   калибровка и тень тестируются на обучаемых за секунды сетках; полные
   37-дневные прогоны — приёмочные задачи (не в `make test`), побитовость дней
   1–30 полных миров проверяется задачей генерации по `data/worlds/`.

## Risks / Trade-offs

- **δ не выравнивает частоты** (§8.4): дискретность доли на ~3,5 тыс. пар val —
  шаг доли ≈ 0,03 %, практический риск мал; при вырождении — json фиксирует
  честное ограничение, генерация сетки продолжается с лучшими δ.
- **Время генерации ветки растёт** (тень = 2 сети): замер задачи приёмки против
  ориентира 25–50 с; запас — батч-инференс тени (решение 3), ориентир M3
  «окна за O(минуты) на всю тест-неделю».
- **Точечная правка `config.yaml` хрупка к переформатированию** (строка `shift:`
  одной строкой): guard «строка не найдена → ошибка без записи» + round-trip
  проверка; риск принят ради сохранения комментариев эталона.
- **`forecasts` только с дня 31**: тумблер «прогноз» в прогреве пуст —
  сознательный размен (объём/время против полноты), отражён в отчёте вехи.
- **Guard артефактов на все ветки** — `a-base` больше не генерируется без
  каталогов `mlp`/`lstm`: в репо артефакты есть (M3 закрыта), CI-тесты уходят на
  `shadow=False` и мини-артефакты.
