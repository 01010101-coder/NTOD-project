# Design: m3-inference

## Context

Заархивированы `ml-dataset`, `ml-baselines`, `ml-model`, `m3-train-cli`;
активных changes нет. Фактические API, на которые опирается этот design:

- `ml.dataset`: `SqliteRowSource` (вся история в памяти), `collect_examples`
  возвращает примеры по ролям дней с ключами `(zone_id, ts)` — окна по
  построению без утечки будущего, границы «есть окно и оба целевых бакета»
  встроены; `DatasetScalers.load(path)`; `world_start(cfg)`.
- `ml.baselines`: `naive_persist(source, ts, zone)` / `naive_season(…)` →
  dict-строки контракта `forecasts` (версии `naive-persist-v1` /
  `naive-season-v1`); нет слота — пустой список.
- `ml.model`: `build_model(arch, ml_cfg, n_zones)`, `ModelOutput`
  (`pred_requests`/`pred_free_drivers` — нормализованное пространство,
  `deficit_prob` — сигмоида, готова к записи).
- `ml.train`: контракт артефактов — каталог `artifacts/{arch}-v1-{дата}/` с
  `weights.pt` (`{arch, state_dict, ml_cfg: model_dump()}`),
  `scalers.pkl`, `loss.json`, `metrics.json`; `model_version` = имя каталога;
  денормализация по образцу `val_mae_requests` (inverse_transform scaler'а
  таргетов).
- `ml.metrics`: `build_summary(model_version, rows, source)` по строкам
  `forecasts` + `render_table(summaries)`; docstring прямо адресует
  `artifacts/summary-<дата>.json` этого change.
- `storage`: `insert_forecasts` / `list_forecasts(model_version=…)`; PK
  `forecasts` — `(ts, zone_id, horizon_min)` **без** `model_version` (схема
  M1) — конфликт с четырьмя версиями на одной паре.

Реальность: эпоха `data/m3_epoch.db` (37 дней, 63 936 строк метрик), обе сети
обучены (`artifacts/mlp-v1-2026-11-06`, `artifacts/lstm-v1-2026-11-06`,
`window-sweep.json` есть), `forecasts` во всех БД проекта пуста (инвариант A5
M2).

## Goals / Non-Goals

**Goals:**

- Walk-forward по тест-эпохе → `forecasts`: две сети + два наива на общем
  наборе пар (ts, зона), горизонт 15/30.
- Идемпотентная перезапись версий; соседство четырёх `model_version` (PK с
  `model_version`, миграция старых пустых таблиц).
- Сводная прогона: `artifacts/summary-<дата>.json` + печатная таблица.
- CLI `python -m ml infer` в существующих конвенциях `ml/__main__.py`.

**Non-Goals:**

- Онлайн-инференс поверх живого движка и политика цены — M6 (слой `RowSource`
  уже подготовлен).
- Графики, вкладка «Лаборатория» — `m3-ml-tab` (читает `forecasts` и
  `summary-*.json` как есть).
- Новые параметры конфига, новая Makefile-цель (план зовёт CLI напрямую),
  новые зависимости, GPU.

## Decisions

1. **Прогон = `collect_examples(test)`, не отдельный walk-forward-цикл.**
   Один сборщик для обучения и инференса: одна семантика границ («есть окно и
   целевые бакеты»), одни анти-лик гарантии, ключи `(zone, ts)` бесплатно
   дают привязку строк. Альтернатива — собственный перебор бакетов только с
   окнами — дублировала бы границы и допускала расхождение входов
   обучения/инференса. Лишняя работа (сбор таргетов test-роли, которые
   инференсу не нужны) — секунды, принята сознательно.

2. **Восстановление сети из артефакта, не из живого конфига.**
   `weights.pt` несёт снимок `ml:`-конфига (решение 4 design.md
   `m3-train-cli`): сеть строится по снимку (`window_hours`, размеры слоёв),
   веса — `state_dict`, нормализация — `DatasetScalers.load` из каталога
   модели. Прогноз: окна нормализуются scaler'ами артефакта → батчи без
   градиентов (`eval`) → `inverse_transform` регрессий → строки.
   `n_zones` для построения — из `config.yaml` города (`max(zone.id)+1`),
   это параметр окружения, а не обучения.

3. **PK `forecasts` дополняется `model_version`; миграция — ensure-шаг.**
   DDL меняется на `PRIMARY KEY (ts, zone_id, horizon_min, model_version)`;
   `init_db` создаёт новую форму. Для существующих БД — `ensure_forecasts_
   schema(conn)`: PK читается из `PRAGMA table_info`; старая форма и пустая
   таблица → DROP + CREATE в одной транзакции; старая и непустая → отказ
   (защита от чужой БД; в проекте `forecasts` пуста везде по A5); новая
   форма → no-op. Вызывается из инференса перед записью. Альтернатива
   «пересоздавать всегда» отвергнута: роняла бы ленивую совместимость
   старых БД; альтернатива «уникальный индекс вместо PK» — тот же
   пересоздание таблицы без выгоды.

4. **Перезапись версий: delete + insert, одной транзакцией на версию.**
   `storage.repo.delete_forecasts(conn, model_version)`; прогон для каждой
   версии сначала удаляет её старые строки, затем вставляет новые. Повтор
   идемпотентен: сеть детерминирована на фиксированных весах, наивы — чистые
   функции, порядок строк фиксирован ключами test-роли. Флаг `--force` не
   нужен: нечего защищать (замена строго своих версий, чужие не трогаются).
   Альтернатива «refuse-if-exists» прецедента генерации отвергнута: там
   защищались данные мира, здесь перезапись — штатный цикл итераций.

5. **Сводная считается по строкам из БД, не из памяти прогона.**
   После записи всех версий — `list_forecasts(model_version=…)` →
   `build_summary` на каждую → список в `artifacts/summary-<локальная
   дата>.json` (`{"date": …, "summaries": […]}`) и `render_table` в stdout.
   Чтение из БД заодно валидирует записанное (пары, денормализацию) —
   свободная проверка целостности прогона.

6. **Выбор версии сети: самый свежий каталог семейства.**
   `--models all|naive|mlp|lstm`; для `mlp`/`lstm` — лексический максимум
   имени каталога `artifacts/{arch}-v1-*` (даты ISO сортируются лексически;
   двух каталогов одной даты не бывает — `train` отказывается). Guard всех
   запрошенных семейств до записи: нет БД, нет каталога, старая непустая
   `forecasts` → stderr + exit 2, ничего не записано (прецедент guard'ов
   `train`). Явный флаг `--model-version` не вводится: один прогон вехи,
   при смене версии достаточно свежести каталога.

7. **Наивы — тем же проходом и тем же источником.**
   `SqliteRowSource` строится один раз на прогон (память уже оплачена
   `collect_examples`); наивы вычисляются по ключам test-роли. Отсутствие
   вчерашнего слота у сезонного наива — пустой список (молчаливый пропуск,
   спека `ml-baselines`); на эталонной эпохе дыр нет, наборы пар совпадают
   полностью.

8. **CLI — третья подкоманда в существующем парсере.**
   Формат приложения Б плана M3: `walk-forward: model=… rows=…` на версию,
   `summary: …`, таблица. Прогресс в stdout (строк немного, stderr не нужен),
   ошибки — stderr + exit 2, успех — exit 0 — конвенции `ml/__main__.py`.

## Risks / Trade-offs

- [Память: `collect_examples` держит окна test-роли в float64] → 7 дней ≈
  12 тыс. примеров × 72×17 ≈ 80 МБ — приемлемо; при будущих длинных тест-эпохах
  (M6, ветки) рассмотреть чанкинг — не сейчас.
- [Побитовое сравнение в мутационном тесте может плавать] → прогон
  детерминирован (фиксированный порядок ключей, одинаковое разбиение на
  батчи, `eval`-режим без dropout) — сравнение значений строк стабильно;
  тест сравнивает значения прогнозов, не биты тензоров.
- [Миграция меняет схему M1, зафиксированную в main-спеке `data-storage`] →
  дельта-спека этого change модифицирует требование; после архива main-спека
  обновится, расхождение живёт только внутри change.
- [`m3_epoch.db` создана со старым PK — первый `infer` против неё миграцию
  применит] → ожидаемо и безопасно (таблица пуста); про это пишет stderr-строка
  миграции? Нет — молча: ожидаемый штатный путь, лишний шум в машинный
  вывод не добавляем.

## Migration Plan

1. Обновить DDL `forecasts` + `ensure_forecasts_schema` + `delete_forecasts`
   (группа 1 задач) — до всякого инференса; `make test` на этом шаге
   проверяет и старые тесты схемы (PK-зависимые тесты M1 обновляются в той
   же задаче).
2. Инференс и CLI (группы 2–3) на синтетических мини-эпохах.
3. Первый прогон на эталонной эпохе — финальная задача: миграция применится
   к `data/m3_epoch.db` лениво, таблица заполнится.
4. Откат: `forecasts` в эталонной БД можно просто очистить (DELETE), артефакты
   обучения не затрагиваются; откат кода — обычный revert change.
