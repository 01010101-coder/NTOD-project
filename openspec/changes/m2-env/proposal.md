## Why

Среда мира (`WorldEnv`) — один из трёх параллельных компонентов движка M2 после `m2-city` (§7: 2, 3, 4 можно параллельно после 1): шаг 1 минутного цикла — «Среда: переходы погоды, календарь, состояние тарифа» (§3.7). Дождь и «пятничный вечер» дают различимые горбы спроса (§9), а обучающие surge-инъекции — «единственный источник вариации `price_multiplier` в эпоху генерации — нужен, чтобы признак не был константой для ML (M3)» (§3.6). Без `simulator/env.py` changes `m2-demand` и `m2-drivers` не могут собрать λ-множители, а `m2-loop` — шаг «Среда» и колонки `is_rain`/`event`/`price_multiplier` агрегата (§3.8).

## What Changes

- Новый `simulator/env.py` — класс `WorldEnv` по приложению Б плана M2 дословно: `__init__(cfg: AppConfig, rng: np.random.Generator)`, `advance_day(day_index: int)`, `is_rain(t: datetime) -> bool`, `event_label(zone: ZoneInfo, t: datetime) -> str`, `price_multiplier(zone_id: int, t: datetime) -> float` (§7 стр. 4; зависимость только от уже существующих `simulator.city.CitySpec`/`ZoneInfo`, `common.config.AppConfig`, `common.timeutil`).
  - **Дождь** (§3.6): «раз в день Bernoulli `weather.rain_day_chance` (эталон 0.15). Эпизод: старт U(6:00–22:00), длительность U(1–3) ч» — ключи приложения А `episode_start_h: [6, 22]`, `episode_duration_h: [1, 3]`, `demand_mult: 1.4`, `travel_mult: 1.4`.
  - **«Пятничный вечер»** (§3.6): «календарно, дни из конфига (пт, сб), часы 17–23 включительно, для архетипов business/mixed — спрос × 1.3» — ключи приложения А `days: [4, 5]`, `hours: [17, 23]` (диапазон включительно), `archetypes: [business, mixed]`, `demand_mult: 1.3`.
  - **Тариф со случайными surge-инъекциями** (§3.6): «раз в день Bernoulli `surge_injection.day_chance` (0.10) → случайная зона, старт U(сутки), длительность U(30–60) мин, множитель U(1.2–1.6)»; `price_multiplier(zone, t)`: «всюду 1.0, кроме обучающих инъекций».
  - **Нескачущий rng-поток** (§10.13): «Если `price_fn` задан — он подменяет тариф зон, но **розыгрыши инъекций всё равно происходят**: поток rng не сдвигается, ветки A/B на одном seed сравнимы попарно» → все розыгрыши происходят безусловно в `advance_day` (00:00, приложение Б), запросы `is_rain`/`event_label`/`price_multiplier` rng не тратят.
- Новый `tests/test_sim_env.py` — проверки строки №4 §7: «форс-дождь (шанс 1.0) → спрос выше и поездки дольше; форс-инъекция → `price_multiplier` в агрегате > 1 в заданном окне; пятница даёт горб в заданных архетипах» — на уровне публичного API `WorldEnv` (см. Open Questions, вопрос 1 о распределении композитных проверок по changes конвейера).

## Capabilities

### New Capabilities

- `simulator-env`: среда мира симулятора M2 — суточные розыгрыши дождя (Bernoulli/день, эпизод U(6:00–22:00) × U(1–3) ч), календарное событие «пятничный вечер» (пт+сб, 17–23 включительно, архетипы business/mixed), случайные обучающие surge-инъекции (Bernoulli/день → зона, старт U(сутки), 30–60 мин, множитель 1.2–1.6), тариф зон `price_multiplier(zone, t)` (1.0 вне инъекций); публичный контракт `WorldEnv` — приложению Б плана M2, нескачущий rng-поток — §10.13.

## Open Questions

Непонятности плана, зафиксированные вопросами (§2.2 п. 8: «непонятность в плане — вопрос в чейндже, а не молчаливое решение своим способом»). Ни один не меняет внешнее поведение строки №4 §7; ниже — предлагаемые ответы, окончательные — за владельцем плана:

1. **Композитные проверки строки №4 §7 vs состав файлов change'а.** «Спрос выше и поездки дольше» требует λ-формулы (`simulator/demand.py`, change `m2-demand`) и формулы длительности (`simulator/drivers.py`, change `m2-drivers`), «`price_multiplier` в агрегате» — `AggregateBuffer` (`simulator/aggregate.py`, change `m2-loop`); changes 2–4 идут параллельно после 1 (§7), на момент `m2-env` этих файлов нет, и в список файлов change'а они не входят. Предлагаемое решение: в `tests/test_sim_env.py` проверять среду по публичному API `WorldEnv` и значениям приложения А — форс-дождь (`rain_day_chance = 1.0`) → `is_rain(t)` истинен внутри разыгранного эпизода и ложен вне его (факторы `demand_mult`/`travel_mult` к λ и длительностям применяют `m2-demand`/`m2-drivers` в своих тестах); форс-инъекция (`day_chance = 1.0`) → `price_multiplier(zone_id, t) > 1` внутри разыгранного окна и `= 1.0` вне; пятница → `event_label` в заданных днях/часах/архетипах. Агрегатная проверка (колонка `price_multiplier` > 1 в окне) и композитные горбы завершаются в тестах `m2-demand`/`m2-drivers`/`m2-loop` без изменения контракта `WorldEnv`.
2. **«В заданном окне» при форс-инъекции.** Шанс 1.0 гарантирует инъекцию в день, но зона, старт, длительность и множитель — случайные розыгрыши (§3.6); API приложения Б не принимает окно снаружи. Предлагаемое решение: при фиксированном seed окно детерминировано; тест находит его по наблюдаемому состоянию (минуты, где `price_multiplier(zone, t) > 1`) и проверяет: > 1 внутри окна, `= 1.0` вне, длительность ∈ [30, 60] мин, множитель ∈ [1.2, 1.6], ровно одна зона; доступ к приватным полям — на усмотрение исполнителя (приложение Б: «внутренние детали реализации (приватные функции, поля) — на усмотрение исполнителя»).
3. **Границы и разрешение розыгрышей §3.6.** «Старт U(6:00–22:00)» (`episode_start_h: [6, 22]`), «длительность U(1–3) ч» (`episode_duration_h: [1, 3]`), «старт U(сутки)», «длительность U(30–60) мин», «множитель U(1.2–1.6)» — план не уточняет целые/вещественные значения и включительность границ; при старте 22:00 и длительности 3 ч эпизод дождя переходит через полночь. Предлагаемое решение: целые равновероятные значения по замкнутому диапазону ключа конфига (час старта дождя 6..22, длительность дождя 1..3 ч, длительность инъекции 30..60 мин), старт инъекции — целая минута 0..1439, множитель инъекции — вещественный U(1.2–1.6); эпизоды — абсолютные интервалы времени, `is_rain` остаётся истинным и после полуночи, пока эпизод не закончился (розыгрыш следующего дня этого не меняет). Порядок розыгрышей внутри `advance_day` — в порядке изложения §3.6: дождь, затем инъекция; при неуспехе Bernoulli параметры эпизода не разыгрываются (розыгрыши безусловны в смысле §10.13 — не зависят от решений потребителя тарифа, а не от исхода Bernoulli).
4. **`day_index` и день недели «пятничного вечера».** `advance_day(day_index: int)` получает номер дня (приложение Б), событие же «календарное» (§3.6). Предлагаемое решение: дата дня = `engine.sim_start + day_index` суток (разбор `engine.sim_start` через `common.timeutil.from_iso`), день недели — по этой дате с нумерацией Mon=0 (§3); для эталонного старта «2026-11-02» (понедельник) это совпадает с `day_index % 7`.
