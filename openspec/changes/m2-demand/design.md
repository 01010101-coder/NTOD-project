## Goals / Non-Goals

**Goals:**

- `simulator/demand.py` с публичным контрактом ровно по приложению Б: `TripRequest`, `lambda_rate`, `spawn_requests`; внутренние детали — приватные.
- λ §3.3 дословно со всеми множителями; эластичность внутри λ; пуассоновский спавн с фиксированным порядком разыгрываний; выбор назначения `P(B | A) ∝ attract_dest(B) × exp(−path_min[A][B] / dest_decay_min)`, B ≠ A; семантика лимита ожидания §3.4.
- `tests/test_sim_demand.py` закрывает все проверки строки №2 §7: λ без факторов = `base_rate`; эластичность m=2 при α=1 режет поток ~вдвое (фиксированный rng); назначение тяготеет к `attract_dest` с затуханием по `dest_decay_min`; нулевой парк → все заказы `unfulfilled` ровно через лимит.
- Детерминизм: один переданный `rng`, порядок разыгрываний зафиксирован; никакой wall-clock (запрет §2.2 п. 3); numpy и stdlib (запрет §2.2 п. 2); комментарии/docstring на русском, идентификаторы на английском (запрет §2.2 п. 7).

**Non-Goals:**

- `env.py` (`WorldEnv`: дождь, пятница-метка, инъекции) — change `m2-env`; `demand.py` получает среду готовыми параметрами `is_rain` / `event_mult` / `price_mult` (приложение Б) и сам случайных событий не разыгрывает.
- `drivers.py` (парк, диспатч) — change `m2-drivers`; «нулевой парк» в тестах — отсутствие назначений, а не объект парка.
- Минутный цикл, агрегация, writer, CLI — change `m2-loop`; БД не трогается: `TripRequest` — внутренний объект движка, в storage пишут дикты из `m2-loop`.
- Правки `common/`, `storage/`, `config.yaml`, `simulator/city.py`, `simulator/__init__.py` (запрет §2.2 п. 1 и п. 5); новые зависимости; реэкспорты в `__init__`.

## Decisions

### 1. λ §3.3 дословно; каждый множитель берётся из строго определённого места

Составляющие λ и их источники (путаница источников — главный риск формулы):

| Множитель | Источник |
|---|---|
| `base_rate` | `cfg.demand.base_rate` |
| профиль_часа | `city.profiles[zone.archetype]`, строка по дню недели, индекс `t.hour` |
| будни/выходные | `t.weekday() < 5` → `weekday`, иначе `weekend` (proposal, вопрос 1) |
| `attract_origin` | `zone.attract_origin` |
| `population.scale` | `cfg.population.scale` |
| дождь | `cfg.weather.demand_mult` при `is_rain=True`, иначе 1.0 |
| `event_mult` | параметр; применяется по условию «для архетипа» (решение 3) |
| эластичность | `price_mult ** (−cfg.pricing.elasticity_alpha)` |

Другие ключи конфига и поля `CitySpec` λ не читает. `spawn_requests` не дублирует формулу: для каждой зоны вызывает `lambda_rate(...)` с `price_mult = price_mult_by_zone[zone.id]` — единый источник формулы. Альтернатива (повторить формулу внутри спавна ради скорости) отвергнута: расхождение двух копий формулы при правке.

### 2. Порядок разыгрываний спавна — часть контракта детерминизма (§10.1, §3.7)

Внутри `spawn_requests`: зоны по возрастанию `zone_id` (`CitySpec.zones` сортирован контрактом приложения Б); для каждой — `count = rng.poisson(λ)` (розыгрыш всегда, даже при λ=0, решение §10.9), затем для каждого из `count` пассажиров по порядку — один розыгрыш назначения и немедленное создание заказа (§3.3: «каждый пассажир сразу создаёт заказ и выбирает назначение»). Итоговый список — в порядке создания. До `m2-loop` спавн — единственный минутный потребитель `rng` (диспатч §3.5 детерминирован, среда рисует только в `advance_day` на 00:00), поэтому порядок внутри спавна фиксирует поток генератора для всего мира. Альтернатива «сначала все пуассоны, потом все назначения» меняет тот же мир при том же seed — отвергнута.

### 3. `event_mult` — значение множителя; условие «пятничный вечер для архетипа» проверяет `demand.py`

Скалярный `event_mult` на вызов (приложение Б) физически не может выразить архетип-специфичность события, если условие проверяет вызывающий. Поэтому: `demand.py` сам проверяет по конфигу и `t` активность «пятничного вечера» для архетипа зоны — `t.weekday() ∈ cfg.events.friday_evening.days`, `cfg.events.friday_evening.hours[0] ≤ t.hour ≤ cfg.events.friday_evening.hours[1]` (диапазон включительно, приложение А), `zone.archetype ∈ cfg.events.friday_evening.archetypes` — и при активности умножает λ на переданный `event_mult`; движок передаёт туда `cfg.events.friday_evening.demand_mult` (эталон 1.3). Параметр остаётся швом подмены значения, не условия; календарные розыгрыши (дождь, инъекции — случайные) `demand.py` не ведёт. Альтернатива «движок передаёт 1.0/1.3 по минуте, λ умножает как есть» несовместима со скалярной сигнатурой (разделение business/mixed vs residential в одном вызове); «пер-зонный массив события» ломает сигнатуру приложения Б — запрещено. Вопрос зафиксирован в proposal (вопрос 2); метка для агрегата (`event`, §3.8) — за `WorldEnv.event_label` (`m2-env`), свой источник календарных фактов.

### 4. Выбор назначения — нормированные веса и один вызов `rng.choice` на пассажира

Для пассажира из зоны A кандидаты — все зоны B ≠ A в порядке возрастания id (кроме A); веса `w_B = zone.attract_dest × exp(−path_min[A][B] / cfg.demand.dest_decay_min)`; выбор — один вызов `rng.choice` по массиву кандидатов с нормированными вероятностями. На эталоне `path_min ≤ 21`, `dest_decay_min = 15` — показатели в диапазоне `[exp(−1.4), exp(−1/3)]`, переполнений нет. Механизм выбора после слияния становится частью мира для данного seed (менять молча нельзя — сломает детерминизм A7); альтернатива (инверсия CDF через `rng.random()`) эквивалентна по распределению, но даёт другой поток — не выбирается лишь потому, что выбор уже надо однажды зафиксировать.

### 5. Лимит ожидания §3.4 — приватный предикат в `demand.py`; переиспользуется `m2-loop`

Заказ без назначения истекает ровно в минуту `created_at + cfg.drivers.wait_limit_min` (эталон 6; «ожидает назначения не дольше лимита», §3.4): приватная функция-предикат «истёк ли неназначенный заказ в минуту t» (`t ≥ created_at + wait_limit_min`; минуты обрабатываются циклом ровно по одному разу, поэтому «ровно в лимитную минуту»). Проверка §7 «нулевой парк → все заказы `unfulfilled` ровно через лимит» исполняется тестом напрямую на предикате: назначений нет (парк нулевой — change идёт параллельно с `m2-drivers`, объект парка не существует) → заказы не истекли в минуты `created_at + 0 … +5` и истекли в `created_at + 6`. Движок (`m2-loop`, шаг 5 цикла §3.7) переиспользует предикат (приватный импорт внутри пакета `simulator` — единый источник правила, новых публичных имён нет, A3/A12 не затронуты). Истечение — только для неназначенных: назначение «спасает» даже при долгой подаче (решение §10.3); статус `cancelled` не используется (решение §10.6); поля статусов у `TripRequest` нет — статус возникает при записи строки trips движком, предикат отвечает только на вопрос «истёк ли к моменту t, если не назначен».

### 6. Тесты: точные равенства для λ, фиксированные seed и широкие допуски для статистики

`tests/test_sim_demand.py` — только файла change'а; конфиги: эталонный `load_config("config.yaml")`, дефолты `AppConfig()` и синтетические через `AppConfig.model_validate({...})` (управляемые профили/параметры; магические числа в тестах — это параметры конфигов, не кода). Проверки строки №2 §7:

- **λ без факторов = `base_rate`** — точное равенство: эталон, residential (зона 0: `attract_origin = 1.0`), будни 16:00 (профиль 1.0), `is_rain=False`, `event_mult=1.0`, `price_mult=1.0` → `lambda_rate == 2.0`. Соседние проверки: каждый множитель формулы мультипликативен (поочерёдная активация), дождь даёт отношение `weather.demand_mult`, α=0 отключает эластичность.
- **эластичность m=2 при α=1 режет поток ~вдвое (фиксированный rng)** — один seed `np.random.default_rng`, две серии спавна на одинаковой последовательности минут (синтетический конфиг с ненулевым профилем), `price_mult_by_zone` = 1.0 против 2.0; допуск на отношение суммарных объёмов `[0.4, 0.6]` при выборке ≥ 2000 минут (σ отношения < 0.02 — запас 10σ).
- **назначение тяготеет к `attract_dest` с затуханием** — выборка ≥ 20000 заказов из одной зоны при фиксированном seed; эмпирические доли зон против нормированных весов `w_B` (допуск по каждой зоне); отдельная проверка затухания: увеличение `dest_decay_min` (например 15 → 60) увеличивает долю дальней цели с равным `attract_dest` — эмпирическое отношение долей сходится к отношению весов.
- **нулевой парк → все заказы `unfulfilled` ровно через лимит** — серия заказов в разные минуты, предикат решения 5: не истёк в `+0…+5`, истёк в `+6` (решение §10.3 — назначение спасает: заказ, помеченный назначенным до лимитной минуты, предикат не истёкшего не помечает).

Соседние проверки контракта: детерминизм спавна (два прогона одного seed попарно равны), разыгрывание при λ=0 продвигает `rng` (два последовательных спавна с λ=0 дают одинаковый последующий поток), `dest ≠ origin`, `price_multiplier` заказа = множителю зоны происхождения, неизменяемость и порядок полей `TripRequest` (приложение Б).

## Risks / Trade-offs

- [Статистические допуски (эластичность, тяготение) могут флейкнуть] → фиксированные seed'ы, большие выборки, широкие коридоры (решение 6); точные равенства там, где статистика не нужна; прогон перед сдачей.
- [Порядок разыгрываний (решения 2 и 4) расползётся с будущими changes] → порядок зафиксирован здесь и будет закреплён `test_reproducibility` `m2-loop`; правка — только через правку артефактов change'а.
- [Приватный предикат лимита — точка сцепки с `m2-loop`] → семантика закреплена спекой («нулевой парк → unfulfilled ровно через лимит», «назначение спасает»); `m2-loop` планово обязан применять правило шагом 5 (§3.7); если `m2-loop` предпочтёт иную форму — правка через `openspec-update-change`, не молча.
- [Двойственность `event_mult` (значение у движка, условие в demand)] → зафиксировано решением 3 и вопросом 2 proposal; расходится с «горбом пятницы» `m2-env` только в точке вычисления, не в наблюдаемом поведении (λ и агрегат дают тот же горб).
- [Расчёт λ на каждую зону каждую минуту — ~260 тыс. вызовов на 30 дней] → вызов лёгкий (арифметика скаляров), бюджет 60 с (§5) с запасом; векторизация пуассонов (§5) — резерв `m2-loop`, порядок разыгрываний сохраняется, формула не меняется.
