## Why

`m2-city` закрыт: канонический конфиг и `build_city` → `path_min` готовы, но заказов в мире ещё нет. Спрос — ядро симулятора M2 (§3.3–3.4 плана `docs/plan-m2-engine.md`): пуассоновский спавн по мультипликативной λ с эластичностью по тарифу создаёт заказы, выбор назначения формирует пространственную структуру потока, лимит ожидания порождает статус `unfulfilled` — без этого не работают ни диспатч (`m2-drivers`), ни минутный цикл и агрегация (`m2-loop`), ни калибровка (`m2-calibration`). Это change №2 в порядке конвейера §7 плана M2 (после `m2-city` изменения 2–4 идут параллельно).

## What Changes

- Новый `simulator/demand.py` по приложению Б плана M2 — публичный контракт ровно три имени:
  - `TripRequest` — frozen-dataclass заказа: `created_at`, `origin`, `dest`, `price_multiplier` (§3.4: заказ рождается с временем создания и множителем зоны происхождения на момент создания);
  - `lambda_rate(city, zone, t, *, is_rain, event_mult, price_mult, cfg) -> float` — мультипликативная λ §3.3 плана дословно, со всеми множителями: `base_rate × профиль_часа(архетип, час, будни/выходные) × attract_origin(зоны) × population.scale × (дождь? × rain.demand_mult) × event_mult × m(зоны, t)^(−pricing.elasticity_alpha)`; эластичность — внутри λ (×m^(−α)), а не отдельной фильтрацией пассажиров (решение §10.7 плана);
  - `spawn_requests(rng, city, t, *, is_rain, event_mult, price_mult_by_zone, cfg) -> list[TripRequest]` — пуассоновский спавн: по всем зонам в порядке возрастания `zone_id`, розыгрыш `rng.poisson(λ)` всегда, даже при λ=0 (решение §10.9 плана); каждый пассажир сразу создаёт заказ и выбирает назначение `P(B | A) ∝ attract_dest(B) × exp(−path_min[A][B] / demand.dest_decay_min)`, B ≠ A (§3.3).
- Семантика лимита ожидания §3.4: заказ ожидает назначения не дольше `drivers.wait_limit_min` (эталон 6 мин); не назначенный за лимит — `status='unfulfilled'`, `assigned_at` NULL. Публичный API `demand.py` приложением Б расширен не будет (см. вопрос 3 в Open Questions).
- Новый `tests/test_sim_demand.py` — проверки строки №2 §7 плана M2: λ без факторов = `base_rate`; эластичность m=2 при α=1 режет поток ~вдвое (фиксированный rng); назначение тяготеет к `attract_dest` с затуханием по `dest_decay_min`; нулевой парк → все заказы `unfulfilled` ровно через лимит.

## Capabilities

### New Capabilities

- `simulator-demand`: модель спроса симулятора — мультипликативная интенсивность λ §3.3 со всеми множителями (суточный профиль по архетипу, привлекательность источника, масштаб населения, дождь, событие, эластичность по тарифу), пуассоновский спавн заказов по минутам с детерминированным порядком разыгрываний, выбор назначения с притяжением к `attract_dest` и экспоненциальным затуханием по расстоянию `dest_decay_min`, лимит ожидания §3.4; публичный контракт `TripRequest`/`lambda_rate`/`spawn_requests` — приложению Б плана M2.

### Modified Capabilities

(нет — конфиг-канон и модель города уже приведены к канону change'ом `m2-city` и этим change'ом не меняются)

## Impact

- Файлы change'а — ровно список §7 стр. 2 плана M2: `simulator/demand.py`, `tests/test_sim_demand.py`. Никакие другие файлы не трогаются: `simulator/city.py`, `common/`, `storage/`, `config.yaml` остаются без изменений (запреты §2.2 плана M2: никаких новых модулей, зависимостей и параллелизма; в движке numpy и stdlib).
- Зависимость от `m2-city` (архив): `build_city` → `CitySpec` (зоны, `path_min`, профили), `AppConfig` с каноном §6 (`demand.base_rate`, `demand.dest_decay_min`, `demand.profiles`, `drivers.wait_limit_min`, `pricing.elasticity_alpha`, `weather.demand_mult`, `population.scale`).
- Параллельность (§7: изменения 2–4 после 1 параллельно): от `m2-drivers` (парк) и `m2-env` (множители среды) этот change не зависит — множители среды входят в λ готовыми параметрами `is_rain`/`event_mult`/`price_mult` (приложение Б); их вычисление — `WorldEnv` change'а `m2-env`.
- Потребители: `m2-loop` (шаг 2 минутного цикла §3.7 — спавн; шаг 5 — истечения по лимиту ожидания), `m2-drivers` (заказы как вход диспатча), гейт A12 (§11.1: импорт `TripRequest`, `lambda_rate`, `spawn_requests`).
- Гейты приёмки (§7 плана M2): `make lint` (A1) и `make test` (A2) остаются зелёными; `make accept-m2` перед сдачей прогоняется целиком, проваленными могут быть только критерии будущих changes (A3–A13, кроме проверок импорта `demand`-имён в A12).

## Open Questions

Непонятности плана, зафиксированные вопросами (§2.2 п. 8 плана M2: «непонятность — вопрос в чейндже, а не молчаливое решение своим способом»). Источник — `docs/plan-m2-engine.md`; ниже — места, где план не задаёт поведение явно, с предлагаемыми ответами. Ни один не меняет проверки строки №2 §7:

1. **Разделение будни/выходные для профиля.** Формула λ (§3.3) требует «профиль_часа(архетип, час, будни/выходные)», но план не перечисляет, какие номера дней считаются выходными. Косвенно задано: нумерация с понедельника = 0 (§3), «пятничный вечер» — дни [4, 5] = пт, сб (приложение А). Предлагаемое решение: `t.weekday() < 5` → профиль `weekday`, иначе `weekend` — единственное разбиение, совместимое с комментарием «пт, сб» приложения А. На эталонном мире влияет только на сб/вс.
2. **Состав параметра `event_mult` λ и где проверяется условие «для архетипа».** Строка формулы §3.3 — «(пятничный вечер **для архетипа?** × events.friday_evening.demand_mult)», но сигнатуры приложения Б передают `event_mult` готовым **скаляром** на вызов `spawn_requests` (один вызов на минуту сразу для всех зон) — скаляр не выражает архетип-специфичность события, поэтому проверку условия «пятничный вечер для архетипа» (день ∈ `events.friday_evening.days`, час ∈ `events.friday_evening.hours` включительно, архетип ∈ `events.friday_evening.archetypes`) обязан выполнять сам `demand.py` по конфигу и `t`. Предлагаемое решение: `demand.py` проверяет условие по `cfg.events.friday_evening` и при активности умножает λ зоны на переданный `event_mult`; движок передаёт в `event_mult` значение `events.friday_evening.demand_mult` конфига (эталон: 1.3) — параметр остаётся точкой подмены значения, а не условия. Дождь в `event_mult` не входит (свой булев параметр `is_rain` и множитель `weather.demand_mult`). Альтернатива «движок считает 1.0/1.3 по минуте, demand умножает как есть» отвергнута: не выражает разделение business/mixed vs residential одним вызовом без ломки сигнатуры приложения Б. Метка для агрегата (`event`, §3.8) остаётся за `WorldEnv.event_label` change'а `m2-env` — там свой источник календарных фактов.
3. **Где живёт механика лимита ожидания.** Проверка строки №2 §7 («нулевой парк → все заказы `unfulfilled` ровно через лимит») требует наблюдаемого истечения, но: у `TripRequest` (приложение Б) нет поля статуса, а сам шаг истечений — шаг 5 минутного цикла §3.7, т. е. движок change'а `m2-loop`, который идёт после параллельной тройки 2–4. Предлагаемое решение: семантика §3.4 («не назначенный за лимит → unfulfilled ровно в `created_at + drivers.wait_limit_min`») реализуется в `simulator/demand.py` внутренней (приватной) частью — приложение Б разрешает «внутренние детали реализации (приватные функции, поля) — на усмотрение исполнителя», новых публичных имён не появляется; тест `tests/test_sim_demand.py` прогоняет её с нулевым парком (назначение невозможно) и сверяет моменты истечения с лимитом. Альтернатива — мини-цикл только в тесте с реализацией правила в самом тесте — отвергается как проверка не кода change'а; окончательное место вызова (движок) фиксирует `m2-loop`.
