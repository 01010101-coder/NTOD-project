## Goals / Non-Goals

**Goals:**

- `simulator/drivers.py`: публичный контракт приложения Б дословно — `DriverState`, `Driver`, `Fleet` (`__init__`, `nearest_free`, `assign`, `tick`, `free_by_zone`, `busy_by_zone`); внутренние детали (приватные функции/поля) — на усмотрение исполнителя, дополнительных модулей нет.
- Детерминированный старт парка: водитель `i` в зоне `i mod Z`, без rng (§10.14, §3.5).
- Диспатч: ближайший свободный по времени подачи, тай-брейк — меньший `driver_id` (§3.5); нет свободных → `None`.
- Длительности: `ceil(путь × k)`, минимум 1 минута, подача = поездка (§3.2, §10.5); проверка строки №3 §7 «длительность = `ceil(путь × k)`» закрывается в этом change'е.
- Движение: тики счётчиков, посадка `to_pickup → on_trip`, высадка `on_trip → free` в зоне назначения заказа (§3.5, §3.7 шаг 4).
- `tests/test_sim_drivers.py` закрывает все проверки строки №3 §7: ближайший водитель получает заказ; при равенстве — меньший id; после dropoff водитель free в dest; длительность = `ceil(путь × k)`; старт парка: водитель i в зоне i mod Z.

**Non-Goals:**

- Выбор ожидающих заказов по `(created_at, внутренний_id)`, лимит ожидания `drivers.wait_limit_min`, «спасение» диспатчем (§3.4, §3.5, §10.3) — сторона движка, change `m2-loop`.
- Дождь и множитель `k` (`rain.travel_mult`), прочие события — `simulator/env.py`, change `m2-env` (№4); здесь `k` — параметр формулы длительности.
- Спавн заказов, λ, объект заказа `TripRequest` — `simulator/demand.py`, change `m2-demand` (№2); `Fleet` получает только `trip_id: int` и не импортирует `demand`/`env`.
- Минутный цикл, агрегация §3.8, CLI, writer — `m2-loop`; снапшоты `free_by_zone`/`busy_by_zone` только поставляют данные.
- Правки `common/`, `storage/`, `config.yaml`, `simulator/city.py` (запрет §2.2 п. 5); новые зависимости (запрет §2.2 п. 2).

## Decisions

### 1. Публичный контракт — приложение Б дословно

```python
# drivers.py
class DriverState(enum.Enum):
    FREE = "free"
    TO_PICKUP = "to_pickup"
    ON_TRIP = "on_trip"

@dataclass
class Driver:
    id: int
    zone: int
    state: DriverState
    trip_id: int | None      # внутренний id заказа
    remaining_min: int       # до посадки (TO_PICKUP) или высадки (ON_TRIP)

class Fleet:
    def __init__(self, count: int, zone_count: int) -> None: ...   # водитель i → зона i mod Z
    def nearest_free(self, zone: int, path_row: np.ndarray) -> int | None: ...  # тай-брейк: меньший id
    def assign(self, driver_id: int, trip_id: int, pickup_min: int) -> None: ...
    def tick(self) -> list[tuple[int, int]]: ...   # высадки этой минуты: (driver_id, зона_высадки)
    def free_by_zone(self) -> np.ndarray: ...      # counts
    def busy_by_zone(self) -> np.ndarray: ...      # counts
```

Имена, сигнатуры, типы и комментарии параметров — как в приложении Б; `Driver` — изменяемый dataclass (без `frozen`), `DriverState` — строковый enum. Чтение сигнатуры `nearest_free(zone, path_row)`: `zone` — зона посадки, `path_row` — строка `path_min[zone]` (единственная осмысленная строка для всех водителей сразу); сам `zone` в выборе не участвует помимо `path_row` — время подачи водителя есть `path_row[driver.zone]`. Зависимости модуля: `enum`, `dataclasses`, `math`, `numpy` — только numpy и stdlib (запрет §2.2 п. 2).

### 2. §3.5 плана — дословно, поведение диспатча и состояний

> «Парк: `drivers.count` (эталон 200). Старт — детерминированно без rng: водитель `i` в зоне `i mod Z`. Состояния: `free(зона)`, `to_pickup(заказ, осталось_мин)`, `on_trip(заказ, осталось_мин)`.
> Диспатч раз в минуту: ожидающие заказы по возрастанию `(created_at, внутренний_id)`; каждому — свободный водитель с минимальным временем подачи, при равенстве — меньший `driver_id`. После высадки водитель свободен в зоне назначения (отсюда дрейф машин в привлекательные зоны — главный источник локальных дефицитов).»

Часть «ожидающие заказы по возрастанию…» — сторона движка (`m2-loop`); `Fleet` отвечает за «каждому — свободный водитель с минимальным временем подачи, при равенстве — меньший `driver_id`» через `nearest_free` + `assign`. Альтернатива «словарь зон → списки водителей» отвергнута: усложняет тай-брейк и подсчёты без выигрыша на парке из 200; хранение — плоский список `Driver` по возрастанию `id`, все итерации по возрастанию `id` (§3.7: «Никаких итераций по множествам/словарям без сортировки»).

### 3. §3.2 и §10.5 — формула длительности дословно

> §3.2: «Время поездки = `ceil(path_min[A][B] × k_дождь)`, минимум 1 минута; время подачи = так же для `path_min[зона водителя][зона посадки]`.»
> §10.5: «Длительности: `ceil`, минимум 1 минута; подача считается так же, как поездка.»

Функция уровня модуля `travel_minutes(path_min: int, k: float) -> int = max(1, ceil(path_min × k))`, `math.ceil`; вызывается для подачи (движком при диспатче, результат передаётся в `assign`) и для поездки (движком при назначении — решение 6). Имя функции — вопрос 4 в proposal.md (план функцию не называет; предлагаемое `travel_minutes`). Минимум 1 минута покрывает и подачу в свою зону (`path_min = 0`). Альтернатива «формула только в движке» отвергнута: проверка строки №3 §7 «длительность = `ceil(путь × k)`» относится к этому change'у, файлы которого — `drivers.py` и его тесты.

### 4. Старт парка и счётчики по зонам

`__init__(count, zone_count)`: список водителей `id = 0..count-1`, зона `i mod zone_count`, `state = FREE`, `trip_id = None`, `remaining_min = 0`; rng не создается и не принимается (§10.14: «Старт парка детерминирован без rng: водитель `i` стартует в зоне `i mod Z`»). `free_by_zone()`/`busy_by_zone()` — `np.zeros(zone_count, dtype=int)` + подсчёт по `Driver.zone` (снапшот под §3.8). Зона занятого водителя — вопрос 1 в proposal.md: принято предлагаемое решение «зона меняется ровно один раз — при высадке»; до высадки занятый числится в зоне, где был свободен.

### 5. Диспатч: `nearest_free` — детерминированный минимум с тай-брейком

Один проход по водителям в порядке возрастания `id` среди `state is FREE`; кандидат лучше, если `path_row[d.zone]` строго меньше текущего минимума (строгое `<` сохраняет первого при равенстве → меньший `id`, как требует §3.5). Свободных нет → `None`. Сложность O(count), для эталонных 200 водителей и диспатча раз в минуту — заведомо в бюджете производительности §5 (30 дней ≤ 60 с). Альтернатива `min(...)` по генератору с ключом `(path_row[d.zone], d.id)` эквивалентна; выбор способа — за исполнителем, контракт — только результат.

### 6. Машина состояний `assign`/`tick` и внутренний канал сведений о поездке

`assign(driver_id, trip_id, pickup_min)`: `state = TO_PICKUP`, `trip_id`, `remaining_min = pickup_min`. `tick()` (одна сим-минута, §3.7 шаг 4: «счётчики `to_pickup`/`on_trip` тикают; происходят посадки и высадки; водители меняют состояния и зону»): один проход по занятым по возрастанию `id`, `remaining_min -= 1`; исчерпание у `TO_PICKUP` → `ON_TRIP` (посадка), исчерпание у `ON_TRIP` → `FREE`, `zone = зона назначения заказа`, `trip_id = None`, пара `(driver_id, зона_высадки)` добавляется в результат; список высадок — по возрастанию `driver_id`.

Назначенный в текущей минуте водитель тикает в шаге 4 той же минуты — буквальное чтение §3.7 (вопрос 2 в proposal.md); следствие: посадка происходит в минуту `T + pickup_min − 1` при назначении в минуту `T`. Правило «минимум 1 минута» (§10.5) гарантирует, что переходы не сцепляются: у только что перешедшего в `ON_TRIP` счётчик ≥ 1, и в том же тике он не уменьшается второй раз — переход ровно один за тик.

Канал сведений о поездке (вопрос 3 в proposal.md): сигнатуры приложения Б не несут ни зону назначения заказа (а `tick()` обязан вернуть `(driver_id, зона_высадки)`), ни длительность поездки (нужна как `remaining_min` в `ON_TRIP`). Приватное поле `Fleet` — план поездки на водителя `(dest, trip_min)` — заполняется движком (`m2-loop`) при назначении приватным методом, например `_plan_trip(driver_id, dest, trip_min)`, сразу после `assign` — приложение Б: «внутренние детали реализации (приватные функции, поля) — на усмотрение исполнителя»; публичные сигнатуры Б и список полей `Driver` (решение 1: хранение — словарь в `Fleet`, не поля водителя) не расширяются. До заполнения дефолт плана поездки — `None`, и высадка невозможна; движок всегда заполняет план в шаге диспатча §3.7, поэтому недозаполнение — ошибка использования, а не ветка логики. Альтернатива — правка приложения Б (`assign(..., dest, trip_min)` или поля в `Driver`): допустима только вместе с правкой плана, владельцу плана.

### 7. Применимые зафиксированные решения §10 плана M2 (дословно, в части этого change'а)

- **§10.1.** «Порядок шагов цикла и правила тай-брейков — часть контракта детерминизма; их изменение меняет мир (другая история при том же seed)» → тай-брейк диспатча и порядок высадок зафиксированы в спеке и не меняются.
- **§10.3.** «Диспатч "спасает" от истечения даже при долгой подаче; истечение — только для неназначенных» → сторона движка; `nearest_free`/`assign` не знают про лимит ожидания.
- **§10.5.** «Длительности: `ceil`, минимум 1 минута; подача считается так же, как поездка» → решение 3.
- **§10.9.** «Один `numpy.random.Generator`; разыгрывания всегда для всех зон…» → в `drivers.py` разыгрываний нет вовсе: модуль не принимает и не создаёт rng (сильнее, чем требуется).
- **§10.11.** «Внутренние id заказов — счётчик движка с 1 в порядке создания (нужен диспатчу для тай-брейков)» → `Fleet` получает `trip_id` параметром и сам идентификаторы не порождает.
- **§10.14.** «Старт парка детерминирован без rng: водитель `i` стартует в зоне `i mod Z`» → решение 4.
- **§10.6.** «Статус `cancelled` не используется» → `Fleet` статусов заказов не знает вовсе.

### 8. Тесты: `tests/test_sim_drivers.py` против строки №3 §7

Проверки §7 стр. 3 закрываются так (сценарии спеки `simulator-drivers`):

| Проверка §7 | Тест |
|---|---|
| ближайший водитель получает заказ | `nearest_free` на синтетической `path_row` и на эталонной матрице `build_city(load_config('config.yaml'))`: побеждает минимум времени подачи |
| при равенстве — меньший id | два водителя с равным временем подачи (одна зона; симметричные зоны эталонного графа) → меньший `id` |
| после dropoff водитель free в dest | полный цикл `assign` → тики → высадка: `free` в зоне назначения, `trip_id = None`, пара в возврате `tick` |
| длительность = `ceil(путь × k)` | `travel_minutes`: 9×1.4→13, 9×1.0→9, 0×k→1 |
| старт парка: водитель i в зоне i mod Z | `Fleet(200, 6)`, `Fleet(3, 6)`; счётчики `free_by_zone` = `[34, 34, 33, 33, 33, 33]` |

Дополнительно: отсутствие свободных → `None`; занятые не диспатчатся; счётчики вдоль цикла и их сумма; порядок высадок по возрастанию `id`; несцепленность переходов; отсутствие случайности (повторные вызовы дают тот же результат без seed). Тесты детерминированы, rng не используется; эталонные значения `path_min` берутся из `build_city(load_config('config.yaml'))` (зависимость от закрытого `m2-city`), синтетические строки `path_row` — `np.array` фиксированных значений.

### 9. Применимые запреты §2.2 плана M2 (контроль исполнителя)

1. **Не изобретать структуру.** Только файлы приложения Б. Никаких абстрактных базовых классов, плагинов, шин событий, «стратегий», фабрик; никаких дополнительных модулей и подпакетов → один новый файл `simulator/drivers.py`.
2. **Не добавлять зависимости.** В движке — numpy и stdlib. pandas разрешён только в `calibrate.py`; matplotlib — только там же → импорты `drivers.py`: `enum`, `dataclasses`, `math`, `numpy`.
3. **Никакого параллелизма и wall-clock времени.** Без asyncio, потоков, `datetime.now()`/`time.*` внутри симуляции. Единственное время — сим-часы (§3), передаваемые явно → `drivers.py` времени не знает вовсе: движение считается в целых минутах.
4. **Переиспользовать M1 по именам**, не создавая дублей: `common.config.load_config`, `common.timeutil.{to_iso, from_iso, add_minutes, bucket5}`, `storage.db.{connect, transaction}`, `storage.repo.{insert_trips, insert_zone_metrics}`, `storage.csv_export.export_table` → тесты грузят эталон через `common.config.load_config`; дублей `common/`/`storage/` нет.
5. **Конфиг-модели правятся один раз** и только как описано в §6 (change `m2-city`). Схема SQLite не меняется; `common/` и `storage/` кроме `common/config.py` не трогаются → в этом change'е конфиг-модели не трогаются вовсе.
6. **Магических чисел в коде нет**: все параметры мира — из конфига; сами значения мира (зоны, дороги, профили) — только в `config.yaml` → `drivers.py` констант мира не содержит; литералы в тестах — это данные тестов, не мира.
7. **Идентификаторы на английском, комментарии и docstring на русском** (правило `openspec/config.yaml`).
8. Непонятность в плане — вопрос в чейндже (раздел Open Questions в proposal.md), а не молчаливое решение своим способом.

## Risks / Trade-offs

- [Вопросы 1–2 proposal.md меняют наблюдаемые данные (`busy_drivers` агрегата, `pickup_at`/`dropoff_at`)] → в спеке зафиксированы предлагаемые ответы (буквальное чтение §3.5/§3.7); смена решения владельцем плана — локальная правка `drivers.py` и тестов, контракт приложения Б не затрагивает.
- [Приватный канал сведений о поездке (решение 6: `dest` + длительность) — движок вызывает приватный метод `Fleet`] → соответствует оговорке приложения Б «внутренние детали — на усмотрение»; альтернатива (правка публичной сигнатуры `assign` или полей `Driver`) требует правки плана и зафиксирована вопросом 3.
- [`nearest_free` — O(count) на каждый ожидающий заказ каждую минуту] → 200 водителей × ≤10–15 заказов/мин × 43 200 минут ≈ 10⁸ простых операций — в пределах бюджета §5 (≤ 60 с); при необходимости векторизация не меняет порядок сравнений (§5 разрешает векторизовать, «не меняя порядок разыгрываний»).
- [Тесты зависят от закрытого `m2-city` (`build_city`, эталонный конфиг)] → зависимость уже в репо; синтетические `path_row` покрывают диспатч независимо от города, эталонный конфиг — один интеграционный слой.
- [Линтер на новый файл] → файл пишется сразу с русскими docstring и в стиле ruff-конфига репо; контроль — `make lint` в последней группе задач.

## Migration Plan

Change добавляет два новых файла и ничего не переписывает: `simulator/drivers.py`, `tests/test_sim_drivers.py`. Откат — удаление файлов (git checkout ветки); промежуточных состояний нет. Обратной миграции не требует: `Fleet` начинает использоваться движком только в `m2-loop`.

## Open Questions

Четыре вопроса зафиксированы в proposal.md (раздел Open Questions) с предлагаемыми ответами; решения 3–6 design.md принимают предлагаемые ответы до ответа владельца плана: (1) зона занятого водителя — меняется только при высадке; (2) назначенный в текущей минуте водитель тикает в той же минуте; (3) канал сведений о поездке (зона назначения и длительность) — приватное поле `Fleet`; (4) имя функции длительности — `travel_minutes`. Вопросы 1–2 меняют наблюдаемые данные при альтернативном ответе, 3–4 — нет; ни один не блокирует реализацию строки №3 §7.
