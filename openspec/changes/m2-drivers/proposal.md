## Why

Конвейер вехи M2 (`docs/plan-m2-engine.md` §7): после `m2-city` (канонический конфиг + `build_city` → `path_min`) изменения 2–4 идут параллельно. Change №3 `m2-drivers` даёт движку парк водителей: детерминированный старт, диспатч «ближайший свободный с тай-брейком по id», движение с посадкой и высадкой. Без него минутный цикл (§3.7) не может ни назначать заказы, ни перемещать машины, а «дрейф машин в привлекательные зоны» (§3.5) — главный источник локальных дефицитов, которые потом калибрует `m2-calibration`.

## What Changes

- Новый `simulator/drivers.py` по приложению Б плана M2 (публичный контракт дословно): `DriverState` — enum `FREE`/`TO_PICKUP`/`ON_TRIP`; `Driver` — dataclass `id, zone, state, trip_id, remaining_min`; `Fleet` — `__init__(count, zone_count)`, `nearest_free(zone, path_row) -> int | None`, `assign(driver_id, trip_id, pickup_min)`, `tick() -> list[tuple[int, int]]` (высадки минуты), `free_by_zone()`, `busy_by_zone()`.
- Состояния водителей (§3.5): `free(зона)`, `to_pickup(заказ, осталось_мин)`, `on_trip(заказ, осталось_мин)`.
- Старт парка детерминирован без rng (§10.14, §3.5): водитель `i` стартует в зоне `i mod Z`.
- Диспатч (§3.5): свободный водитель с минимальным временем подачи (`path_row[driver.zone]`), при равенстве — меньший `driver_id`; свободных нет → `None`.
- Длительности (§3.2, §10.5): `ceil(путь × k)`, минимум 1 минута; подача считается так же, как поездка.
- Движение и высадка (§3.7 шаг 4): счётчики `remaining_min` тикают; исчерпание подачи → посадка (`to_pickup → on_trip`); исчерпание поездки → высадка, водитель свободен в зоне назначения заказа (§3.5).
- Новый `tests/test_sim_drivers.py` — все проверки строки №3 §7: ближайший водитель получает заказ; при равенстве — меньший id; после dropoff водитель free в dest; длительность = `ceil(путь × k)`; старт парка: водитель i в зоне i mod Z.
- rng в модуле не используется вовсе: старт, диспатч и движение детерминированы (§10.9 соблюдается тривиально — разыгрываний в модуле нет).

## Impact

- Файлы change'а — ровно список §7 стр. 3 плана M2: `simulator/drivers.py`, `tests/test_sim_drivers.py`. Остальные файлы (`simulator/city.py`, `common/`, `storage/`, `config.yaml`) не трогаются (запреты §2.2 п. 1, 5 плана M2).
- Зависит от `m2-city` (закрыт): тесты строят `path_min` через `build_city` из `simulator.city` и эталонный `config.yaml`; сам `drivers.py` от `city.py` не зависит (матрица приходит параметром `path_row`) и не импортирует `demand`/`env` — ветки 2–4 §7 остаются независимыми.
- Разблокирует `m2-loop`: движок вызывает `nearest_free`/`assign`/`tick` в шагах 3–4 цикла §3.7, агрегация §3.8 берёт снапшоты `free_by_zone`/`busy_by_zone`; выбор ожидающих заказов по `(created_at, внутренний_id)`, лимит ожидания и «спасение» диспатчем (§3.4, §3.5, §10.3) — сторона движка, в этот change не входят.
- Зависимости: numpy и stdlib (`enum`, `dataclasses`, `math`) — новых зависимостей нет (запрет §2.2 п. 2); параллелизм и wall-clock не используются (запрет §2.2 п. 3 — в модуле нет даже сим-времени: движение считается в минутах).
- Гейты §7: `make lint && make test` зелёные (правило `openspec/config.yaml`); критерии приёмки A1 (`make lint`) и A2 (`make test`) остаются зелёными; полный `make accept-m2` (A1–A13) — после `m2-loop`, который ставит скрипт приёмки.

## Open Questions

Непонятности плана, зафиксированные вопросами (§2.2 п. 8 плана M2: «Непонятность в плане — вопрос в чейндже, а не молчаливое решение своим способом»). Наблюдаемое поведение строки №3 §7 план задаёт полностью; ниже — места, где приложение Б/§3.5/§3.7 не задают проводку явно, с предлагаемыми ответами. До ответа владельца плана реализация и спека следуют предлагаемым ответам (design.md, решения 5–7):

1. **Зона занятого водителя в `Driver.zone` — влияет на `busy_by_zone` → `busy_drivers` агрегата §3.8.** §3.5 фиксирует только высадку: «После высадки водитель свободен в зоне назначения». Про зону в состояниях `to_pickup`/`on_trip` план не говорит. Предлагаемое решение: зона меняется ровно один раз — при высадке; занятый водитель числится в зоне, где был свободен на момент назначения. Альтернатива — обновлять зону ещё и при посадке (в зону заказа). Единственный вопрос, меняющий наблюдаемые данные агрегата, — выносится владельцу плана.
2. **Тикает ли водитель, назначенный в текущей минуте, в шаге 4 «Движение» той же минуты (§3.7).** Буквальное чтение («счётчики `to_pickup`/`on_trip` тикают») даёт: назначенный в минуту T с подачей N минут получает посадку в T+N−1; альтернатива — пропуск свежих назначений в текущем тике даёт посадку ровно через N минут. Влияет на наблюдаемые `pickup_at`/`dropoff_at` в БД. Предлагаемое решение: буквальное чтение §3.7 — все занятые тикают в каждом тике; правило «минимум 1 минута» (§10.5) гарантирует, что посадка и высадка не сцепляются в одном тике.
3. **Канал сведений о поездке: зона назначения и длительность.** Приложение Б не сообщает `Fleet` ни зону назначения заказа (а `tick()` должен вернуть `(driver_id, зона_высадки)` — §3.5: «водитель свободен в зоне назначения»), ни длительность поездки (нужна как `remaining_min` в `on_trip`): `assign(driver_id, trip_id, pickup_min)` несёт только время подачи, конструктор — только `(count, zone_count)`, `tick()` без параметров, в полях `Driver` места нет. Предлагаемое решение: внутреннее (приватное) поле `Fleet` — план поездки на водителя `(зона_назначения, длительность)`, заполняемый движком при назначении через приватный метод — приложение Б: «внутренние детали реализации (приватные функции, поля) — на усмотрение исполнителя»; публичные сигнатуры Б и список полей `Driver` не расширяются. Альтернатива — правка приложения Б (`assign(..., dest, trip_min)` или поля в `Driver`), допустимая только вместе с правкой плана. На поведение §7 стр. 3 не влияет.
4. **Имя и размещение формулы длительности.** Проверка §7 стр. 3 «длительность = `ceil(путь × k)`» относится к этому change'у, но приложение Б функцию не называет. Предлагаемое решение: функция уровня модуля в `drivers.py`, например `travel_minutes(path_min: int, k: float) -> int` — «внутренние детали реализации — на усмотрение исполнителя»; движок (`m2-loop`) сможет вызывать её и для подачи, и для поездки (§10.5: «подача считается так же, как поездка»). Имя планом не задано — предлагаемое `travel_minutes`.
