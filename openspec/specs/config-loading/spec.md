# config-loading Specification

## Purpose
Конфигурация проекта «taxi-demand-forecast»: все параметры (seed, хранилище, город, население, спрос, водители, погода, события, прайсинг, движок — скелет §5 плана M1) описаны pydantic-моделями с дефолтами и запретом неизвестных ключей и загружаются из YAML-файла; эталонный `config.yaml` лежит в репо. Проверяется тестами `tests/test_config.py`.

## Requirements

### Requirement: Корневая модель со всеми секциями скелета

Корневая модель конфигурации SHALL содержать все секции скелета конфига плана M1 §5: `seed`, `storage`, `city`, `population`, `demand`, `drivers`, `weather`, `events`, `pricing`, `engine`. Значение `seed` SHALL быть читаемым целым числом.

#### Scenario: Все секции скелета присутствуют

- **WHEN** конфигурация загружена (из дефолтов или из файла)
- **THEN** доступны все десять секций: `seed`, `storage`, `city`, `population`, `demand`, `drivers`, `weather`, `events`, `pricing`, `engine`

#### Scenario: Seed читается

- **WHEN** в конфигурации задан `seed` (в файле или дефолтом)
- **THEN** значение читается как целое число и совпадает с заданным (например, `42` из скелета §5)

### Requirement: Дефолты у каждой секции

Каждая секция конфигурации SHALL иметь полные значения по умолчанию; конфигурация SHALL загружаться без файла и из файла, задающего лишь часть секций (правило «старые конфиги грузятся после добавления новых секций»). После правки под канон M2 (§6 плана `docs/plan-m2-engine.md`) дефолты моделей SHALL быть равны каноническим значениям приложения А этого плана: пустой конфиг грузится и валиден.

#### Scenario: Конфиг целиком из дефолтов

- **WHEN** конфигурация создаётся без внешнего источника (ни одного значения из файла)
- **THEN** все секции заполнены дефолтами и валидны: `seed = 42`, `storage.db_path = "data/taxi.db"`, `city.zones` — 6 зон приложения А, `city.roads` — 7 дорог приложения А, `demand.base_rate = 2.0` и `demand.profiles` — 4 архетипа с профилями 24×2 приложения А, `drivers.count = 200`, `weather.rain_day_chance = 0.15`, `events.friday_evening.days = [4, 5]`, `pricing.base_boarding = 100.0`, `pricing.per_min_rub = 12.0`, `engine.sim_start = "2026-11-02"` — то есть все значения соответствуют канону §6 и приложению А плана M2

#### Scenario: Частичный конфиг дозаполняется дефолтами

- **WHEN** YAML-файл задаёт только часть секций (например, только `seed`)
- **THEN** конфигурация загружается успешно; незаданные секции принимают дефолты, заданная секция принимает значение из файла

### Requirement: Запрет неизвестных ключей

Неизвестный ключ в конфигурации SHALL отклоняться с понятной ошибкой, называющей путь до неверного ключа (секция и ключ); конфигурация при этом не загружается. Молчаливое игнорирование опечаток недопустимо.

#### Scenario: Неизвестный ключ в корне

- **WHEN** YAML-файл содержит неизвестный ключ верхнего уровня (например, `sied` вместо `seed`)
- **THEN** загрузка завершается ошибкой, в сообщении которой указан неверный ключ верхнего уровня; конфигурация не создана

#### Scenario: Неизвестный ключ внутри секции

- **WHEN** YAML-файл содержит неизвестный ключ внутри известной секции (например, `drivers.coun` вместо `drivers.count`)
- **THEN** загрузка завершается ошибкой, в сообщении которой указан путь до неверного ключа (секция `drivers`, ключ `coun`); конфигурация не создана

### Requirement: Загрузка конфигурации из YAML-файла

Библиотека SHALL предоставлять загрузку конфигурации по пути к YAML-файлу: файл разбирается, содержимое валидируется корневой моделью, результат — валидный объект конфигурации. Эталонный `config.yaml` в корне репо SHALL быть валидным конфигом проекта, переписанным целиком под приложение А плана `docs/plan-m2-engine.md` (канон §6). Значение YAML-файла, не являющееся отображением секций (список, скаляр), SHALL отклоняться с понятной ошибкой.

#### Scenario: Эталонный config.yaml валиден

- **WHEN** конфигурация загружается из эталонного `config.yaml` в корне репозитория
- **THEN** загрузка успешна и значения соответствуют канону §6: 6 зон, 7 дорог, `base_rate > 0`, 4 архетипа (`residential`, `business`, `airport`, `mixed`) с профилями 24×2, `engine.sim_start = "2026-11-02"`, множители дождя `demand_mult > 1` и `travel_mult > 1`, `pricing.surge_injection.day_chance ∈ (0, 1]`; загруженный конфиг равен конфигурации целиком из дефолтов

#### Scenario: YAML не словарём отклоняется

- **WHEN** YAML-файл содержит список или скаляр вместо отображения секций
- **THEN** загрузка завершается понятной ошибкой (не молчаливым успехом и не внутренним исключением без объяснения); конфигурация не создана

### Requirement: Канонические модели секций M2

Конфиг-модели SHALL соответствовать канону §6 плана `docs/plan-m2-engine.md` (таблица замен против скелета M1; правка выполняется один раз, в этом change'е): `ZoneCfg` содержит `id`, `name`, `archetype`, `attract_origin`, `attract_dest` и вложенное `map:{x, y}`; `DemandCfg` содержит `base_rate` и жёсткую структуру `profiles` — «архетип → `{weekday: [24 float], weekend: [24 float]}`»; `WeatherCfg` содержит `rain_day_chance`, `episode_start_h`, `episode_duration_h`, `demand_mult`, `travel_mult`; `events.friday_evening` содержит `days`, `hours` (диапазон включительно), `archetypes`, `demand_mult` — без флага `enabled`; `pricing.surge_injection` содержит `day_chance`, `duration_min`, `multiplier`; `PricingCfg` содержит `base_boarding`, `per_min_rub`; `EngineCfg` содержит `sim_start`. `RoadCfg` (`from_zone`, `to_zone`, `minutes`) SHALL остаться без изменений (форма M1 сохранена осознанно). Ключи скелета M1, удалённые каноном (`attractiveness`, `x`, `y` на верхнем уровне зоны, `rain_chance_per_day`, `episode_duration_min`, `request_multiplier`, `driver_multiplier`, `enabled` в `friday_evening` и `surge_injection`, календарные `days`/`hours` инъекций), SHALL отклоняться как неизвестные. Обратная совместимость со старыми конфигами не требуется (§6: внешних конфигов, кроме эталонного в репо, не существует).

#### Scenario: Канонические ключи валидируются

- **WHEN** конфигурация содержит канонические ключи M2 (`attract_origin`, `attract_dest`, `map` у зоны; `base_rate`; `rain_day_chance`, `episode_start_h`, `episode_duration_h`, `demand_mult`, `travel_mult`; `days`, `hours`, `archetypes`, `demand_mult` пятничного вечера; `day_chance`, `duration_min`, `multiplier` инъекций; `base_boarding`, `per_min_rub`; `sim_start`)
- **THEN** конфигурация загружается успешно и все значения читаются по соответствующим полям моделей

#### Scenario: Удалённые ключи скелета M1 отклоняются

- **WHEN** конфигурация содержит ключ скелета M1, удалённый каноном §6 (например, `attractiveness` или `x` у зоны, `driver_multiplier` в погоде, `enabled` в `friday_evening` или в `surge_injection`)
- **THEN** загрузка завершается ошибкой с путём до неверного ключа; конфигурация не создана

#### Scenario: Жёсткая структура профилей

- **WHEN** конфигурация задаёт `demand.profiles` с архетипами в виде `{weekday: [...], weekend: [...]}` (списки чисел) — как в приложении А
- **THEN** конфигурация загружается успешно, профили читаются как отображение «архетип → `{weekday, weekend}`»

#### Scenario: Лишний ключ внутри профиля отклоняется

- **WHEN** профиль архетипа в `demand.profiles` содержит ключ вне `{weekday, weekend}` (например, `holidays`)
- **THEN** загрузка завершается ошибкой с путём до неверного ключа; конфигурация не создана

### Requirement: Секция отклика предложения drivers.reposition

Модель секции `drivers` SHALL содержать вложенную подсекцию `reposition` с полями и дефолтами:

| поле | тип | дефолт |
|---|---|---|
| `enabled` | bool | `false` |
| `every_min` | int ≥ 1 | `5` |
| `min_gain` | float > 0 | `0.10` |
| `sensitivity` | float > 0 | `1.0` |
| `max_share` | float в (0, 1] | `0.3` |
| `max_reach_min` | int ≥ 1 | `12` |

Конфиг без подсекции `reposition` и конфиг с частью полей SHALL загружаться, недостающие поля берутся из дефолтов. Неизвестные ключи внутри `reposition` SHALL отклоняться с путём до ключа. Значения вне допустимых диапазонов SHALL отклоняться ошибкой валидации. Эталонный `config.yaml` SHALL содержать подсекцию со значениями, равными дефолтам, в том числе `enabled: false`.

#### Scenario: Старый конфиг без подсекции

- **WHEN** загружается конфиг, где `drivers` задан как `{count: 380, wait_limit_min: 6}`
- **THEN** загрузка успешна, `drivers.reposition.enabled` равно `false`, остальные поля равны дефолтам

#### Scenario: Частичная подсекция

- **WHEN** загружается конфиг с `drivers.reposition: {enabled: true, max_share: 0.5}`
- **THEN** `enabled` равно `true`, `max_share` равно `0.5`, `every_min` равно `5`, `min_gain` равно `0.10`

#### Scenario: Неизвестный ключ отклоняется

- **WHEN** конфиг содержит `drivers.reposition.max_shar`
- **THEN** загрузка завершается ошибкой с путём `drivers.reposition.max_shar`

#### Scenario: Недопустимое значение отклоняется

- **WHEN** конфиг содержит `drivers.reposition.max_share: 1.5` или `drivers.reposition.every_min: 0`
- **THEN** загрузка завершается ошибкой валидации, конфигурация не создана

### Requirement: Секция диспатча drivers.dispatch

Модель секции `drivers` SHALL содержать вложенную подсекцию `dispatch` с полями и дефолтами:

| поле | тип | дефолт | смысл |
|---|---|---|---|
| `max_pickup_min` | int ≥ 1 или `null` | `null` | радиус поиска: максимальная длительность подачи в минутах; `null` — без ограничения |
| `cancel_grace_min` | int ≥ 0 | `5` | подача, которую пассажир терпит без риска отказа, минут |
| `cancel_prob_per_min` | float ≥ 0 | `0.0` | прирост вероятности отказа за каждую минуту подачи сверх `cancel_grace_min`; `0.0` — отказов нет |
| `cancel_max_prob` | float в [0, 1] | `0.9` | потолок вероятности отказа |

Конфиг без подсекции `dispatch` и конфиг с частью полей SHALL загружаться, недостающие поля берутся из дефолтов. Неизвестные ключи внутри `dispatch` SHALL отклоняться с путём до ключа. Значения вне допустимых диапазонов SHALL отклоняться ошибкой валидации. Эталонный `config.yaml` SHALL содержать подсекцию со значениями, равными дефолтам (`max_pickup_min: null`, `cancel_prob_per_min: 0.0`).

#### Scenario: Старый конфиг без подсекции

- **WHEN** загружается конфиг, где `drivers` задан как `{count: 380, wait_limit_min: 6}`
- **THEN** загрузка успешна, `drivers.dispatch.max_pickup_min` равно `None`, `drivers.dispatch.cancel_prob_per_min` равно `0.0`, остальные поля равны дефолтам

#### Scenario: Частичная подсекция

- **WHEN** загружается конфиг с `drivers.dispatch: {max_pickup_min: 12}`
- **THEN** `max_pickup_min` равно `12`, `cancel_grace_min` равно `5`, `cancel_prob_per_min` равно `0.0`, `cancel_max_prob` равно `0.9`

#### Scenario: Неизвестный ключ отклоняется

- **WHEN** конфиг содержит `drivers.dispatch.max_pickup`
- **THEN** загрузка завершается ошибкой с путём `drivers.dispatch.max_pickup`

#### Scenario: Недопустимое значение отклоняется

- **WHEN** конфиг содержит `drivers.dispatch.max_pickup_min: 0`, или `cancel_prob_per_min: -0.1`, или `cancel_max_prob: 1.5`
- **THEN** загрузка завершается ошибкой валидации, конфигурация не создана

### Requirement: Секция шоков спроса demand.shocks

Модель секции `demand` SHALL содержать вложенную подсекцию `shocks` с полями:

| поле | тип | дефолт | ограничение |

| `enabled` | bool | `false` | — |
| `city_sigma` | float | `0.12` | ≥ 0 |
| `city_tau_min` | float | `240` | > 0 |

`*_sigma` — стационарное стандартное отклонение компоненты логарифма множителя, `*_tau_min` — время корреляции в минутах. Значение вне ограничения SHALL отклоняться ошибкой валидации с путём до поля. Эталонный `config.yaml` SHALL содержать подсекцию со значениями, равными дефолтам, в том числе `enabled: false`.

#### Scenario: Недопустимое значение отклоняется

- **THEN** загрузка завершается ошибкой с путём `demand.shocks.holiday_mult`

### Requirement: Секция вызова подработчиков drivers.callout

Модель секции `drivers` SHALL содержать вложенную подсекцию `callout` с полями:

| поле | тип | дефолт | ограничение |
|---|---|---|---|
| `enabled` | bool | `false` | — |
| `part` | int | `60` | ≥ 0 |
| `lag_min` | int | `20` | ≥ 1 |
| `session_min` | int | `120` | ≥ 1 |
| `every_min` | int | `5` | ≥ 1 |
| `min_gain` | float | `0.10` | ≥ 0 |
| `sensitivity` | float | `0.3` | ≥ 0 |
| `max_share` | float | `0.3` | в (0, 1] |

`part` — число подработчиков сверх штатного парка `drivers.count`. Остальные поля задают правило вызова (capability `simulator-callout`) и его применение в минутном цикле (capability `simulator-loop`).

Конфиг без подсекции `callout` и конфиг с частью её полей SHALL загружаться, а недостающие поля SHALL браться из дефолтов. Неизвестные ключи внутри `callout` SHALL отклоняться с путём до ключа. Значение вне ограничения SHALL отклоняться ошибкой валидации с путём до поля. Эталонный `config.yaml` SHALL содержать подсекцию со значениями, равными дефолтам, в том числе `enabled: false`.

#### Scenario: Старый конфиг без подсекции

- **WHEN** загружается конфиг, где `drivers` задан как `{count: 380, wait_limit_min: 6}`
- **THEN** загрузка успешна, `drivers.callout.enabled` равно `false`, остальные поля равны дефолтам

#### Scenario: Частичная подсекция

- **WHEN** загружается конфиг с `drivers.callout: {enabled: true, lag_min: 30}`
- **THEN** `enabled` равно `true`, `lag_min` равно 30, остальные поля равны дефолтам

#### Scenario: Недопустимое значение отклоняется

- **WHEN** конфиг содержит `drivers.callout.lag_min: 0` или `drivers.callout.max_share: 1.5`
- **THEN** загрузка завершается ошибкой валидации с путём до поля, конфигурация не создана

#### Scenario: Неизвестный ключ отклоняется

- **WHEN** конфиг содержит `drivers.callout.bonus_rub`
- **THEN** загрузка завершается ошибкой с путём `drivers.callout.bonus_rub`
