- **Статус: ЧЕРНОВИК — ТРЕБУЕТ ДООБСУЖДЕНИЯ** (открытые вопросы собраны в §10; в конвейер веху не запускать, пока они не закрыты).
- Зафиксировано обсуждением от 2026-11-02.
- Последовательность вех: M1 Каркас → M2 Движок → **M3 ML** → M4 Сервер воспроизведения → M5 Интерфейс → M6 Вмешательство.
- Предпосылки: M1, M2 закрыты (`docs/plan-m1-foundation.md`, `docs/plan-m2-engine.md`); в SQLite лежит история: `trips`, `zone_metrics_5min`. Таблица `forecasts` пуста — её заполняет эта веха.
- Стек уже в `.venv`: torch, scikit-learn, numpy, pandas.

## 1. Цель вехи

Обучаемая на сгенерированной истории модель, которая для каждой зоны на каждом 5-минутном шаге предсказывает состояние на +15 и +30 минут, и честное сравнение её с бейзлайнами:

- построитель датасета (окна из SQLite, признаки, нормализация);
- multi-task LSTM: предсказание спроса и свободных водителей + вероятность дефицита;
- два бейзлайна-«наива» и сводная таблица метрик;
- CLI обучения и инференса; walk-forward заполнение `forecasts`;
- версионируемые артефакты модели в `artifacts/` (gitignored).

## 2. Границы

**Входит:** перечисленное в цели.

**Не входит:** ценовая политика и ветки теста — веха M6 (краткая фиксация наработанного — в §11); UI выбора параметров обучения — экран M5 (сами параметры заводятся здесь, в конфиге); онлайн-инференс в живом режиме — M4/M6 (здесь только оффлайн-прогон по истории).

## 3. Что предсказываем

Дефицит — это спрос против предложения, поэтому предсказываем **обе стороны** и вероятность их столкновения. Одна модель, несколько выходных головок (multi-task):

| Выход | Что это | Зачем |
|---|---|---|
| `pred_requests` | спрос в бакете ts+15 и ts+30 | главная кривая для графика «факт vs прогноз» |
| `pred_free_drivers` | свободные машины в тех же бакетах | вторая половина уравнения дефицита |
| `deficit_prob` | вероятность дефицита по правилу контракта | вход для ценовой политики (M6) |

Горизонты 15/30 мин — из контракта `forecasts`. Совместное предсказание спроса и предложения осознанно: они связаны (спрос поглощает машины), общая часть сети выучивает динамику обоих.

**Коэффициент тарифа модель НЕ предсказывает.** Мир предсказывает сеть, ценой управляет правило (порог по `deficit_prob`, шаг, потолок) — это M6. Формула ест прогноз целиком, а не один спрос.

## 4. Признаки и окно истории

Окно истории — **настройка обучения** (меняет размер входа сети): дефолт **6 ч = 72 пятиминутки**, диапазон 3–12 ч, параметр конфига `ml.window_hours`. В UI выносится в M5.

Признаки на каждый шаг окна (по зоне):

- метрики зоны из `zone_metrics_5min`: requests, completed, unfulfilled, free/busy drivers, avg_wait_min, supply_demand_ratio;
- календарь: час суток и день недели в циклическом кодировании (sin/cos), флаг выходного;
- среда: `is_rain`, `event`, `price_multiplier` (варьируется благодаря сурcharge-инъекциям M2);
- идентификация зоны: `zone_id` (эмбеддинг или one-hot — см. §10);
- **возвращающиеся водители**: сколько занятых на момент ts высадятся в ближайшие 15/30 мин — известно из расписания поездок, легально (без подглядывания в будущее) и сильно упрощает предсказание `free_drivers`.

Целевые значения: бакеты ts+15 и ts+30 (точечный прогноз бакета; накопительный вариант — открытый вопрос §10.6).

## 5. Модель и обучение

- Архитектура: LSTM-туловище → общее представление → три головки (2 регрессии × 2 горизонта + 1 классификация на дефицит). Детали (скрытая размерность, слои, dropout) — §10.2.
- Одна модель на все зоны (зона — признак), а не по модели на зону: данных на зону мало, общие закономерности одни.
- Нормализация признаков и целевых: scaler'ы scikit-learn, обучаются **только на тренировочной части**, сохраняются в артефакты.
- Разделение данных: целыми днями, train/test из конфига (дефолт ~80/20, выбирать будет UI M5); внутри train — хвостовые 2 дня как валидация для ранней остановки.
- Обучение: seed фиксируется, loss — взвешенная сумма регрессий (MSE/MAE) и классификации (BCE); кривая loss сохраняется в артефакты.
- Объём: 30 дней × 288 бакетов × 6 зон ≈ 50 тыс. примеров — достаточно для небольшой LSTM (при слабых метриках первым делом догенерировать данные, а не усложнять архитектуру).

## 6. Бейзлайны и метрики

Бейзлайн — нарочно примитивная модель-эталон, с которой сравнивают нейросеть, чтобы показать её полезность. Два наива, без обучения:

- **«как сейчас»** (persistence): прогноз = последнее наблюдение;
- **сезонный наив**: прогноз = значение сутки назад в тот же слот (сильный противник при суточной сезонности).

Метрики: MAE и RMSE по `pred_requests` и `pred_free_drivers` (по горизонтам), precision/recall/F1 детекции дефицита (порог 0.5), сводная таблица «наив-1 / наив-2 / LSTM» — она же экран метрик в M5 и таблица отчёта.

## 7. Инференс и таблица forecasts

Walk-forward по тестовой части: на каждом 5-минутном шаге модель видит только прошлое окно, пишет строку `forecasts(ts, zone_id, horizon_min∈{15,30}, pred_requests, pred_free_drivers, deficit_prob, model_version)`. `model_version` — строка вида `lstm-v1-<дата>`; связывает прогнозы с конкретными артефактами.

## 10. ОТКРЫТЫЕ ВОПРОСЫ (закрыть до запуска вехи)

1. **`deficit_prob`: классификационная головка или вывод из регрессий?** Вариант A: отдельная BCE-головка на метку дефицита (просто). Вариант B: вероятность из распределения ошибок регрессий (сложнее, зато согласованная с кривыми).
2. **Архитектура точно**: скрытая размерность, число слоёв, dropout; эмбеддинг зоны vs one-hot.
3. **Нормализация**: MinMax vs Standard; глобальная vs по-зонная.
4. **Баланс потерь** регрессии и классификации в общем loss.
5. **Окно по умолчанию 6 ч** — подтвердить экспериментально (сравнить 3/6/12 на валидации).
6. **Таргет спроса**: точечный бакет ts+15 vs накопленный спрос за горизонт (ts, ts+15]. Влияет на поведение политики M6.
7. **Калибровка** `deficit_prob` (предсказала 70% — сбывается ли в 70%): нужна ли отдельная процедура.
8. Достаточно ли 30 дней; стратегия догенерации при слабых метриках.

## 11. Захвачено из обсуждения — для будущей вехи M6 (Вмешательство)

Тестовая эпоха — лаборатория политик на одном seed (детерминизм M2):

- **A «без управления»** — тариф 1.0, записанный факт;
- **B «реактивный»** — правило по текущему состоянию (дефицит уже случился → поднимаем цену); анти-пример из первого абзаца ТЗ;
- **C «предиктивный»** — тариф по прогнозу модели за 15–30 мин;
- **D «жадная»** (опционально) — множитель всегда на потолке; живая демонстрация, что высокий коэффициент ≠ прибыль.

Метрики веток: поездок, невыполненных, среднее ожидание, **выручка** (= Σ базовая цена маршрута × `price_multiplier`, вычислима post-hoc по решению M2). Ожидаемая картина: B лучше A, C лучше B (механика лага: реактивная опаздывает на несколько пятиминуток), D проседает по выручке. Порог/шаг/потолок политики — тюнингуемые параметры M6, критерий: unfulfilled вниз при не просевшей выручке.
