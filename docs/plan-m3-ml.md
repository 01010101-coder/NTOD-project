## 1. Цель вехи (картина конца)

После вехи существуют:

1. `data/m3_epoch.db` — единый прогон 37 дней (seed 42): первые 30 дней побитово
   идентичны `data/taxi.db` (детерминизм A7), дни 31–37 — свежее продолжение.
2. Пакет `ml/` и CLI `python -m ml train …` / `python -m ml infer …`.
3. `artifacts/` — версонируемые артефакты двух моделей: веса, scaler'ы,
   `metrics.json`, кривая loss, сводная таблица метрик.
4. `forecasts` заполнена walk-forward на тест-эпохе: 4 `model_version`
   (два наива + MLP + LSTM) × 24 120 строк.
5. Сводная таблица «наив-1 / наив-2 / MLP / LSTM»: MAE/RMSE по таргетам и
   горизонтам, precision/recall/F1 дефицита, таблица калибровки.
6. Вкладка «Лаборатория» в веб-интерфейсе: факт vs прогноз, метрики, ошибки,
   калибровка, кривая loss.
7. Автотесты анти-утечки: ни окно, ни таргет, ни scaler'ы, ни walk-forward не
   видят будущее.

Бизнес-цели человеческим языком (рамка для отчёта и защиты):

- **Город перестаёт удивляться пикам** — система видит зарождающийся дефицит за
  15–30 минут (ритм суток, дождь, «пятничный вечер», сушение стока).
- **Время на действие вместо реакции** — прогноз на 15/30 минут вперёд даёт
  перебросить парк или поднять тариф до очереди без машин (деньгами разницу
  покажет M6; без прогноза сравнивать нечего).
- **Известная цена доверия** — MAE в заказах и F1 детекции против двух наивов
  превращают «нейросеть находит закономерности» в измеренный факт.
- **Честность** — walk-forward и анти-лик автотесты: каждая строка прогноза
  рождена моделью, видевшей только прошлое.
- **Фундамент M5/M6** — M5 рисует «факт vs прогноз» из `forecasts`, M6 кормит
  политику цены `deficit_prob`. Модель — оракул (6 чисел на зону раз в 5 минут);
  цену она не предсказывает и не назначает.

## 4. Вход: окно и признаки

Окно истории — настройка обучения `ml.window_hours`, дефолт **6 ч = 72
пятиминутки**, диапазон 3–12 (дефолт подтверждается свипом, §8 m3-train-cli).
Один пример = одна зона в момент ts. Признаки на каждый шаг окна:

| Группа | Признаки | Источник |
|---|---|---|
| метрики зоны | requests, completed, unfulfilled, free_drivers, busy_drivers, avg_wait_min, supply_demand_ratio | `zone_metrics_5min` (снапшот конца интервала — семантика M2) |
| календарь | час sin/cos, день недели sin/cos, флаг выходного | из ts |
| среда | is_rain, event, price_multiplier | `zone_metrics_5min` |
| возвращающиеся водители | ret_15, ret_30: число занятых на момент ts поездок с `dest_zone = зона` и `dropoff_at ∈ (ts, ts+H]` | `trips` (расписание уже назначенных поездок; легально: известно в момент ts) |

Итого 17 признаков на шаг. Идентификация зоны — обучаемый эмбеддинг
`nn.Embedding(Z, ml.zone_embed_dim=8)`: в MLP конкатенируется к плоскому входу,
в LSTM — к каждому шагу. Вход MLP: flatten 72×17 + 8 ≈ 1.2 тыс.

Замечание честности: `price_multiplier` в train-эпохе почти без дисперсии
(171 поездка с surge за 30 дней, m2_analysis) — признак оставляем (нужен M6),
но ожидаем, что модель на нём почти не выучит реакции цены. Усиление
инъекций — вопрос M6 (§11), в этой вехе мир не меняется.

Таргеты (точечный бакет, не накопительный): requests и free_drivers в бакетах
ts+15 и ts+30; метка дефицита в тех же бакетах по правилу контракта
(`free_drivers / max(requests,1) < 0.5` или `unfulfilled > 0`).

**Слоистость (требование M6).** Сборка признаков отделена от источника строк:
протокол `RowSource` (метрики окна + расписание поездок), единственная
реализация в этой вехе — `SqliteRowSource(m3_epoch.db)`. Реализация поверх
живого состояния движка — M6, без переписывания сборки.

## 5. Модель и обучение

Контракт туловища: **окно (72×17) + zone_id → представление R (128)**. Две
реализации, всё остальное общее:

| | MLP-туловище | LSTM-туловище |
|---|---|---|
| вход | flatten + эмбеддинг зоны | шаги с эмбеддингом зоны на каждом |
| слои | Dense(256) ReLU → Dropout(0.1) → Dense(128) | LSTM(hidden=64, layers=1) → последний h → Dense(128) |
| роль | основная модель (тема курса) | сравнение (буква ТЗ) |

Головки общие, из R=128: Linear→2 (спрос +15/+30), Linear→2 (сток +15/+30),
Linear→2 (дефицит-логиты +15/+30 — **одна BCE-головка с двумя выходами**,
ровно как лежит в контракте `forecasts`: вероятность в строке каждого
горизонта).

- Одна модель на все зоны (зона — признак): данных на зону мало, закономерности
  общие; дефицит по зонам перекошен (4.4%…48.2%) — зона обязана быть признаком.
- Нормализация: `StandardScaler` глобальный (один на признак, не по-зонный);
  таргеты регрессий — отдельными scaler'ами. Fit **только на train**; scaler'ы
  сериализуются в артефакт.
- Loss: MSE(спрос) + MSE(сток) + `ml.cls_weight` × BCE(дефицит, два выхода,
  `pos_weight = neg/pos` по train-доле дефицитных бакетов ≈ 4.3). Оптимизатор
  Adam, lr из конфига; батч 256; эпох ≤ 100, ранняя остановка по val-loss,
  терпение 8.
- Детерминизм: `ml.seed` фиксирует torch и numpy; два обучения с одним seed
  дают идентичные метрики (автотест).
- Правила честного сравнения (закреплены): у архитектур одинаковые сплит,
  scaler'ы, окно, веса loss, терпение; каждой — один стартовый конфиг; свип
  окна 3/6/12 — только на MLP, LSTM учится на окне-победителе.

## 6. Бейзлайны и метрики

Два наива без обучения, пишут `forecasts` наравне с сетями:

- **«как сейчас»** (persistence): прогноз = последнее наблюдение на ts;
  `deficit_prob` = текущий флаг дефицита (0/1). `model_version=naive-persist-v1`.
- **«сутки назад»** (сезонный наив): значение из того же слота вчера;
  `deficit_prob` = флаг дефицита того слота. `model_version=naive-season-v1`.

Метрики: MAE и RMSE по pred_requests и pred_free_drivers на каждом горизонте;
precision/recall/F1 дефицита (порог 0.5) на каждом горизонте; таблица
калибровки (10 бинов прогнозной вероятности → доля сбывшихся). Печатная сводная
— 4 строки × 7 колонок (MAE req+15/req+30/free+15/free+30, RMSE req+15,
F1 def+15/def+30); полный набор — в `artifacts/summary-<дата>.json`.

## 7. Инференс: walk-forward и `forecasts`

Walk-forward по тест-эпохе: для каждого ts (с шагом 5 мин) и каждой зоны модель
видит окно, заканчивающееся на ts, и пишет две строки
`forecasts(ts, zone_id, horizon_min∈{15,30}, pred_requests, pred_free_drivers,
deficit_prob, model_version)`. Границы: только ts с существующим бакетом ts+30
(последние 6 бакетов тест-эпохи пропускаются). Наивы пишутся тем же проходом.
`model_version` нейросетей: `{arch}-v1-{YYYY-MM-DD}` — связка прогнозов с
артефактами.

Правило отсутствия заглядываний (главный класс тестов, §9): вход прогноза на ts
содержит только строки с бакетом ≤ ts; расписание поездок — только поездки,
назначенные до ts; scaler'ы fit на train; walk-forward не читает тест-строки
как вход.

## 11. Захвачено для M6 (Вмешательство)

Лаборатория политик на одном seed. Всё ниже — решения этой вехи M3, зафиксированные
рано, чтобы не потерять:

- **Контур только при генерации, просмотр — чистый replay.** Все записи
  (train-эпоха + ветки) генерируются заранее, до просмотра; сервер в продукте —
  проигрыватель записей, модель в нём не работает.
- Ветки: **A «без модели» / B «MLP» / C «LSTM»** (модель управляет тарифом через
  `deficit_prob`); дизайн под **N веток** — реактивная (анти-пример ТЗ) и жадная
  подключаются без переделок.
- **Точность модели — только против ветки A** (факт не искажён её действиями);
  в B/C меряем исходы: поездки, невыполненные, ожидание, выручка
  (Σ (`base_boarding + per_min × path_min`) × `price_multiplier`). Точность
  внутри контура — коварная метрика (self-fulfilling prophecy), не показываем.
- Подключение политики — существующий шов `Engine(price_fn=…)` (§10.13 плана
  M2), rng не тратит.
- **Разделение rng-потоков — вместе с веточным генератором M6, не отдельным
  change**: экзогенные погода/события/инъекции в отдельный `Generator`
  (SeedSequence), иначе после первой смены цены погода разъедется между ветками
  и A/B сравнение замутится. После разделения — один контрольный прогон
  `simulator.calibrate` (коридор [10, 20] имеет запас).
- Ветки = полный перезапуск с seed (37+дней ≈ 25–50 с; до активации политики
  побитово идентичны), снапшоты состояния не нужны.
- **Правило выбора модели для M6 (закоммитить до обучения):** политику кормит
  модель с лучшим test-F1 детекции дефицита; при разнице < 0.02 — MLP (дешевле
  инференс).
- `RowSource` поверх живого движка — реализация M6 (слой заложен в §4).
- Накопительный таргет спроса (ts, ts+H] — пересмотреть при проектировании
  политики; усиливать ли surge-инъекции (признак цены почти мёртв: 171 поездка)
  — туда же.
- UI M6: переключатель миров в «Городе» (4 записи: эпоха + 3 ветки); «Сравнение»
  — отдельная вкладка (сводная таблица исходов + расходящиеся линии
  кумулятивной выручки).
