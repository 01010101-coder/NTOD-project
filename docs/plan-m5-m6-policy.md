# План M5+M6 «Лаборатория политик» (интерфейс + вмешательство)

- **Статус: ЧЕРНОВИК К ОБСУЖДЕНИЮ.** Обсуждение 2026-11-07 (explore-сессия); открытых
  блокеров нет, числа ступеней — стартовые, калибруются в change'е m6-worlds.
- Последовательность вех: M1 Каркас → M2 Движок → web-линейка (закрыта) → M3 ML
  (закрыта) → **M5+M6 объединены в эту веху**. Обоснование слияния: web-линейка и
  вкладка «Лаборатория» уже закрыли ~80 % старого M5; остаток M5 (унификация миров,
  seek-связка) — это сантехника, без которой переключатель миров M6 не работает.
  Один пользовательский сценарий — одна веха.
- Предпосылки: `data/m3_epoch.db` (37 дней, seed 42, побитово = taxi.db на первых 30),
  артефакты двух моделей в `artifacts/`, `forecasts` 24 120 × 4, вкладки «Город» и
  «Лаборатория» работают. Швы готовы: `Engine(price_fn=…)` (§10.13 M2, rng не
  тратит), `RowSource`-протокол в `ml/dataset.py` (живой источник — наша реализация),
  сервер = (ReplayLog, meta) на мир.
- Стек: уже установленный. Новых зависимостей нет.
- **Ключевые решения вехи (2026-11-07):**
  1. Ветки: **A «без модели» / B «реактивная» / C «MLP» / D «LSTM»** — реактивная
     вставлена второй, модели сдвинуты (анти-пример ТЗ внутри сетки веток).
  2. Форма политики — **ступени**; числа стартовые, живут в `config.yaml` (секция
     `policy:`), калибруются позже (задача в m6-worlds).
  3. Экран параметров обучения в UI — **выброшен** (параметры в `config.yaml`).
  4. Окраска карты — **тумблер «факт/прогноз»**.
  5. «Эпоха» в переключателе = replay `m3_epoch.db`; live-режим пользователю не
     показывается — внутренний двигатель генератора веток (§11 M3: сервер в продукте —
     проигрыватель записей).
  6. Композиция с погодным surge — **умножением** (тариф_мира × политика), не
     подменой: иначе политика в дождь делала бы ветку дешевле базовой.
  7. Тень-прогноз: в каждой ветке обе модели считают `deficit_prob` и пишут его в
     `forecasts` этой ветки (политика использует его только в C/D) — тумблер
     «прогноз» и «факт vs прогноз» работают во всех мирах.

## 1. Цель вехи (картина конца)

После вехи пользователь открывает приложение и:

1. **Переключатель миров в «Городе»** — 5 записей: «Эпоха» (m3_epoch.db) + 4 ветки
   одной тест-недели (A/B/C/D). Одна и та же неделя, один seed — четыре ценовых
   мозга. Карта, время, скорость — как сейчас, для каждого мира.
2. **Тариф виден на карте**: бейдж множителя на зоне (×1.15/×1.3/×1.5), тумблер
   окраски «факт/прогноз» (прогноз = `deficit_prob` тень-модели).
3. **Seek-связка**: клик по точке графика «Лаборатории» прыгает картой «Эпохи» на тот
   же момент (связка действует в мире «Эпоха» — данные «Лаборатории» из неё).
4. **Вкладка «Сравнение»** — экран вердикта: таблица исходов тест-недели по веткам
   (поездки, невыполненные, ожидание, выручка) + расходящиеся линии кумулятивной
   выручки.
5. **Точность — только против ветки A** (факт не искажён действиями политики);
   внутри C/D точность не показываем (self-fulfilling prophecy, §11 M3).

Артефакты: `config.yaml` с секцией `policy:`; `data/worlds/{a-base, b-reactive,
c-mlp, d-lstm}.db`; `artifacts/policy-calibration.json` (δ-сдвиги, частоты
срабатываний); REST `/api/ml/worlds`, `/api/ml/compare`; 5 закрытых changes.

Бизнес-цели человеческим языком (рамка защиты):

- **«Включите ветку C — смотрите»**: на одном seed ML-тариф заранее (15 мин)
  прижимает спрос в зоне, которую ждёт дефицит; реактивная (B) опаздывает и мигает;
  A — красный дефицит и брошенные заказы.
- **Вердикт числом**: «MLP-тариф: −X % невыполненных, +Y % выручки против A и B на
  одной неделе» — вместо призыва поверить.
- **Границы честности**: равная частота вмешательств у C и D (δ-калибровка);
  сравнение прогнозной силы, а не шкалы самоуверенности сетей.

## 2. Границы. Чего НЕ делать

**Входит:** rng-разделение; веточный генератор; ступенчатая и реактивная политики;
контур генерации (RowSource поверх живого движка, инференс из артефактов M3);
δ-калибровка; генерация A/B/C/D с тень-прогнозами; переключатель миров; тумблер
факт/прогноз; бейдж тарифа; seek-связка; вкладка «Сравнение».

**Не входит и запрещено:**

1. Ретрейн моделей, Platt/изотонная калибровка вероятностей — δ-сдвиг ступеней
   достаточен; артефакты M3 не трогаем.
2. Регенерация `m3_epoch.db` и пере-валидация M3 — эпоха остаётся как есть; мир
   веток после rng-разделения свой (см. §3), сравнение веток — внутри их самих.
3. Гистерезис/сглаживание ступеней — только если мигание реально помешает
   (патч-запас, §9.2); не делать превентивно.
4. Live-сервер как пользовательский режим, кнопка «пожить сейчас» — нет.
5. Экран параметров обучения, ретрейн из браузера — выброшено (решение 3).
6. Новые зависимости, GPU, сборка фронтенда — нет; canvas + REST/WS как сейчас.
7. Политики помимо четырёх веток (жадная, оптимизационная) — нет; дизайн N-веток
   сохраняется (реестр миров — список, не перечисление).

## 3. Мир и ветки

- **Rng-разделение.** Сейчас один `Generator` на мир (§10.9 M2): погода/события/
  инъекции и спрос/высадки пьют из одного потока — после первой же смены цены
  (ветка C/D) погода разъехалась бы между ветками. Разделение: экзогенные розыгрыши
  `WorldEnv` — в отдельный `Generator`, высаженный из `SeedSequence(seed)` рядом с
  основным; эндогенные (спрос, дропофф-дрейф) остаются в основном.
- **Следствие, принять явно:** после разделения последовательности розыгрышей иные,
  мир веток ≠ m3_epoch побитово. Это нормально: эпоха — самостоятельная запись
  («Эпоха» в переключателе), ветки сравниваются между собой. Контроль: один прогон
  `simulator.calibrate`, коридор дефицита [10, 20] % имеет запас (§11 M3).
- **Ветки** — полный перезапуск, seed 42, 37 дней, политика активна **только дни
  31–37** (тест-неделя; 30 дней — прогрев и оседание парковки). До дня 31 все ветки
  **побитово идентичны** — автотест сравнивает дампы дней 1–30. Ориентир: 25–50 с
  на ветку (прецедент M3), четыре ветки + контрольный прогон ≈ 3–4 мин.
- **Хранение:** по одной БД на ветку в `data/worlds/` (транспортный формат уже
  существует — сервер ест «БД + meta»); тень-прогнозы — в `forecasts` этой же БД
  (`model_version` = `mlp`/`lstm`; PK схемы подходит без миграций).

## 4. Политика (ступени)

Форма (решение 2): множитель ступенями по **эффективной вероятности**
`p_eff = clip(deficit_prob + shift[model], 0, 1)`; итоговый тариф зоны =
`тариф_мира(t) × множитель`, с потолком `total_cap` (композиция умножением —
решение 6). Горизонт — один на обе модели: где test-F1 выбранной политики лучше
(ожидаемо 15 мин; фиксируется до генерации, прецедент «правила до эксперимента»).

Стартовые числа (Приложение А; калибровка — m6-worlds):

| p_eff | множитель |
|---|---|
| < 0.40 | ×1.00 |
| ≥ 0.40 | ×1.15 |
| ≥ 0.60 | ×1.30 |
| ≥ 0.80 | ×1.50 |

- **Ветка B «реактивная»** (анти-пример ТЗ): дефицит в зоне **сейчас** → ×1.30,
  иначе ×1.00. Без прогноза, без упреждения; мигание у неё — часть патологии,
  которую контрастируем.
- **δ-калибровка честности:** `shift.mlp`/`shift.lstm` подбираются на валидационных
  днях 29–30 m3_epoch (офлайн-инференс, walk-forward-машина M3) так, чтобы частота
  «любая ступень активна» совпадала у обеих моделей и ≈ `target_fire_rate`.
  Стартовые δ = 0.0; результат — `artifacts/policy-calibration.json` + обновление
  `config.yaml`.
- При α = 1 (§3 `demand.py`) цена в спокойной зоне почти рублёво-нейтральна
  (меньше заказов × дороже каждый); рублёвая игра — в дефицитных моментах. Ожидаемо:
  главный выигрыш C/D — невыполненные заказы и ожидание, выручка расходится
  скромнее — честно отразить в отчёте вехи.

## 5. Контур генерации (только при генерации, просмотр — чистый replay)

```
seed 42 ──▶ 37 дней движка ──▶ data/worlds/{a,b,c,d}.db
                │  дни 31–37, в C/D:
                ▼
  тик движка → LiveRowSource (новая реализация RowSource) → сборка признаков
  (ml/dataset, слой M3 §4) → инференс из артефактов M3 (без ретрейна)
  → deficit_prob → ступени → price_fn → движок
```

- `price_fn` — существующий шов (§10.13 M2): rng не тратит, розыгрыши инъекций
  происходят; в A/B возвращаем тариф мира (A) / реактивное правило (B).
- Тень-прогноз (решение 7): в каждой ветке обе модели инференсатся независимо от
  политики и пишутся в `forecasts` — карта «прогноз» и факт-vs-прогноз работают
  во всех мирах.
- Анти-лик: признаки контура собираются только из прошлого относительно момента
  прогноза (автотест по прецеденту M3); детерминизм ветки — повторный прогон даёт
  побитово ту же БД.

## 6. UI

- **Переключатель миров** — выпадающий список в «Городе»: Эпоха / A / B / C / D
  (реестр: имя, файл БД, метка политики). Смена мира = смена (ReplayLog, meta),
  позиция сбрасывается на старт мира.
- **Тумблер «факт/прогноз»** — окраска зоны текущим дефицитом или `deficit_prob`
  тень-модели (переключатель модели не нужен: показываем модель политики C? нет —
  выбранную в «Лаборатории» `model_version`, дефолт = лучшая по test-F1).
- **Бейдж тарифа** — актуальный множитель зоны (округление ×1.2), включая мирной
  части (дождь ×1.5 виден и в A).
- **Seek-связка** — клик по графику «Лаборатории» (мир «Эпоха»): карта прыгает на
  момент; в чужих мирах — переключить на «Эпоху» и прыгнуть (одно действие).
- **Вкладка «Сравнение»** — REST `/api/ml/compare`: таблица веток × исходов
  (поездки, невыполненные, среднее ожидание, выручка — Σ (`base_boarding +
  per_min_rub × path_min`) × `price_multiplier`, прецедент §11 M3) + линии
  кумулятивной выручки тест-недели; точность тень-моделей — против факта ветки A.

## 8. Риски и патч-запасы

1. После rng-разделения дефицит выйдет из коридора [10, 20] → ворота в change'е 1:
   сначала контрольный прогон calibrate, при выходе — перес-калибровка до веток.
2. Мигание ступеней у границ (0.39↔0.41) → патч-запас: гистерезис (шаг вниз при
   p_min − 0.10); включать только по факту, не превентивно.
3. Выручка расходится слабо (α = 1 нейтральность) → первичный метрический выигрыш —
   невыполненные заказы/ожидание; отразить в отчёте, не подкручивать мир под
   красивые цифры.
4. δ не выравнивает частоты на валидации → зафиксировать в
   policy-calibration.json как честное ограничение, не изобретать Platt.
5. Инференс в контуре замедляет генерацию → замер в change'е 2; запас — окна/признаки
   уже считаются за O(минуты) на всю тест-неделю в M3.

## Приложение А. Конфиг `policy:` (стартовые числа, калибровка — m6-worlds)

```yaml
policy:
  horizon_min: 15          # лучший test-F1; фиксируется до генерации веток
  stairs:                  # p_eff = clip(deficit_prob + shift[model], 0, 1)
    - { p_min: 0.80, mult: 1.50 }
    - { p_min: 0.60, mult: 1.30 }
    - { p_min: 0.40, mult: 1.15 }
  total_cap: 2.0           # итог = тариф_мира × множитель, потолок суммарного тарифа
  reactive_mult: 1.30      # ветка B: дефицит сейчас → ×1.30
  shift: { mlp: 0.0, lstm: 0.0 }   # δ-калибровка частоты срабатываний
  target_fire_rate: 0.10   # цель: ступень активна в ~10 % зон-моментов
  worlds_dir: data/worlds  # реестр: a-base, b-reactive, c-mlp, d-lstm
```
